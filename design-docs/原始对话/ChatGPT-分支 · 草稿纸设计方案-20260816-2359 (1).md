# 草稿证据驱动的高中数学知识诊断与学习规划 Agent 产品设计方案

## 一、产品定位

产品建议定义为：

> **以数字草稿为主要数学表达空间、以聊天为诊断控制通道、以过程证据为依据的高中数学主动诊断与学习规划 Agent。**

学生在草稿纸上完成画图、辅助线、条件标注、列式、推导和修改；Tutor Agent 在聊天栏发题、追问、提示和总结。Agent原则上不直接修改学生草稿，避免破坏真实思维过程。

赛题要求以“解三角形”为首个试点章节，完成知识点库、题型库、错因库、题库和诊断规则的数据结构化，通过少量题目和多轮对话完成知识诊断，并输出掌握度报告和一至四周学习计划。最低数据规模包括不少于25个知识点、20个题型、20个错因、80道题、20条诊断规则和3个完整学生案例。`deep-research-report.md` `deep-research-report.md`

大赛官网进一步要求作品基于大模型构建，并至少体现工具调用、规划或记忆中的一种 Agent 特征；作品须可运行、可演示，评审权重为业务价值30%、技术实现20%、创新性20%、完成度20%、展示表达10%。`大赛官网信息.txt` `大赛官网信息.txt`

因此，草稿纸不能只作为视觉效果，应同时承担三项核心职责：

1. **学生表达载体**：保留真实数学书写和思考习惯。
2. **Agent观察环境**：允许Agent主动查看近期内容、局部区域和历史变化。
3. **诊断证据来源**：为方法选择、错误位置、修改过程和提示依赖提供证据。

产品闭环为：

> 学生画像 → 轻量发题 → 草稿作答 → 主动观察 → 确认式追问 → 错因消歧 → 掌握度报告 → 学习计划 → 复测与状态更新。

## 二、三类用户对象

### 1. 学生端

学生端是主要产品界面，采用“左侧聊天、右侧草稿”的双栏布局。

学生能够：

- 填写年级、当前分数、目标分数、可投入时间和自认为薄弱的内容；
- 接收题目、追问、提示和阶段总结；
- 使用数字笔迹或纸面照片表达思路；
- 查看知识掌握报告、错因证据和学习计划；
- 在后续训练中进行复测并观察变化。

学生不需要理解知识点ID、规则编号或诊断算法。

### 2. 教师端

教师端主要用于复核，而不是代替Agent操作。

教师能够：

- 查看原题、最终答案、草稿关键帧和聊天过程；
- 查看Agent判断的知识点、题型、错因和置信度；
- 区分“学生错误”和“视觉识别不确定”；
- 将结论确认、修改为其他错因或标记为“待观察”；
- 查看学生在多次测评中的掌握度变化。

比赛版只需实现单学生、单结论的复核页面，不必建设完整班级管理系统。

### 3. 教研与内容运营端

教研人员负责维护章节内容包：

- 知识点及前置关系；
- 题型及典型解法；
- 常见错因和鉴别依据；
- 题目、答案、解析和评分点；
- 诊断规则；
- 补弱建议、练习和复测题。

赛题提供的Excel模板作为导入和交换格式；正式运行时应导入结构化数据库，避免Agent直接反复读取Excel。

## 三、核心领域对象设计

### 1. 章节内容对象

| 对象 | 主要职责 | 核心属性 |
|---|---|---|
| `ChapterPackage` | 封装一个可独立发布的章节诊断包 | 章节、版本、适用年级、发布状态 |
| `KnowledgePoint` | 描述知识点及前置依赖 | K-ID、层级、掌握标准、前置点 |
| `QuestionType` | 描述题型和标准解法结构 | T-ID、典型问法、步骤、评分点 |
| `ErrorCause` | 描述可诊断错因 | E-ID、表现、鉴别依据、补救方法 |
| `Question` | 提供正式题目或微型诊断探针 | Q-ID、题干、答案、难度、标签 |
| `DiagnosisRule` | 将证据映射到候选诊断 | R-ID、触发条件、支持错因、后续动作 |
| `SolutionPath` | 描述同一题目的不同合法解法 | 解法名称、适用条件、步骤模式 |

一个题目可以关联多个知识点、题型和候选错因，避免“一题答错就绑定一个错误”。

### 2. 学习过程对象

| 对象 | 主要职责 |
|---|---|
| `StudentProfile` | 保存当前水平、目标、时间预算和设备条件 |
| `AssessmentSession` | 管理一次诊断的题量、阶段、时间和当前假设 |
| `QuestionAttempt` | 保存学生对某道题的一次完整作答 |
| `ChatTurn` | 保存Agent和学生的正式对话 |
| `DraftSheet` | 保存某道题对应的独立草稿 |
| `StrokeEvent` | 保存笔画坐标、时间、压力、擦除和撤销事件 |
| `ObservationAsset` | 统一表示草稿快照、局部图、回放片段或纸面照片 |
| `Evidence` | 将原始作答转化为支持、反对或不确定证据 |
| `DiagnosticHypothesis` | 表示当前候选错因及概率 |
| `DiagnosticClaim` | 表示最终或阶段性诊断结论 |
| `StudentState` | 保存知识、题型、错因和策略的长期状态 |
| `LearningPlan` | 保存一至四周目标、任务、资源和复测点 |
| `TeacherReview` | 保存教师对AI结论的确认和修改版本 |

核心对象关系可概括为：

```text
ChapterPackage
 ├─ KnowledgePoint
 ├─ QuestionType
 ├─ ErrorCause
 ├─ Question
 └─ DiagnosisRule

AssessmentSession
 ├─ ChatTurn
 ├─ QuestionAttempt
 │   └─ DraftSheet
 │       ├─ StrokeEvent
 │       └─ ObservationAsset
 ├─ Evidence
 ├─ DiagnosticHypothesis
 └─ DiagnosticClaim
      ├─ StudentState
      ├─ LearningPlan
      └─ TeacherReview
```

### 3. 关键对象约束

- `DraftSheet`只能由学生书写行为修改。
- Agent只能通过观察工具读取草稿，不能直接写入学生笔迹层。
- 原始笔迹、照片和回答不可被AI结论覆盖。
- 视觉识别结果属于派生数据，必须保存置信度和原始资产引用。
- 教师修正生成新版本，保留AI原始结论。
- 掌握度更新必须引用证据，不能由大模型自由填写分数。

## 四、草稿纸产品设计

## 4.1 界面结构

平板和电脑端建议采用：

```text
┌───────────────┬──────────────────────────────┐
│ 聊天与题目区   │ 当前题目草稿纸                │
│               │                              │
│ Agent发题      │ 题干固定区或可折叠题目卡       │
│ 确认式追问     │                              │
│ 学生文字回答   │ 学生自由书写区                 │
│ 阶段提示       │                              │
│               │ 页码、撤销、清空、移动画布       │
└───────────────┴──────────────────────────────┘
```

草稿工具只保留：

- 一种基础笔触；
- 橡皮或撤销；
- 清空当前页；
- 缩放和移动画布；
- 新建附加草稿页。

不加入自动画直线、公式美化、图形吸附等功能，避免学生为了操作软件而改变真实解题方式。

## 4.2 一题一草稿

每一道题创建独立的`DraftSheet`，并与`QuestionAttempt`绑定。

这样可以：

- 清晰区分每道题的过程证据；
- 在报告中回溯具体错误；
- 对比同一知识点不同时间的作答；
- 防止多道题笔迹混杂；
- 支持完整案例回放。

## 4.3 近期内容优先观察

系统不应每次把完整笔迹坐标或整张高清草稿发送给模型。

一次有效停笔后，感知服务生成：

1. 最近一段时间新增笔迹的局部高清图；
2. 当前整张草稿的低分辨率缩略图；
3. 与上一次观察状态的差异图；
4. 新增、删除和重画区域的坐标摘要。

Agent默认只查看近期变化。当证据不足时，再主动调用工具查看局部、整页或历史过程。

这种设计同时降低视觉调用成本，并使Agent的注意力集中在学生刚刚发生的思维变化上。

## 4.4 纸面拍照模式

纸面照片和数字草稿统一抽象为`ObservationAsset`。

处理流程为：

```text
拍照上传
→ 裁边与透视校正
→ 去阴影和清晰度检测
→ 保存原图与校正图
→ 多模态模型观察
→ 必要时局部OCR或公式识别
→ 聊天确认
→ 形成诊断证据
```

学生可以选择：

- 完成后上传，进行整体诊断；
- 写到一半上传，说明“我卡在这里”；
- 修改后再次上传，系统比较两张照片中的新增内容。

数字草稿提供连续过程，纸面照片提供低门槛覆盖，两种模式进入同一诊断体系。

## 五、Tutor Agent运行机制

## 5.1 Agent状态循环

每轮交互执行以下流程：

```text
观察学生输入
→ 调用判题或草稿观察工具
→ 形成若干候选诊断假设
→ 判断证据是否充分
→ 选择下一动作
→ 更新学生状态
```

下一动作只能从有限集合中选择：

- `ASK_PROBE`：发一道新的微型诊断题；
- `ASK_REASON`：询问学生为什么这样做；
- `CONFIRM_VISUAL`：确认草稿中某个图形或公式的含义；
- `INSPECT_REGION`：放大查看草稿局部；
- `REPLAY_CHANGE`：查看书写顺序或修改过程；
- `GIVE_HINT`：按提示等级给出引导；
- `RETEST`：用等价或更简单题复核；
- `FINALIZE`：结束诊断并生成报告。

这能够明确体现大赛要求的工具调用、规划和记忆能力。

## 5.2 草稿观察工具

建议至少实现以下工具：

| 工具 | 功能 |
|---|---|
| `inspect_recent(seconds)` | 查看最近新增内容 |
| `inspect_region(bbox)` | 查看指定局部高清图 |
| `inspect_full_canvas()` | 查看整体布局和解法分支 |
| `compare_draft(t1,t2)` | 判断新增、删除和重画 |
| `replay_region(bbox,t1,t2)` | 查看局部书写顺序 |
| `recognize_region(bbox,mode)` | 识别文字、公式或图形 |
| `verify_math(expression)` | 验证公式、数值和条件 |
| `select_probe(hypotheses)` | 选择最能区分候选错因的问题 |
| `ask_student_to_confirm()` | 在视觉含义不确定时请求确认 |

所有观察结果应返回：

- 原始资产ID；
- 观察区域；
- 识别结果；
- 置信度；
- 警告信息。

## 5.3 确认式追问

多模态模型不应将视觉推断直接写入正式诊断。

例如Agent看到学生画了一条从顶点到底边的线，可以询问：

> “我看到你从A点向BC补了一条线。你是准备把它当作高，使用面积关系吗？”

学生确认后，才形成“尝试面积法”的可靠证据。

若学生否认，则更新为“视觉理解错误”，不影响掌握度。

## 5.4 假设驱动的错因消歧

一道SSA题答错后，系统可能同时保留：

- 不会正弦定理；
- 边角对应错误；
- 反三角函数计算错误；
- 忽略补角；
- 忘记检查三角形存在条件；
- 偶然计算错误。

Agent选择能够最大程度区分这些原因的追问，而不是立即推荐整章重学。

建议比赛版采用可解释的离散证据权重：

| 证据类型 | 建议权重 |
|---|---:|
| 独立完成中档题 | 1.0 |
| 独立完成基础题 | 0.7 |
| 轻提示后完成 | 0.4 |
| 低置信度视觉推断 | 0.1或仅待确认 |
| 教师确认 | 1.2 |
| 无原始依据的模型推断 | 不写入正式状态 |

推荐同时满足“最高候选置信度达到0.8”和“至少两条相对独立证据”后，将结论标记为“较可能薄弱”；证据不足时标记为“待观察”。该阈值属于产品设计参数，不是赛题硬性要求。

### 2. 结构化学生状态优于堆积完整历史

Khan Academy在2025年10月至2026年4月的大规模线上实验中发现，向Tutor提供结构化的近期表现和未掌握前置技能，可以提高学生下一题独立正确率；直接加入未经整理的完整聊天日志最初未产生可测量提升。相关实验累计覆盖超过1500万条会话线程。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

### 3. Tutor应关注学生已经完成的过程

Khan Academy的公开实验还显示，让数学Tutor缩短输出并聚焦学生已经完成的部分，可以降低延迟和过早泄露答案的比例。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

因此，本产品要求Agent观察和追问，但不在草稿纸上补全过程，也不应第一时间完成剩余计算。

### 4. 草稿适合承载元认知过程

EEF关于元认知和自我调节学习的证据综述强调，应在具体学科任务中显式支持学生进行计划、监控和评价。([EEF](https://educationendowmentfoundation.org.uk/education-evidence/guidance-reports/metacognition?utm_source=chatgpt.com))

草稿纸中的“先画什么、使用什么方法、何时修改、为何换解法”，正好对应计划、监控和评价过程；聊天栏可以围绕这些过程提出短追问。

### 5. 数字笔迹具有现实学习价值

一项针对1530名学习障碍学生和25400名普通学生的研究发现，使用数字笔记录数学过程与更高的正确解题概率相关；该结果属于关联性证据，不能直接视为因果结论，但说明保留自然书写过程具有实际研究基础。([Illinois Experts](https://experts.illinois.edu/en/publications/digital-pencil-usage-and-mathematics-performance-among-students-w?utm_source=chatgpt.com))

| 答错后的多轮追问 | 基于候选错因进行确认式追问和微型复测 | P0 |
| 目标分路径 | 根据当前分、目标分、可用时间调整知识优先级 | P0 |
| 变式题或降阶题 | 从同知识点的探针题、前置题和等价题中选择 | P1 |
| 教师复核 | 查看证据链，确认、修改或标记为待观察 | P1 |
| 章节迁移 | 统一章节内容包结构，可导入函数、数列、导数等 | P1 |
| 历史过程数据 | 保存学生状态版本、复测结果和薄弱项变化 | P1 |
| 纸面多次拍照对比 | 对两张照片配准并定位新增内容 | P2 |
| 班级共性分析 | 聚合经教师确认的诊断结论 | P2 |

# 三、需求设计

## 3.1 使用对象

### 学生

学生需要：

- 用接近真实考试的方式画图、列式和推导；
- 不必把数学思路全部转换成聊天文字；
- 在卡住时获得针对当前步骤的提示；
- 做完后知道具体错在哪里；
- 获得与目标分和时间匹配的学习安排；
- 能区分“确定薄弱”和“暂时证据不足”。

### 数学教师

教师需要：

- 快速查看学生具体在哪一步出现问题；
- 区分概念错误、方法错误、计算失误和偶然失误；
- 核查Agent是否误读草稿；
- 修改诊断结论并保留修改记录；
- 查看学生多次诊断之间的变化。

### 教研与内容运营人员

教研人员需要：

- 维护知识点、题型、错因、题目和规则；
- 检查题目标签是否完整；
- 配置诊断探针、解法路径和补弱策略；
- 将同一数据结构迁移到其他章节；
- 通过黄金案例验证规则和模型版本。

### 系统管理员与模型运营人员

管理员需要：

- 查看模型调用、工具调用和失败原因；
- 对比不同模型、提示词和诊断策略；
- 监控成本、延迟、错误率和答案泄漏；
- 管理数据权限、删除请求和模型版本。

## 3.2 核心需求冲突及解决方法

诊断、辅导和复盘对Agent行为的要求不同，应在产品中显式区分三种模式。

| 模式 | 目标 | Agent行为 |
|---|---|---|
| 诊断模式 | 获取尽可能真实的独立能力证据 | 不直接提示解法，只做中性澄清和必要追问 |
| 求助模式 | 帮助学生继续完成当前题目 | 逐级提示，记录使用了哪一级提示 |
| 复盘模式 | 理解完整解法和错误原因 | 可以展示完整分析、正确步骤和变式训练 |

这样可以避免学生在诊断阶段随时索要答案，导致掌握度被高估。

## 3.3 设计目标

1. **自然表达**：学生仍以画图、标注和列式为主要行为。
2. **最小充分测评**：尽量少出题，多利用已有过程证据。
3. **证据可追溯**：所有正式结论都能定位到原题、草稿、回答或复测。
4. **不确定性可见**：识别不确定不能直接转化为知识薄弱。
5. **多设备覆盖**：数字笔用户使用实时草稿，普通设备使用纸面拍照。
6. **章节可迁移**：运行逻辑不写死在“解三角形”章节中。
7. **学生保持主体性**：Agent通过聊天引导，不接管草稿和思考过程。

OECD关于数字评估的研究指出，过程日志能够补充最终结果，帮助理解学生如何完成任务；同时强调，过程数据必须经过适当验证，才能支持可靠推断。因此，停顿、擦改和解法变化只能作为候选证据，不能单独决定诊断结论。([OECD](https://www.oecd.org/en/publications/2023/12/oecd-digital-education-outlook-2023_c827b81a/full-report/digital-assessment_a102e604.html?utm_source=chatgpt.com))

EEF的元认知指导将计划、监控和评价视为重要学习过程，并强调这些策略应嵌入具体学科情境。草稿中的画图、方法选择、检查和改写正好可以承载这些过程，聊天负责促使学生解释与反思。([EEF](https://educationendowmentfoundation.org.uk/education-evidence/guidance-reports/metacognition))

## 3.4 建议验收指标

以下为产品目标，并非赛题硬性指标。

| 维度 | 指标 |
|---|---|
| 使用体验 | 诊断完成率、平均诊断时长、平均题量 |
| 草稿感知 | 关键区域定位成功率、意图识别率、需学生确认比例 |
| 诊断质量 | 知识点Macro-F1、错因Macro-F1、教师一致率 |
| 教学效果 | 下一题独立正确率、复测通过率、提示依赖变化 |
| 安全性 | 答案提前泄漏率、数学错误率、误归因率 |
| 工程质量 | P50/P95响应时间、工具失败率、会话恢复率 |
| 可解释性 | 有完整证据链的正式结论比例 |

Khan Academy近期将下一题独立正确率、响应延迟和认知参与质量作为核心指标，同时监控答案泄漏和数学错误。这比单独评估“模型回答是否流畅”更适合教育Agent。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

# 四、功能设计

## 4.1 学生端功能

### 画像采集

首次进入章节时，通过短对话或表单采集：

- 年级；
- 当前数学成绩区间；
- 目标成绩；
- 每周可投入时间；
- 自认为薄弱的内容；
- 设备类型；
- 是否允许保存草稿过程用于后续诊断。

画像只影响首题选择和计划优先级，不能直接形成“已掌握”结论。

### 轻量测评

支持：

- 选择题；
- 判断题；
- 填空题；
- 简短理由说明；
- 数字草稿；
- 纸面照片；
- 最终答案框。

最终答案应单独提交。草稿用于理解过程，最终答案用于稳定判题，二者不能混为同一种输入。

### 一题一草稿

每道题建立独立草稿对象：

- 当前题草稿与题目、作答、聊天回合绑定；
- 新题不会覆盖上一题草稿；
- 可以查看历史题目的只读草稿；
- 报告可直接跳转到对应草稿时间点；
- 同一题需要补充内容时继续写在原草稿中。

### 极简工具

学生常驻工具只保留：

- 基础笔；
- 画布移动。

学生通过直接划线删除错误，保留真实修改轨迹。新建草稿页、重置本题等低频操作放在二级菜单，并要求确认。

### 主动求助

学生可在任何时刻点击：

- “我卡住了”；
- “帮我看看这一步”；
- “我不确定方法是否可行”；
- “我已经完成，开始诊断”。

不同按钮会改变Agent的观察目标，避免模型无目的地分析整张草稿。

### 报告与学习计划

报告包括：

- 本次覆盖范围；
- 已掌握、基本掌握、较可能薄弱、待观察和未测量；
- 知识点、题型、方法和错因；
- 每项结论的证据；
- 优先补弱顺序；
- 一至四周计划；
- 每个阶段的复测条件。

## 4.2 教师端功能

比赛版教师端只需实现以下纵向切片：

- 查看学生完整会话；
- 查看草稿关键帧和时间轴；
- 查看Agent观察过的区域；
- 查看数学验证结果；
- 查看候选错因及置信度；
- 确认、修改或标记为待观察；
- 输入简短复核理由；
- 生成新的学生状态版本。

教师修改不覆盖AI原结论，系统同时保存：

```text
AI原结论
→ 教师修改结果
→ 修改理由
→ 修改时间
→ 使用的证据
```

## 4.3 内容运营端功能

章节内容包应具备：

- Excel或CSV导入；
- ID唯一性检查；
- 知识点前置关系检查；
- 题目答案和解析完整性检查；
- 题目与K/T/E标签关联检查；
- 诊断规则引用检查；
- 内容版本发布与回滚；
- 黄金案例回归测试；
- 章节复制与迁移。

## 4.4 管理端功能

- 模型与工具配置；
- Agent提示词版本；
- 诊断规则版本；
- 调用成本和延迟；
- 失败会话回放；
- 数据导出与删除；
- 安全事件和权限审计；
- 评测集运行与版本对比。

# 五、流程设计

## 5.1 主诊断流程

```text
创建诊断会话
      ↓
读取学生画像与历史状态
      ↓
确定本轮诊断目标和题量预算
      ↓
选择首道诊断题
      ↓
学生聊天/结构化答案/草稿/照片作答
      ↓
生成近期草稿区域和整页缩略图
      ↓
判题 + 数学验证 + 草稿初步观察
      ↓
形成候选知识、题型、方法和错因
      ↓
证据是否足够？
  ┌───────┴────────┐
  │                │
 否                是
  │                │
查看局部/回放      更新正式学生状态
或进行确认追问      │
  │                │
选择微型复测题      判断是否停止
  └───────┬────────┘
          ↓
生成报告与学习计划
          ↓
安排后续复测
```

## 5.2 实时数字草稿流程

```text
学生开始书写
→ 前端本地实时绘制
→ 追加保存Stroke事件
→ 停笔后计算近期变化包围框
→ 生成近期高清图和整页缩略图
→ Agent结合当前问题初步判断
→ 需要更多证据时调用局部、整页或回放工具
→ 中低置信度通过聊天确认
→ 形成证据对象
```

系统不在每一笔结束后立即调用模型。建议初始触发条件为：

- 连续停笔约2-4秒；
- 累计形成一定面积的新内容；
- 学生主动求助；
- 学生提交最终答案；
- 长时间停顿且前面已经形成可分析内容。

具体阈值应通过真实书写样本调节。

## 5.3 纸面拍照流程

```text
学生拍照或扫码上传
→ 端侧检查清晰度、方向和完整性
→ 服务端裁边、透视校正、去阴影
→ 保存原图和校正图
→ 主多模态模型查看整页
→ 需要精确转录时调用局部OCR或公式识别
→ 识别不确定时请学生确认
→ 与答案、聊天和规则共同形成证据
```

普通电脑端可增加“手机扫码续传”功能：电脑显示二维码，学生用手机拍照后直接上传到当前会话。

## 5.4 错因消歧流程

例如学生在SSA问题中只给出一个角，系统不立即判断“不会正弦定理”。

候选假设可能为：

- 正弦定理公式不会；
- 边角对应关系错误；
- 反三角函数计算错误；
- 忽略补角；
- 忘记检验三角形存在条件；
- 仅为偶然笔误。

随后按信息价值选择动作：

```text
草稿已有正确公式
→ 降低“公式不会”的概率
→ 追问“0°-180°中同一正弦值是否可能对应两个角”
→ 若学生知道补角，再追问三角形内角和条件
→ 用一题微型判断题复测
→ 得到“公式掌握、SSA多解判断薄弱”的结论
```

## 5.5 终止条件

建议满足以下条件时停止继续出题：

- 目标知识范围已经覆盖；
- 最高候选原因达到预设置信度；
- 至少获得两条相对独立证据；
- 下一题预期信息增益较低；
- 达到题量或时间预算；
- 学生主动结束。

单次低置信度视觉观察只能标记为“待观察”。

# 六、交互设计

## 6.1 基本交互原则

### Agent不写入草稿

学生墨迹层只接受学生输入。Agent不能：

- 自动补全公式；
- 绘制辅助线；
- 修改错误步骤；
- 删除学生内容；
- 把标准答案覆盖到草稿中。

Agent只能在聊天栏描述观察结果。必要时可在聊天消息中显示一张局部裁剪图，但不改变原始草稿。

### Agent不在学生连续书写时打断

Agent等待语义停顿、主动求助或提交事件。分析期间显示轻量状态：

```text
草稿已保存
正在查看最近新增内容
需要你确认一处标注
```

### 观察行为透明

学生可以知道：

- Agent是否正在查看草稿；
- 查看了近期内容、整页还是历史过程；
- 哪些证据将写入诊断报告；
- 是否允许保存长期历史。

## 6.2 提示等级

| 等级 | 行为 | 示例 |
|---|---|---|
| L0 澄清 | 只确认视觉或文字含义 | “这里写的是sin B=0.8吗？” |
| L1 定位 | 指出需要检查的区域 | “先检查角B是否只有一个可能值。” |
| L2 概念提示 | 提醒相关概念 | “回想正弦函数在0°到180°内的对称性。” |
| L3 脚手架 | 给出下一步框架 | “先列出两个候选角，再分别检查内角和。” |
| L4 方法提示 | 明确主要方法 | “使用补角关系和A+B<180°进行筛选。” |
| L5 完整讲解 | 展示完整过程 | 仅在复盘模式使用 |

掌握度更新必须记录提示等级。轻提示后完成和独立完成不能赋予相同证据权重。

## 6.3 视觉不确定性处理

| 视觉置信状态 | 系统行为 |
|---|---|
| 高 | 作为候选证据，但仍需数学或对话支持 |
| 中 | 在聊天中确认具体内容 |
| 低 | 不进行错因归因，请学生放大、重写或重拍 |
| 相互矛盾 | 保留冲突证据，转微型复测或教师复核 |

### 确认式追问示例

不推荐：

> “你画了高，说明你准备使用面积法。”

推荐：

> “我看到你从A点向BC补了一条线，并在旁边写了面积公式。你准备把这条线作为高来使用吗？”

## 6.4 不同设备的交互策略

| 设备 | 主输入 | 交互形态 |
|---|---|---|
| 平板 | 数字笔 | 左聊天、右草稿，连续过程观察 |
| 触屏电脑 | 触控笔 | 双栏布局，可折叠聊天栏 |
| 数位板电脑 | 数位板 | 鼠标操作聊天，数位板书写 |
| 普通电脑 | 键盘、鼠标、纸面照片 | 题目与聊天为主，手机扫码传图 |
| 手机 | 拍照、文字、选项 | 单栏纵向，照片卡片与聊天穿插 |

# 七、UI设计

## 7.1 学生作答主界面

桌面端建议比例：

- 聊天区：28%-34%；
- 草稿区：66%-72%。

```text
┌──────────────────────────────────────────────────────────┐
│ 解三角形诊断 · 第2题   诊断模式   草稿已保存   进度 2/-  │
├──────────────────┬───────────────────────────────────────┤
│                  │  题目卡：可折叠                       │
│ Agent聊天         │  ───────────────────────────────────  │
│                  │                                       │
│ 发题              │                                       │
│ 确认式追问        │          学生草稿区域                 │
│ 提示              │                                       │
│ 学生文字回复      │                                       │
│                  │                                       │
│ [输入框] [发送]   │                           [笔] [移动]  │
├──────────────────┴───────────────────────────────────────┤
│ 提交答案： [              ]   [我卡住了] [完成本题]       │
└──────────────────────────────────────────────────────────┘
```

题目卡固定在草稿顶部或采用可折叠浮层，避免学生频繁在聊天和草稿之间滚动。

## 7.2 视觉风格

- 草稿背景使用低对比度米白或浅灰；
- 笔迹为深色单色；
- 正常交互使用中性蓝；
- 待确认使用橙色；
- 红色只用于经过验证的风险和错误；
- 状态不能只依靠颜色表达，应同时显示文字和图标；
- 避免工具栏、动画和装饰抢占数学书写空间。

## 7.3 报告界面

报告采用四层结构：

### 第一层：总体结论

```text
本次使用4道题、3次追问，覆盖8个知识点。
主要优势：正弦定理基本应用、边角对应。
优先问题：SSA多解判断、三角形存在条件。
```

### 第二层：掌握度视图

按知识、题型、方法、错因分栏，状态使用：

- 已掌握；
- 基本掌握；
- 较可能薄弱；
- 待观察；
- 未测量。

### 第三层：证据卡

```text
结论：SSA情形下容易遗漏补角解
状态：较可能薄弱
证据：
1. 首次草稿只写出锐角解
2. 追问时认为反正弦只有一个取值
3. 微型复测中再次遗漏补角
反证：
1. 能正确列出正弦定理
建议：
复习正弦函数对称性，并完成两道存在性筛选题
```

### 第四层：学习计划

计划应显示：

- 周目标；
- 每次任务；
- 预计时间；
- 练习类型；
- 是否需要草稿检查；
- 复测题；
- 达标条件；
- 未达标后的调整动作。

## 7.4 教师复核界面

采用“三栏复核”：

```text
左栏：题目和聊天
中栏：草稿时间轴与关键帧
右栏：AI结论、规则、置信度、教师操作
```

教师点击证据时，中栏自动跳转到对应时间和区域。

# 八、前端设计

## 8.1 技术栈

建议使用：

- React或Next.js；
- PWA；
- Canvas作为主绘制层；
- Pointer Events统一处理鼠标、触摸和数字笔；
- IndexedDB保存本地草稿和待同步事件；
- WebSocket或SSE接收Agent流式消息；
- Web Worker处理轨迹渲染、快照和局部裁剪。

W3C Pointer Events规范为鼠标、数字笔和触摸屏提供统一输入模型，并支持高频原始更新、合并事件等能力，适合作为跨设备数字墨水输入基础。([W3C](https://www.w3.org/TR/pointerevents3/))

## 8.2 笔迹数据模型

```ts
type StrokeEvent = {
  strokeId: string;
  sheetId: string;
  seq: number;
  pointerType: "pen" | "touch" | "mouse";
  startedAt: number;
  endedAt: number;
  points: Array<{
    x: number;
    y: number;
    t: number;
    pressure?: number;
    tiltX?: number;
    tiltY?: number;
  }>;
  viewportTransform: {
    scale: number;
    offsetX: number;
    offsetY: number;
  };
};
```

坐标应使用画布世界坐标保存，避免缩放后重放位置错误。

## 8.3 前端绘制架构

建议分为三个逻辑层：

1. **背景与题目层**：纸面背景、题目引用；
2. **学生墨迹层**：唯一可编辑层；
3. **系统临时层**：保存状态、加载状态和选择框，不写入学生墨迹。

处理方式：

```text
Pointer输入
→ 前端立即绘制
→ 合并高频采样点
→ 形成Stroke事件
→ 写入IndexedDB
→ 批量同步后端
→ 服务端确认event_id
```

绘制不能等待服务器响应。即使网络短暂断开，学生仍应继续书写。

## 8.4 近期变化提取

每个Stroke完成后计算包围框：

$$
B_t=\operatorname{bbox}(stroke_t)
$$

在一个观察时间窗口内合并：

$$
B_{recent}=\bigcup_{i=t-n}^{t}B_i
$$

随后加入适当边距并生成局部高清图。这样比每次传输整张高清画布更节省带宽和模型输入成本。

## 8.5 本地恢复与同步

- 每一笔先写入IndexedDB；
- 每批事件带幂等ID；
- 后端返回最大确认序号；
- 页面刷新后从本地和服务端共同恢复；
- 未同步事件自动重传；
- 草稿截图只是派生数据，原始Stroke为主数据；
- 同一题同一时刻只允许一个可写设备，避免复杂冲突合并。

## 8.6 照片上传

前端先检查：

- 分辨率；
- 模糊度；
- 过曝和欠曝；
- 页面是否完整；
- 图片方向；
- 文件大小。

检测不合格时立即给出明确提示，例如：

> “照片右下角被裁掉，请重新拍摄并保留整张纸边缘。”

## 8.7 建议性能目标

| 项目 | 建议目标 |
|---|---:|
| 本地笔迹可见延迟 | P95低于20ms |
| 草稿自动保存 | 1秒内完成本地持久化 |
| 普通文本首响应 | 2秒内开始流式输出 |
| 草稿视觉分析 | 中位数8秒内给出结果 |
| 页面刷新恢复 | 3秒内恢复当前题 |
| 未确认Stroke丢失 | 0 |

# 十、Agent与模型设计

## 10.1 架构选择

推荐采用：

> **单Tutor Agent + 确定性状态机 + 领域工具。**

在线诊断没有必要让多个Agent相互讨论。多Agent会增加延迟、成本和结果不稳定性。Anthropic的工程经验强调从简单、可组合的模式开始，只在确实需要时增加自主性；LangGraph类运行时适合持久状态、流式、人工介入以及确定性步骤和Agent步骤混合。([Anthropic](https://www.anthropic.com/engineering/building-effective-agents?via=aitoolhunt))

比赛版可以使用：

- FastAPI自建状态机；
- 或轻量LangGraph保存会话状态和中断点。

## 10.2 Agent状态

```json
{
  "mode": "diagnosis",
  "stage": "disambiguating_error",
  "current_question_id": "Q_TRI_027",
  "target_scope": ["K_012", "K_014"],
  "question_budget_remaining": 3,
  "time_budget_seconds": 280,
  "top_hypotheses": [
    {
      "error_id": "E_009",
      "probability": 0.58
    },
    {
      "error_id": "E_013",
      "probability": 0.26
    }
  ],
  "pending_confirmation": {
    "type": "visual_intent",
    "asset_id": "asset_083"
  }
}
```

## 10.3 Agent动作空间

Agent每轮只能选择一个或少量合法动作：

```text
ASK_QUESTION
ASK_REASON
ASK_VISUAL_CONFIRMATION
INSPECT_RECENT
INSPECT_REGION
INSPECT_FULL_CANVAS
REPLAY_REGION
RECOGNIZE_REGION
VERIFY_ANSWER
VERIFY_STEP
GIVE_HINT
SELECT_RETEST
FINALIZE_DIAGNOSIS
GENERATE_PLAN
```

## 10.4 草稿主动观察工具

| 工具 | 输入 | 输出 |
|---|---|---|
| `inspect_recent` | 时间窗口、分辨率 | 最近新增区域图、范围、事件ID |
| `inspect_region` | bbox、图层 | 局部高清图 |
| `inspect_full_canvas` | 缩放等级 | 整页缩略图或高清图 |
| `compare_workspace` | 两个时间点 | 新增、删除和重画区域 |
| `replay_region` | bbox、时间段 | 关键帧或短回放 |
| `recognize_region` | bbox、识别类型 | 文字、公式或结构化结果 |
| `verify_math` | 表达式、条件 | 等价性、数值和约束结果 |
| `select_probe` | 候选错因、预算 | 下一题或追问及选择理由 |

默认上下文只附带：

- 当前题目；
- 最近一次结构化回答；
- 近期变化区域；
- 整页低清缩略图；
- 当前前两至三个候选假设；
- 精简后的学生状态。

Agent需要更多信息时自行调用工具。

## 10.5 模型分工

| 任务 | 模型或工具 |
|---|---|
| 意图判断、短摘要、格式化 | 快速文本模型 |
| 错因分析和下一动作选择 | 强推理模型 |
| 草稿和照片语义理解 | 强多模态模型 |
| 局部文字和公式精确转录 | PaddleOCR-VL或公式识别模型 |
| 数学等价性和数值验证 | SymPy、数值代入、领域规则 |
| 图像裁边、透视和差分 | OpenCV |
| 掌握度更新 | 确定性状态服务 |
| 题目和规则检索 | PostgreSQL结构化查询 |

PaddleOCR-VL官方定位是文档解析和元素识别，覆盖文字、公式、表格、图表及手写内容。因此适合作为局部精确转录工具，不应承担完整的学生认知诊断。([PaddleOCR](https://www.paddleocr.ai/v3.3.1/en/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL.html))

## 10.6 Context Compiler

模型上下文不应直接堆积全部历史聊天和全部草稿图像。

Context Compiler按当前决策目标生成上下文：

```text
当前诊断目标
+ 当前题目和标准评分点
+ 最近有效回答
+ 近期草稿区域
+ 已确认的关键证据
+ 前三项候选错因
+ 精简学生状态
+ 可调用工具
```

Khan Academy的线上实验显示，结构化的近期作答历史和未掌握前置技能能够提高下一题独立正确率；直接加入未经整理的完整会话日志最初没有产生可测量改善。这支持“状态提炼后再进入模型”的设计。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

## 10.7 假设驱动诊断

每次错误形成候选集合：

$$
\mathcal H_t=\{H_1,H_2,\ldots,H_n\}
$$

下一动作评分可以采用：

$$
Score(a)=
w_1IG(a)
+w_2Coverage(a)
+w_3TargetValue(a)
-w_4TimeCost(a)
-w_5Interruption(a)
-w_6LeakageRisk(a)
$$

其中：

- $IG$：区分候选错因的预期信息增益；
- $Coverage$：尚未覆盖知识点的价值；
- $TargetValue$：对目标分路径的重要程度；
- $TimeCost$：题量和时间成本；
- $Interruption$：对学生书写的干扰；
- $LeakageRisk$：过早泄露答案的风险。

比赛版不需要训练强化学习模型，可由教研人员给每道诊断探针配置离散区分能力。

## 10.8 掌握度更新

建议第一版采用专家先验与加权Beta更新：

$$
M_k\sim Beta(\alpha_k,\beta_k)
$$

正向证据：

$$
\alpha_k'=\alpha_k+w_e
$$

负向证据：

$$
\beta_k'=\beta_k+w_e
$$

建议权重区间：

| 证据 | 建议权重 |
|---|---:|
| 独立完成中档题 | 1.0 |
| 独立完成基础题 | 0.7 |
| 轻提示后完成 | 0.4 |
| 猜测概率较高的选择题 | 0.2-0.3 |
| 教师确认的关键证据 | 1.2 |
| 学生确认的草稿意图 | 0.5-0.8 |
| 低置信视觉推断 | 不更新或0.1 |
| 无直接证据的模型猜测 | 不更新 |

正式结论建议至少要求：

- 最高候选概率达到约0.8；
- 存在两条相对独立证据；
- 视觉识别不确定已被排除或确认。

这些是可调产品参数。

## 10.9 教学输出门控

在诊断和求助模式下，模型输出前经过检查：

- 是否直接给出最终答案；
- 是否补全学生尚未完成的主要步骤；
- 是否包含未经验证的数学结论；
- 是否将低置信视觉结果写成确定事实；
- 是否使用了不存在的知识点、题型或错因ID；
- 是否超出当前提示等级。

Khan Academy的实验表明，让数学Agent聚焦学生已经完成的部分，而不继续推完剩余解答，能够减少答案泄漏并降低延迟。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

| 等级 | 含义 | 是否允许强更新状态 |
|---|---|---|
| E0 | 原始Stroke、照片、回答 | 否 |
| E1 | 模型或OCR识别结果 | 否 |
| E2 | 学生确认的含义 | 可以 |

- `supports`；

## 11.4 原始数据与派生数据

```text
原始Stroke / 原始照片 / 原始回答
                    ↓
快照 / 裁剪图 / OCR结果 / 视觉描述
                    ↓
证据对象
                    ↓
候选假设
                    ↓
正式诊断结论
                    ↓
学生状态和学习计划
```

任何派生结论都不能覆盖原始数据。模型升级后可以重新运行派生流程。

## 11.5 数据质量校验

导入章节内容包时自动检查：

- ID是否唯一；
- K/T/E引用是否存在；
- 知识前置关系是否有环；
- 每道题是否有答案、解析和难度；
- 诊断题是否配置区分目标；
- 诊断规则是否引用有效对象；
- 同一题是否存在冲突答案；
- 题目来源和授权状态是否记录；
- 三个学生案例能否完整运行。

## 11.6 过程数据使用边界

停顿时间、重写次数和划掉行为只作为辅助信号。示例：

```text
长时间停顿
可能表示不会，也可能表示思考、分心或设备问题
→ 不能直接归因为知识薄弱
→ 只能触发中性询问或增加复测优先级
```

这符合OECD对过程数据“有价值但必须验证”的结论。([OECD](https://www.oecd.org/en/publications/the-uses-of-process-data-in-large-scale-educational-assessments_5d9009ff-en.html?utm_source=chatgpt.com))

# 十二、安全设计

## 12.1 未成年人和个人信息

学生聊天、草稿、照片、学习状态和错因画像都可能构成个人信息。系统应落实：

- 明确告知采集目的、类型和保存期限；
- 只采集完成诊断所必需的数据；
- 提供查询、更正、导出和删除入口；
- 原始草稿与长期学习状态分开授权；
- 对不满14周岁用户取得监护人同意并制定专门规则；
- 学生能够关闭长期过程记录；
- 教师只能查看其授权范围内的学生；
- 用匿名或假名ID进入模型调用链。

《生成式人工智能服务管理暂行办法》要求保护输入信息和使用记录、避免收集非必要个人信息、处理查询更正删除请求，并采取措施防范未成年人过度依赖。个人信息保护法对不满14周岁未成年人数据规定了监护人同意和专门处理规则。([工业和信息化部](https://www.miit.gov.cn/zcfg/qtl/art/2023/art_f4e8f71ae1dc43b0980b962907b7738f.html))

UNESCO的生成式AI教育指南强调人类能动性、数据保护、年龄适配以及教学和伦理适用性验证。([联合国教科文组织非洲能力建设国际研究所](https://www.iicba.unesco.org/en/africa-education-knowledge-platform/guidance-generative-ai-education-and-research))

## 12.2 权限设计

建议采用RBAC结合资源归属校验：

| 角色 | 权限 |
|---|---|
| 学生 | 自己的草稿、报告、计划和删除请求 |
| 教师 | 被授权学生的报告、证据和复核 |
| 教研 | 章节内容，不默认访问实名学生数据 |
| 模型运营 | 脱敏Trace和评测集 |
| 管理员 | 系统配置，敏感数据访问需二次审批 |

## 12.3 Agent工具安全

Tutor Agent只允许调用教育领域白名单工具：

- 不开放任意Shell；
- 不开放任意SQL；
- 不允许读取其他会话；
- 不允许直接写学生状态；
- 不允许直接删除原始证据；
- 工具参数使用JSON Schema验证；
- 每次调用检查session_id、student_id和tenant_id；
- 上传内容统一视为不可信数据；
- 题目、照片和OCR文本中的指令不得改变系统规则。

OWASP将提示注入、不安全输出处理、敏感信息泄露、过度授权和过度依赖列为LLM应用的重要风险。因此，上传内容隔离、工具白名单、输出校验和最小权限应作为基础架构。([OWASP基金会](https://owasp.org/www-project-top-10-for-large-language-model-applications/))

## 12.4 教学安全

- 数学结论优先经过标准答案或验证器；
- 复杂几何证明无法可靠验证时标记“模型判断”；
- 低置信度草稿识别必须确认；
- 诊断模式禁止提前给出完整答案；
- 学生连续求助时逐级开放提示；
- 正式报告显示置信度和替代解释；
- 教师可以纠正高风险结论；
- AI报告明确标识为AI辅助诊断。

## 12.5 安全评估维度

NIST将有效性与可靠性、安全、韧性、透明度、可解释性、隐私和公平性列为可信AI的重要组成部分。本项目测试不能只看模型准确率，还需要覆盖这些维度。([NIST](https://www.nist.gov/trustworthy-and-responsible-ai))

## 14.4 对照实验

| 实验 | 对照组 | 实验组 | 指标 |
|---|---|---|---|
| 草稿价值 | 只看最终答案 | 加入近期草稿 | 错因准确率、待观察率 |
| 主动观察价值 | 一次提交整图 | Agent可看局部和回放 | 成功率、调用次数、时延 |
| 多轮追问价值 | 首次答错直接归因 | 候选错因后追问 | 教师一致率 |
| 结构化状态价值 | 原始完整历史 | 状态摘要 | 下一题独立正确率 |
| 最小测评价值 | 固定六题 | 动态停止 | 题量、耗时、诊断准确率 |
| OCR工具价值 | 主模型直接看图 | 按需OCR | 转录准确率、总成本 |
| 证据链价值 | 只显示结论 | 显示原始证据 | 教师认可率、复核时间 |

## 14.5 安全测试

至少覆盖：

- 学生在草稿中写入“忽略系统规则”；
- 上传图片包含恶意提示词；
- 跨学生会话ID访问；
- Agent请求不存在的工具；
- 模型输出非法K/T/E编号；
- 未验证答案直接写入报告；
- 视觉低置信度却形成确定结论；
- 诊断模式提前泄露答案；
- 日志中出现学生姓名、手机号或访问令牌；
- 删除请求后派生资产未同步清理。

## 14.6 三个核心演示场景

### 场景一：相同错误答案，不同错误原因

两名学生都做错SSA题。

- 学生A草稿中没有写出正弦定理；
- 学生B公式完全正确，只遗漏补角。

系统通过草稿和追问生成不同报告与不同学习计划。

**展示价值**：诊断准确性、错因归因、少题量测评。

### 场景二：实时草稿中的辅助线和方法意图

学生画三角形，从顶点向底边补线，并写出面积公式。

Agent查看最近新增区域后询问：

> “你准备把这条线作为高，使用等面积关系吗？”

学生确认后，Agent引导其标注两侧底边，不直接补全解答。

**展示价值**：草稿主交互、主动观察、确认式追问、答案泄漏控制。

### 场景三：纸面拍照求助与教师复核

学生在纸上写到一半拍照上传。Agent发现学生已分别处理两个三角形，但没有建立公共边关系。学生圈出公共边并再次拍照，系统比较前后照片形成新证据。

教师端随后将“公共边转化薄弱”修改为“待观察”。

**展示价值**：多设备覆盖、照片过程恢复、教师复核、版本化状态。

## 14.7 五分钟演示脚本

| 时间 | 内容 |
|---|---|
| 0:00-0:30 | 痛点：只看答案无法区分为什么错 |
| 0:30-1:00 | 产品形态：左聊天、右草稿，两种输入模式 |
| 1:00-2:20 | 实时完成一题，展示近期草稿观察和确认式追问 |
| 2:20-3:05 | Agent形成多个候选错因并选择微型复测 |
| 3:05-3:50 | 输出知识、题型、错因掌握度和证据链 |
| 3:50-4:25 | 生成目标分驱动的两周学习计划 |
| 4:25-4:45 | 教师查看并修正结论 |
| 4:45-5:00 | 展示Agent工具调用、章节迁移和部署架构 |

## 二、数字草稿与笔迹组件

### 1. perfect-freehand

一个很小的MIT TypeScript库，将坐标点和压感值转换为平滑笔画轮廓，支持真实压感，也可以根据书写速度模拟压感。无依赖，适合构建只有“笔＋移动”的自定义草稿纸。([最佳JavaScript](https://bestofjs.org/projects/perfect-freehand?utm_source=chatgpt.com))

推荐程度：**最高**

推荐实现：

```text
Pointer Events
→ 采集 x、y、time、pressure
→ perfect-freehand生成显示笔画
→ 原始StrokeEvent独立保存
→ Canvas或SVG渲染
```

这样能够同时获得：

- 极简界面；
- 原始时序数据；
- 局部重绘；
- 近期变化检测；
- 回放；
- 不依赖重型白板框架。

### 2. Rnote、Saber、Xournal++

这三个项目适合研究成熟手写软件的交互细节：

- **Rnote**：矢量笔迹、压感、无限画布、固定页和连续页、不同屏幕自适应。([GitHub](https://github.com/flxzt/rnote?utm_source=chatgpt.com))
- **Saber**：Flutter跨平台手写应用，覆盖Android、iOS、Windows、Linux和macOS，适合研究移动端笔迹和文件组织。GPL-3.0。([GitHub](https://github.com/saber-notes/saber?utm_source=chatgpt.com))
- **Xournal++**：成熟的压感手写、草稿纸背景、PDF批注和多格式导出。GPL-2.0。([GitHub](https://github.com/xournalpp/xournalpp?utm_source=chatgpt.com))

这些项目更适合参考：

- 触笔防误触；
- 画布坐标变换；
- 压感笔迹；
- 长页面组织；
- 本地存储；
- 导出和恢复。

GPL代码不宜直接复制到闭源或许可证不兼容的作品中。

### 草稿实现选择

## 四、手写数学与照片识别

### PaddleOCR

当前开源项目已覆盖通用OCR、手写文字、文档结构、公式和PaddleOCR-VL，并提供坐标级输出、JavaScript浏览器推理SDK和MCP相关组件。Apache-2.0。适合纸面照片预处理后的文字识别和局部区域转录。([GitHub](https://github.com/PaddlePaddle/PaddleOCR?utm_source=chatgpt.com))

项目中建议只将其作为工具：

```text
主多模态模型判断需要精确识别
→ 裁剪特定区域
→ PaddleOCR识别文字或版面
→ 返回坐标、文本和置信度
```

### UniMERNet

面向真实场景数学公式识别，将公式图片转换为LaTeX，提供不同规模模型、训练代码和交互Demo，Apache-2.0。适合识别局部公式。([GitHub](https://github.com/opendatalab/UniMERNet?utm_source=chatgpt.com))

### Pix2Text / LaTeX-OCR

- **Pix2Text**：同时处理布局、文本和数学公式，能够输出Markdown，适合整页“文字＋公式”混排识别。([GitHub](https://github.com/breezedeus/pix2text?utm_source=chatgpt.com))
- **LaTeX-OCR / pix2tex**：专注于公式图像转LaTeX，MIT，接口和Docker部署较简单。([GitHub](https://github.com/lukas-blecher/LaTeX-OCR?utm_source=chatgpt.com))

建议优先顺序：

1. PaddleOCR负责照片文本、定位和版面；
2. UniMERNet或Pix2Text负责困难公式；
3. 多模态主模型负责解释公式在当前解题过程中的含义；
4. SymPy负责数学等价性验证。

不要让OCR结果直接生成错因结论。

### MathWriting数据集

MathWriting包含在线手写轨迹及对应LaTeX，可用于未来测试在线笔迹识别或训练专用模型。公开资料描述其包含约23万个人工书写样本和40万合成样本。([arXiv](https://arxiv.org/abs/2404.10690?utm_source=chatgpt.com))

比赛期不建议训练识别模型，但可以从中抽取样本测试：

- 轨迹渲染；
- 局部公式识别；
- 不同书写顺序；
- 在线与离线识别差异。

## 五、自适应诊断与知识追踪

### pyKT

提供统一的知识追踪实验框架，集成多种深度知识追踪模型和标准数据处理流程。适合研究后续如何根据长期交互预测学生掌握状态。MIT。([GitHub](https://github.com/pykt-team/pykt-toolkit?utm_source=chatgpt.com))

比赛阶段不建议直接引入深度知识追踪，原因是：

- 没有足够真实学生数据；
- 模型解释性弱；
- 赛题更强调错因和规则；
- 难以在短时间证明有效。

更合理的路线是：

```text

商业验证：标准BKT
积累数据后：pyKT评测不同知识追踪模型
```

## 六、苏格拉底式教学和错因数据

### SocraticMath

包含苏格拉底式数学教学方法和对话数据，采用“回顾-启发-纠正-总结”的结构，数据覆盖多轮数学辅导、知识标签和难度。适合设计Agent追问策略和提示等级。([GitHub](https://github.com/ECNU-ICALK/SocraticMath?utm_source=chatgpt.com))

### MathDial

提供以学生困惑和数学推理题为基础的教学对话数据，强调“会解题不等于会教学”。适合研究学生错误表达、教师追问和脚手架话术。([GitHub](https://github.com/eth-nlped/mathdial?utm_source=chatgpt.com))

### MathEDU

包含学生最终答案、LaTeX解题过程、正确性、不能完成的原因和专家反馈，和本项目的“过程-错因-反馈”链条较接近。([GitHub](https://github.com/NYCU-NLP-Lab/MathEDU?utm_source=chatgpt.com))

这些项目不适合直接作为高中“解三角形”题库，但可用于：

- 设计Tutor Prompt；
- 构造错误学生模拟器；
- 整理追问类型；
- 训练或评测“定位错误而不泄露答案”；
- 建立提示等级。

### 1. MathSpring

这是除 OATutor 外，**与你们高中数学方向最接近的系统**。

它具有：

- 自适应数学题目；
- 实时反馈和提示；
- 学生能力估计；
- 教师实时进度看板；
- 学习行为和情绪状态分析；
- 多年真实课堂研究基础。

官方称其面向四年级以上学生，已有超过5万名学生使用，并提供教师实时看板。([数学春天](https://mathspring.org/))

其源码仓库包含Java服务端和JavaScript前端，但技术栈较旧，依赖Java 8、Tomcat、MySQL和单独获取的题目内容包。仓库根目录没有明显许可证文件，因此更适合**研究架构和算法，不宜未经核实直接复制代码**。

重点研究：

```text
学生状态
→ 题目选择
→ 提示决策
→ 学习伙伴反馈
→ 教师实时看板
```

你们可以借鉴 MathSpring 的教师端，但将其传统答题过程替换为：

```text
最终答案
+ 草稿关键区域
+ 修改过程
+ Agent追问
+ 错因证据
```

### 2. CTAT + TutorShop

CTAT 是卡内基梅隆长期发展的 Cognitive Tutor Authoring Tools。

它支持两类Tutor：

- **Example-Tracing Tutor**：教师演示正确和错误路径，系统建立行为图；
- **Model-Tracing Tutor**：使用产生式规则描述领域解题模型。

CTAT可以追踪学生每一步操作，允许一道题存在多条合法解法，并根据当前步骤给出即时、上下文相关的提示。([Ctar Cmu](https://cdn.ctat.cs.cmu.edu/CMUCTAT/CTAT/docs/))

TutorShop负责：

- 学生和班级管理；
- 题目布置；
- 教师查看进度；
- 运行CTAT Tutor；
- 保存详细交互日志。

TutorShop在2026年7月仍有更新，但其免费使用主要面向教学和非商业研究，商业使用不能直接假定许可。([TutorShop](https://tutorshop.web.cmu.edu/))

对你们最重要的是CTAT的行为图思想：

```text
当前状态
├─ 正确操作A → 下一状态
├─ 正确操作B → 另一合法解法
├─ 常见错误C → 指定错因和提示
└─ 未识别操作 → 请求澄清
```

可以将其改造成你们的草稿诊断图：

```text
草稿中写出正弦定理
→ 排除“公式不会”

只写出锐角解
→ 提高“遗漏补角”概率

检查A+B<180°
→ 说明存在性条件已经掌握
```

### 3. Oppia

Oppia是完整的开源交互式学习平台，采用Apache 2.0许可证。其“Exploration”可以模拟一对一智能Tutor，根据学生不同答案走不同分支，并针对具体错误和误概念提供反馈。([Oppia](https://oppia.github.io/))

适合参考：

- 内容编辑器；
- 对话节点；
- 回答分类器；
- 错误反馈分支；
- 技能与主题组织；
- 学习路径；
- 学生进度管理；
- 教师或内容人员审核流程。

它的基本结构很像：

```text
教学节点
→ 学生回答
→ 回答分类规则
→ 个性化反馈
→ 下一节点
```

不足在于其适应性主要依赖内容作者预设分支，没有OATutor那样明确的BKT掌握度更新，也没有针对自由数学草稿的过程理解。

它适合参考**内容运营后台和诊断对话树**，不适合作为完整诊断算法。

### 4. GIFT

GIFT，即 Generalized Intelligent Framework for Tutoring，是一个开源、领域无关的智能辅导框架，目标是降低自适应教学系统的开发难度。它提供完整的：

- 领域模型；
- 学习者模型；
- 教学策略模型；
- 用户界面；
- 课程管理；
- 实验和分析；
- 单人及团队训练。

官方将其定义为基于实证、面向服务的自适应教学系统框架。([GIFT Tutoring](https://gifttutoring.org/))

它最值得借鉴的分层方式是：

```text
Domain Model
题目、知识、正确操作、错误操作

Learner Model
学生知识、行为、状态和历史

Pedagogical Model
下一步应该提问、提示还是训练

Tutor Interface
学生实际操作的界面
```

这几乎可以直接映射到你们：

```text
领域模型：K/T/E/Q/R
学习者模型：掌握度、错因、方法和提示依赖
教学模型：Agent下一动作策略
界面模型：聊天＋草稿纸
```

问题是GIFT工程体量很大，偏军事训练、仿真和实验平台。比赛项目不适合直接作为底座，适合用于论证架构合理性。

### 5. RoboTutor

RoboTutor是CMU开发的开源Android平板教学系统，面向7-10岁儿童的读写和基础数学。它能够自动评估表现、提供个性化反馈、更新学生水平，并选择适合当前水平的活动。([卡内基梅隆大学](https://www.cmu.edu/scs/robotutor/what-is-robotutor/index.html))

其亮点包括：

- 低网络或无网络运行；
- 手写识别；
- 语音识别；
- 学生行为日志；
- 自适应活动；
- 无教师持续参与的学习流程。

它与高中数学内容差异较大，但非常适合参考：

- 平板优先交互；
- 手写过程采集；
- 多模态学习行为；
- 弱网环境；
- 学生活动数据日志；
- 不同能力组件之间的调度。

### 6. Apprentice Tutor Builder / Apprentice Learner

Apprentice Tutor Builder允许教师拖拽创建题目界面，再通过：

- 演示正确操作；
- 标记错误操作；
- 提供反馈；
- 指定关注对象；

训练一个能够解题和辅导学生的模型。研究中的底层 Apprentice Learner 架构是开源的。([科学直通车](https://www.sciencedirect.com/science/article/pii/S1560429226001976))

它特别适合参考你们未来的“教研配置端”：

教师演示一道题的面积法
→ 系统记录操作路径

教师再演示余弦定理法

现阶段它更像研究型Tutor生成工具，部署和产品完成度低于OATutor、Oppia。

### Numbas

- 部分分；
- 针对具体答案的反馈；

- 自适应题目行为；
- 交互式图形；

对你们的价值很高：

Numbas式题目定义

尤其适合参考：

- 诊断考试编排；

如果要选择一个数学题目系统作为结构参考，**Numbas甚至比WeBWorK更适合你们**。

### STACK

STACK是基于计算机代数系统的开源数学评测工具，采用GPL许可证，可运行在Moodle、ILIAS或通过LTI接入其他系统。

它支持：

- 学生输入数学表达式；
- 代数等价判断；
- 针对具体错误的反馈；
- 多步骤作答；
- 行间推导；
- 参数化题目；
- 数学图形交互；
- 4200多个经过测试的题目或模板。

([Stack Assessment Docs](https://docs.stack-assessment.org/en/))

它可以成为你们`verify_math`工具的重要参考：

```text
学生答案
→ 语法有效性检查
→ 数学等价检查
→ 条件检查
→ 对应反馈树
```

但GPL许可证会影响直接整合方式。比较稳妥的办法是独立部署STACK，通过API或LTI连接，避免复制代码进入其他许可证项目。

## 三、新一代LLM教辅系统

这些项目在聊天和Agent方面更先进，但通常没有OATutor那种严格的技能掌握模型。

| 项目 | 主要特点 | 与OATutor的差异 |
|---|---|---|
| **DeepTutor** | Chat、Quiz、Solve、Mastery Path、知识库、工具、记忆、多模型 | 功能丰富，但掌握度和错因模型不够确定性 |
| **GenMentor** | 多Agent、目标导向学习、个性化路径和内容生成 | 偏生成式学习规划，传统ITS结构较弱 |
| **Open TutorAI** | 本地模型、RAG、教育Agent、学习者界面、教师界面 | 更接近教育版聊天平台 |
| **Lumen** | RAG、学习路径Agent、Trace、评测、MCP工具 | 工程参考价值高，真实课堂验证较少 |
| **Tutor-GPT** | 长期用户画像和个性化对话 | 偏对话伙伴，不是完整题目诊断系统 |

DeepTutor目前是这一组中工程完成度较高的项目，同一Agent运行时支持Chat、Quiz、Solve和Mastery Path，并提供知识库、记忆、工具扩展和多模型支持。([GitHub](https://github.com/HKUDS/DeepTutor))

Open TutorAI提供本地Ollama、OpenAI兼容接口、教育RAG和Agent定制，采用BSD-3-Clause许可证，但其核心仍是内容问答和个性化聊天。([GitHub](https://github.com/Open-TutorAi/open-tutor-ai-CE))

这些项目适合借鉴Agent运行时和聊天产品，但不能替代OATutor式的：

```text
技能映射
→ 证据更新
→ 掌握度计算
→ 自适应选题
→ 停止条件
```

## 四、推荐研究顺序

按照你们项目的实际需求，建议这样排：

### 第一优先级：直接研究

1. **OATutor**：BKT、技能映射、自适应选题；
2. **MathSpring**：完整数学Tutor和教师看板；
3. **CTAT**：多步骤、多解法、错误路径和上下文提示；
4. **Numbas**：数学题定义、诊断模式和自适应反馈；
5. **STACK**：表达式验证和针对性错误反馈。

### 第二优先级：产品和平台设计

6. **Oppia**：对话分支与内容编辑；
7. **TutorShop**：教师布置、学生进度和报告；
8. **Torus**：课程包、版本和LMS集成；
9. **DeepTutor**：Agent运行时、工具和记忆。

### 第三优先级：长期能力

10. **Apprentice Tutor Builder**：教师演示式生成Tutor；
11. **GIFT**：完整ITS标准架构；
12. **RoboTutor**：手写、多模态和离线端；
13. **WeBWorK**：题库和参数化题目。

## 五、最适合本项目的组合

不建议Fork一个现有系统整体修改。更合理的是组合各项目的强项：

```text
OATutor
→ 技能模型、BKT、自适应选题

CTAT
→ 步骤路径、错误路径、即时提示

Numbas / STACK
→ 数学表达式判定、参数化题目、针对性反馈

MathSpring
→ 教师看板、学生状态和真实课堂流程

Oppia
→ 对话分支和内容运营后台

DeepTutor
→ Agent运行时、工具调用和记忆

你们自主实现
→ 数字草稿、近期区域观察、错因消歧和证据链
```

其中最值得深入拆代码的四个是：

> **OATutor、CTAT、Numbas、MathSpring。**

OATutor解决“学了多少”，CTAT解决“具体哪一步”，Numbas/STACK解决“数学上是否成立”，你们的草稿Agent负责解决“学生为什么这样做、为什么在这里出错”。

# 第一讲：GIFT

## 一、GIFT究竟是什么

GIFT全称是 **Generalized Intelligent Framework for Tutoring**。它不是一个专门教授某门学科的Tutor，也不是一个类似ChatGPT的教学聊天机器人，而是一套用于构建、运行、研究和评估自适应教学系统的通用框架。

官方对其定位是：

> 通过工具、方法、标准和模块化框架，降低自适应教学系统的开发、内容创作、教学管理和实验评估成本。

截至2026年8月，GIFT官网列出的最新正式公共版本仍是 **2025-1**。源码需要注册GIFT账号后从官网获取。

GIFT的出发点不是“怎样设计一个最聪明的Tutor”，而是：

> 怎样让领域知识、学生状态估计、教学策略、交互界面和外部训练环境能够相互替换，并通过标准接口组成不同的智能教学系统。

这也是GIFT最值得我们研究的地方。

---

## 二、GIFT的核心理念

### 1. 教学系统不是一个大模型，而是多个模型的协作

GIFT将智能教学拆成三个最核心的问题：

```text
学生正在做什么？
        ↓
学生当前处于什么状态？
        ↓
现在应该采取什么教学行动？
```

分别由三个模块负责：

```text
Domain Model
判断学生在具体任务上的表现

Learner Model
根据表现和历史推断学生状态

Pedagogical Model
根据学生状态选择教学策略
```

这种划分非常重要。

例如，一个学生在SSA三角形问题中只写出一个解：

- Domain不应直接说“学生不会正弦定理”；
- Domain只负责识别行为：公式正确、求出一个角、没有检查补角；
- Learner模块综合历史，判断“正弦定理代入较稳定，但多解意识可能薄弱”；
- Pedagogy模块再决定是追问、提示、给微型复测还是结束诊断。

这与我们的“草稿观察-候选错因-确认追问-学生画像”链路高度一致。当前方案也已经要求将草稿、最终答案和追问转化为证据，再进行错因消歧，而不是由一次视觉观察直接形成长期结论。`草稿纸设计方案.txt`

### 2. 教学内容和教学引擎分离

GIFT不把每一门课程的规则写死在程序里。课程流程、领域任务、评价条件、反馈策略等主要通过配置文件描述。

因此：

```text
GIFT运行引擎
≠
某一门课程

运行引擎 + 课程配置 + 领域知识配置
=
一个具体Tutor
```

这意味着同一套运行系统可以服务射击训练、医疗操作、团队协作、对话训练或课堂知识教学。

对于我们而言，“解三角形”也不应该写死在Agent程序里，而应是第一个可插拔的章节内容包。赛题要求的知识点、题型、错因、题目和诊断规则正好可以成为这种内容包。`研究范围修订：从草稿交互扩展到完整教育 Agent 系统`

### 3. 实时表现、长期状态和教学行为必须分层

GIFT区分：

- 当前任务中的表现；
- 学习者的认知、情感和表现状态；
- 根据状态生成的教学策略；
- 训练完成后的总结和记录。

官方的Learner State包含三类信息：

```text
Performance State  表现状态
Cognitive State    认知状态
Affective State    情感状态
```

并可包含当前、短期和预测状态。

我们不需要照搬它的情感传感器体系，但可以沿用分层思想：

```text
题内证据
学生当前诊断状态
日内连续性状态
长期学生画像
```

这正好适配当前“一题一个Pi Session，长期画像异步整理”的方案。`草稿纸设计方案.txt`

# 三、GIFT的模块架构

GIFT 2025-1的主要模块可以概括为九类。

## 1. Domain Module：领域模块

Domain模块负责：

- 加载课程内容；
- 接收学生在训练环境中的行为；
- 根据领域标准进行实时评价；
- 维护任务和概念的表现状态；
- 执行Pedagogy要求的领域反馈或环境调整。

它回答的是：

> 学生刚才的行为，在当前任务和知识标准下意味着什么？

官方说明中，Domain模块负责提供领域内容、根据标准评估表现，并在Pedagogical模块认为需要反馈时提供领域相关反馈。

映射到我们的系统：

```text
题目
标准解法
允许的多种解法
评分点
错因模式
数学验证器
草稿过程证据
```

都属于Domain层。

## 2. Learner Module：学习者模块

Learner模块接收：

- Domain模块产生的表现评价；
- 历史学习记录；
- 传感器或其他状态数据；

然后形成学习者状态。

官方文档同时指出，GIFT现有Learner模型实现仍然较为简单，并预期随着研究继续变化。

这意味着我们应当借鉴它的**边界设计**，而不是假定它已有一个可以直接用于高中数学的成熟知识追踪算法。

映射到我们的系统：

```text
mastery.json
misconceptions.json
strategy_preferences.json
hint_dependency.json
confidence_and_evidence.json
```

由长期画像Agent维护，而不是由实时Tutor Agent自由改写。

## 3. Pedagogical Module：教学策略模块

Pedagogical模块回答：

> 根据当前学生状态，下一步应该怎样教？

它不负责重新判题，而是选择：

- 提示；
- 反馈；
- 复习；
- 继续练习；
- 更换难度；
- 更换内容；
- 触发环境调整。

GIFT不同版本的教学模型有所演进。早期及部分文档重点介绍eMAP：根据认知水平、参与度、挫败、困惑、无聊等学习者状态，通过规则匹配适当内容元数据。2025-1作者指南则列出默认教学模型和iCAP模型，后者结合学生状态和历史数据选择合适内容。

映射到我们的系统：

```text
继续观察草稿
提出视觉确认
追问原因
给L1定位提示
给L2概念提示
选一题微型复测
结束诊断
```

这些是Pedagogy动作，而不是Domain判断。

## 4. Tutor Module：交互模块

Tutor模块处理学习者看到的界面与交互，例如：

- 课程选择；
- 教学内容展示；
- 提示和反馈；
- 调查问卷；
- After-Action Review；
- 用户操作。

在我们的系统中，它对应：

```text
聊天区
题目卡
草稿区
答案输入
提示卡
掌握度报告
学习计划
```

Tutor只展示或收集信息，不应自行判断错因。

## 5. Sensor Module：传感器模块

GIFT最初大量用于仿真和军事训练，因此支持生理和行为传感器，例如脑电、皮电、Kinect和软件自评传感器。Sensor模块负责将原始信号格式化、处理并转成学习者状态相关信息。

对于我们，“Sensor”应扩展理解为：

```text
最终答案
聊天回答
公式输入
草稿Stroke
草稿局部图片
纸面照片
停顿和修改事件
```

不过草稿停顿、划除等行为只能成为候选证据，不能直接解释成“不会”或“焦虑”。

## 6. Gateway Module：外部系统适配

Gateway模块负责接收GIFT以外系统的消息，并将其转换为GIFT内部消息；也负责反向转换。

例如外部仿真系统发送：

```text
角色位置变化
武器操作
任务完成
```

Gateway转成统一事件，Domain再做领域评价。

在我们的系统中，Gateway对应：

```text
前端草稿事件
→ 标准StrokeEvent

学生提交答案
→ AnswerSubmitted

学生点击“我卡住了”
→ HelpRequested

Agent提示
→ PedagogicalActionApplied
```

前端事件不能直接进入学生画像，必须先经过领域解释。

## 7. LMS Module：学习记录模块

LMS负责训练历史、成绩和学习记录，并可产生xAPI语句。GIFT 2025-1会在课程、学生状态、总结评分、环境调整等事件发生时生成xAPI记录。

在我们的系统中可以对应：

- 历史题目Session；
- 掌握度变化；
- 提示使用；
- 复测结果；
- 学习计划执行情况。

早期不必完整实现xAPI，但事件结构应预留导出能力。

## 8. UMS Module：用户与会话模块

UMS负责：

- 用户基本信息；
- 用户Session；
- Domain Session；
- 消息日志。

它不负责保存正式训练成绩，成绩历史属于LMS。

这提示我们应区分：

```text
用户身份
会话记录
学生学习状态
正式诊断结果
```

不能全部塞进同一张`student`表或同一个Markdown文件。

## 9. Monitor：监控模块

Monitor用于观察模块状态、消息和运行过程。

对于我们的Agent，应对应：

- Agent读取了什么文件；
- 查看了哪个草稿区域；
- 执行了什么脚本；
- 使用了哪个模型；
- 形成了什么候选错因；
- 为什么发出当前追问；
- 哪项证据进入最终结论。

这是教师复核和评测回归的基础。

# 四、GIFT最关键的两类配置文件

## 1. Domain Course File：课程流程文件

课程文件是一个XML文件，描述一门课程的整体流程。它可以包含：

- Guidance；
- Survey；
- Lesson Material；
- Training Application；
- After-Action Review；
- 分支节点；
- 多个Lesson。

它由Domain模块读取。课程结构通过`course.xsd`校验，Java对象通过JAXB从Schema生成。GIFT推荐使用Course Authoring Tool，而不是直接编辑XML。

可以将它理解为：

```text
课程级流程图
```

例如：

```text
学生画像问卷
→ 先修能力诊断
→ 正弦定理基础
→ 根据结果分支
   ├─ 补基础
   ├─ SSA多解
   └─ 综合应用
→ 总结报告
```

## 2. Domain Knowledge File：实时评价文件

DKF描述单个Lesson内部如何评价学生。

官方列出的主要内容包括：

- Tasks；
- Concepts；
- Conditions；
- Assessment；
- Scoring；
- Learner Actions；
- State Transitions；
- Strategies；
- Resources；
- Objects和Waypoints。

Domain模块主要使用它做评价；Pedagogical模块重点读取其中的状态转换和策略部分。DKF由`dkf.xsd`约束，可通过DKF Authoring Tool创建和校验。

可以将它理解为：

```text
一道任务或一个情境内部的诊断规则图
```

课程文件决定：

> 学什么、按什么顺序学。

DKF决定：

> 学生做了什么、如何评价、何时触发什么教学行为。

# 五、GIFT的运行流程

一次典型的实时教学循环如下：

```text
1. 学生在外部环境中行动
2. Gateway或Tutor生成标准事件
3. Domain读取事件
4. Domain依据DKF中的Condition进行评价
5. Domain生成Performance State
6. Learner结合历史和其他状态形成Learner State
7. Pedagogy根据Learner State选择教学策略
8. Domain或Tutor执行提示、反馈或环境调整
9. LMS记录结果
10. Monitor和UMS保留运行轨迹
```

GIFT内部模块通过ActiveMQ传输消息。Topics用于发布订阅，Queues用于点对点发送。当前接口文档说明GIFT已从JSON消息迁移到Protocol Buffers，消息包括用户Session、Domain Session和时间戳等统一头部。

这里最重要的不是ActiveMQ本身，而是：

> 每个模块都通过明确消息契约交互，不能直接修改另一个模块的内部状态。

# 六、GIFT的代码和工程实现思路

根据公开的2025-1开发文档，GIFT属于较重型的Java系统，其主要实现方式包括：

```text
Java模块
XML课程和DKF
XSD Schema
JAXB生成Java类
ActiveMQ消息总线
Protocol Buffers消息
关系数据库
Web作者工具
外部仿真插件
xAPI / LRS
```

配置文件和模块拥有分层的property配置；Domain、Tutor、Learner、Pedagogy、Sensor、Gateway、LMS、UMS和Monitor均有各自配置。

GIFT 2025-1还提供Adaptive Learning Service API，让外部系统通过Protobuf消息和消息总线管理Session、接收Learner State、提交实时评价事件，并批准教学环境调整请求。

这种方式适合大型仿真、复杂训练环境和多个可替换模块，但对于比赛版高中数学Agent，直接照搬会产生明显的工程负担：

- Java和XML体系较重；
- ActiveMQ和多个独立模块增加部署复杂度；
- 课程配置以仿真训练为主要历史背景；
- 不是为LLM和自由草稿交互设计的；
- Learner模型本身并不是成熟的高中数学知识追踪模型。

# 七、一个具体例子：SSA多解错误如何按GIFT方式处理

假设题目要求判断三角形个数。

学生草稿中写出：

```text
sin B = 0.8
B = 53.13°
```

但没有写：

```text
B = 126.87°
```

## Sensor/Gateway层

只产生可观察事件：

```json
{
  "type": "draft_formula_observed",
  "formula": "sin(B)=0.8",
  "confidence": 0.94
}
```

```json
{
  "type": "answer_submitted",
  "answer": "one triangle"
}
```

不能在这一层直接产生：

```json
{"misconception": "forgot supplementary angle"}
```

## Domain层

结合题目和数学验证器形成评价：

```json
{
  "concept": "sine_law_substitution",
  "performance": "at_expectation",
  "evidence": ["formula_correct"]
}
```

```json
{
  "concept": "ssa_multiple_solutions",
  "performance": "below_expectation",
  "evidence": ["only_one_candidate_angle"]
}
```

## Learner层

结合历史状态形成暂时性判断：

```json
{
  "knowledge": {
    "sine_law_basic": "stable"
  },
  "hypotheses": [
    {
      "id": "ignore_supplementary_angle",
      "confidence": 0.62
    },
    {
      "id": "triangle_existence_condition_missing",
      "confidence": 0.23
    }
  ]
}
```

## Pedagogy层

根据“证据不足以正式归因”选择动作：

```json
{
  "action": "ask_diagnostic_probe",
  "prompt_target": "sine_symmetry",
  "hint_level": "L0"
}
```

## Tutor层

向学生提出：

> 在 $0^\circ$ 到 $180^\circ$ 内，正弦值为0.8的角是否只有一个？

学生回答后，再决定是否确认错因或进行微型复测。

这就是GIFT思想对我们最直接的价值：

> **观察事实、领域评价、学生状态和教学动作必须分别建模。**

# 八、如何科学迁移到我们的Pi Agent架构

我们不应把GIFT的九个模块重新做成九个微服务。

当前方案是文件系统原生Agent：一题一Session，Prompt提供任务，Files提供外部状态，Skills提供教学方法，Shell执行确定性脚本，异步画像Agent整理长期状态。`草稿纸设计方案.txt`

因此可以采用“逻辑分层、物理合并”的方式：

| GIFT概念 | 我方实现 |
|---|---|
| Domain Course File | `materials/chapter.yaml`、`assessment_flow.yaml` |
| DKF | `questions/<id>/assessment.yaml` |
| Domain Module | 题目文件＋验证脚本＋错因规则 |
| Sensor | `draft/`、答案事件、聊天事件 |
| Gateway | 前端事件标准化程序 |
| Learner Module | 异步画像Agent＋`profile/` |
| Pedagogy Module | `skills/diagnose/`、`skills/guide-student/` |
| Tutor Module | 聊天＋草稿前端 |
| UMS | 用户、Session元数据 |
| LMS | 历史Session和学习记录 |
| Monitor | Agent Trace和证据回放 |

推荐的工作区结构是：

```text
/workspace/
├─ question.md
├─ continuity.md
│
├─ domain/
│   ├─ question.yaml
│   ├─ concepts.yaml
│   ├─ solution_paths.yaml
│   ├─ buggy_paths.yaml
│   └─ assessment_rules.yaml
│
├─ learner/
│   ├─ summary.md
│   └─ state.json
│
├─ pedagogy/
│   ├─ policy.yaml
│   └─ hint_levels.yaml
│
├─ draft/
├─ history/
├─ skills/
└─ scripts/
```

关键不是目录名称，而是禁止以下混写：

```text
识别到一个公式
→ 直接改长期掌握度
→ 直接生成学习计划
```

正确链路应为：

```text
原始事件
→ 领域评价
→ 证据
→ 候选学生状态
→ 教学动作
→ 经复测后才更新长期状态
```

# 十、许可证判断

GIFT不是MIT、Apache或GPL项目，而是使用自己的EULA。

2025-1 EULA允许安装和使用副本，但对于衍生作品、分发和品牌标识有专门要求，包括在衍生作品启动页展示规定的GIFT标志；协议还对软件产品、衍生作品以及向社区提交修改作了专门定义。

因此当前最稳妥的方式是：

> **研究GIFT的公开架构、文档和数据模型，在我方技术栈中进行洁净室式独立实现。**

除非后续逐条完成EULA审查，否则不建议：

- 复制核心Java类；
- 修改后直接嵌入产品；
- 将GIFT源码作为基础仓库；
- 声称项目采用GIFT但不遵守品牌要求。

本轮没有在本地安装和运行完整的GIFT 2025-1源码，因为官方下载需要GIFT账号；实现分析基于其官方2025-1架构、作者指南、DKF、Course File、接口控制和API文档。

# 十一、对GIFT的最终判断

GIFT对我们的最大价值不是代码，而是五个设计原则：

1. **将领域评价、学生状态和教学策略分开。**
2. **将课程流程与单个任务评价规则分开。**
3. **所有模块只通过明确契约交换状态。**
4. **内容必须经过Schema校验和版本管理。**
5. **每次教学决策都必须能够回放其事件、状态和策略依据。**

因此，GIFT在整个研究序列中承担的是“总架构参照系”：

```text
GIFT规定系统应该怎样分层
CTAT研究题内步骤和错误路径
Numbas与WeBWorK负责确定性数学能力
Oppia研究内容状态机
pyKT研究长期知识状态
SocraticMath与MathDial研究教学对话
MathTutorBench与MRBench建立评测闭环
```

下一项按相同深度进入 **CTAT + TutorShop**，重点研究Behavior Graph、Example Tracing、Buggy Path、Skill标签、提示层级以及教师端学习记录。
