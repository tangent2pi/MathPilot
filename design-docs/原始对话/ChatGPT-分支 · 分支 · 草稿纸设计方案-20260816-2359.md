# 草稿证据驱动的高中数学知识诊断与学习规划 Agent 产品设计方案

## 一、产品定位

产品建议定义为：

> **以数字草稿为主要数学表达空间、以聊天为诊断控制通道、以过程证据为依据的高中数学主动诊断与学习规划 Agent。**

学生在草稿纸上完成画图、辅助线、条件标注、列式、推导和修改；Tutor Agent 在聊天栏发题、追问、提示和总结。Agent原则上不直接修改学生草稿，避免破坏真实思维过程。

赛题要求以“解三角形”为首个试点章节，完成知识点库、题型库、错因库、题库和诊断规则的数据结构化，通过少量题目和多轮对话完成知识诊断，并输出掌握度报告和一至四周学习计划。最低数据规模包括不少于25个知识点、20个题型、20个错因、80道题、20条诊断规则和3个完整学生案例。`deep-research-report.md` `deep-research-report.md`

大赛官网进一步要求作品基于大模型构建，并至少体现工具调用、规划或记忆中的一种 Agent 特征；作品须可运行、可演示，评审权重为业务价值30%、技术实现20%、创新性20%、完成度20%、展示表达10%。`大赛官网信息.txt` `大赛官网信息.txt`

因此，草稿纸不能只作为视觉效果，应同时承担三项核心职责：

1. **学生表达载体**：保留真实数学书写和思考习惯。
2. **Agent观察环境**：允许Agent主动查看近期内容、局部区域和历史变化。
3. **诊断证据来源**：为方法选择、错误位置、修改过程和提示依赖提供证据。

产品闭环为：

> 学生画像 → 轻量发题 → 草稿作答 → 主动观察 → 确认式追问 → 错因消歧 → 掌握度报告 → 学习计划 → 复测与状态更新。

## 二、三类用户对象

### 1. 学生端

学生端是主要产品界面，采用“左侧聊天、右侧草稿”的双栏布局。

学生能够：

- 填写年级、当前分数、目标分数、可投入时间和自认为薄弱的内容；
- 接收题目、追问、提示和阶段总结；
- 使用数字笔迹或纸面照片表达思路；
- 查看知识掌握报告、错因证据和学习计划；
- 在后续训练中进行复测并观察变化。

学生不需要理解知识点ID、规则编号或诊断算法。

### 2. 教师端

教师端主要用于复核，而不是代替Agent操作。

教师能够：

- 查看原题、最终答案、草稿关键帧和聊天过程；
- 查看Agent判断的知识点、题型、错因和置信度；
- 区分“学生错误”和“视觉识别不确定”；
- 将结论确认、修改为其他错因或标记为“待观察”；
- 查看学生在多次测评中的掌握度变化。

比赛版只需实现单学生、单结论的复核页面，不必建设完整班级管理系统。

### 3. 教研与内容运营端

教研人员负责维护章节内容包：

- 知识点及前置关系；
- 题型及典型解法；
- 常见错因和鉴别依据；
- 题目、答案、解析和评分点；
- 诊断规则；
- 补弱建议、练习和复测题。

赛题提供的Excel模板作为导入和交换格式；正式运行时应导入结构化数据库，避免Agent直接反复读取Excel。

## 三、核心领域对象设计

### 1. 章节内容对象

| 对象 | 主要职责 | 核心属性 |
|---|---|---|
| `ChapterPackage` | 封装一个可独立发布的章节诊断包 | 章节、版本、适用年级、发布状态 |
| `KnowledgePoint` | 描述知识点及前置依赖 | K-ID、层级、掌握标准、前置点 |
| `QuestionType` | 描述题型和标准解法结构 | T-ID、典型问法、步骤、评分点 |
| `ErrorCause` | 描述可诊断错因 | E-ID、表现、鉴别依据、补救方法 |
| `Question` | 提供正式题目或微型诊断探针 | Q-ID、题干、答案、难度、标签 |
| `DiagnosisRule` | 将证据映射到候选诊断 | R-ID、触发条件、支持错因、后续动作 |
| `SolutionPath` | 描述同一题目的不同合法解法 | 解法名称、适用条件、步骤模式 |

一个题目可以关联多个知识点、题型和候选错因，避免“一题答错就绑定一个错误”。

### 2. 学习过程对象

| 对象 | 主要职责 |
|---|---|
| `StudentProfile` | 保存当前水平、目标、时间预算和设备条件 |
| `AssessmentSession` | 管理一次诊断的题量、阶段、时间和当前假设 |
| `QuestionAttempt` | 保存学生对某道题的一次完整作答 |
| `ChatTurn` | 保存Agent和学生的正式对话 |
| `DraftSheet` | 保存某道题对应的独立草稿 |
| `StrokeEvent` | 保存笔画坐标、时间、压力、擦除和撤销事件 |
| `ObservationAsset` | 统一表示草稿快照、局部图、回放片段或纸面照片 |
| `Evidence` | 将原始作答转化为支持、反对或不确定证据 |
| `DiagnosticHypothesis` | 表示当前候选错因及概率 |
| `DiagnosticClaim` | 表示最终或阶段性诊断结论 |
| `StudentState` | 保存知识、题型、错因和策略的长期状态 |
| `LearningPlan` | 保存一至四周目标、任务、资源和复测点 |
| `TeacherReview` | 保存教师对AI结论的确认和修改版本 |

核心对象关系可概括为：

```text
ChapterPackage
 ├─ KnowledgePoint
 ├─ QuestionType
 ├─ ErrorCause
 ├─ Question
 └─ DiagnosisRule

AssessmentSession
 ├─ ChatTurn
 ├─ QuestionAttempt
 │   └─ DraftSheet
 │       ├─ StrokeEvent
 │       └─ ObservationAsset
 ├─ Evidence
 ├─ DiagnosticHypothesis
 └─ DiagnosticClaim
      ├─ StudentState
      ├─ LearningPlan
      └─ TeacherReview
```

### 3. 关键对象约束

- `DraftSheet`只能由学生书写行为修改。
- Agent只能通过观察工具读取草稿，不能直接写入学生笔迹层。
- 原始笔迹、照片和回答不可被AI结论覆盖。
- 视觉识别结果属于派生数据，必须保存置信度和原始资产引用。
- 教师修正生成新版本，保留AI原始结论。
- 掌握度更新必须引用证据，不能由大模型自由填写分数。

## 四、草稿纸产品设计

## 4.1 界面结构

平板和电脑端建议采用：

```text
┌───────────────┬──────────────────────────────┐
│ 聊天与题目区   │ 当前题目草稿纸                │
│               │                              │
│ Agent发题      │ 题干固定区或可折叠题目卡       │
│ 确认式追问     │                              │
│ 学生文字回答   │ 学生自由书写区                 │
│ 阶段提示       │                              │
│               │ 页码、撤销、清空、移动画布       │
└───────────────┴──────────────────────────────┘
```

草稿工具只保留：

- 一种基础笔触；
- 橡皮或撤销；
- 清空当前页；
- 缩放和移动画布；
- 新建附加草稿页。

不加入自动画直线、公式美化、图形吸附等功能，避免学生为了操作软件而改变真实解题方式。

## 4.2 一题一草稿

每一道题创建独立的`DraftSheet`，并与`QuestionAttempt`绑定。

这样可以：

- 清晰区分每道题的过程证据；
- 在报告中回溯具体错误；
- 对比同一知识点不同时间的作答；
- 防止多道题笔迹混杂；
- 支持完整案例回放。

## 4.3 近期内容优先观察

系统不应每次把完整笔迹坐标或整张高清草稿发送给模型。

一次有效停笔后，感知服务生成：

1. 最近一段时间新增笔迹的局部高清图；
2. 当前整张草稿的低分辨率缩略图；
3. 与上一次观察状态的差异图；
4. 新增、删除和重画区域的坐标摘要。

Agent默认只查看近期变化。当证据不足时，再主动调用工具查看局部、整页或历史过程。

这种设计同时降低视觉调用成本，并使Agent的注意力集中在学生刚刚发生的思维变化上。

## 4.4 纸面拍照模式

纸面照片和数字草稿统一抽象为`ObservationAsset`。

处理流程为：

```text
拍照上传
→ 裁边与透视校正
→ 去阴影和清晰度检测
→ 保存原图与校正图
→ 多模态模型观察
→ 必要时局部OCR或公式识别
→ 聊天确认
→ 形成诊断证据
```

学生可以选择：

- 完成后上传，进行整体诊断；
- 写到一半上传，说明“我卡在这里”；
- 修改后再次上传，系统比较两张照片中的新增内容。

数字草稿提供连续过程，纸面照片提供低门槛覆盖，两种模式进入同一诊断体系。

## 五、Tutor Agent运行机制

## 5.1 Agent状态循环

每轮交互执行以下流程：

```text
观察学生输入
→ 调用判题或草稿观察工具
→ 形成若干候选诊断假设
→ 判断证据是否充分
→ 选择下一动作
→ 更新学生状态
```

下一动作只能从有限集合中选择：

- `ASK_PROBE`：发一道新的微型诊断题；
- `ASK_REASON`：询问学生为什么这样做；
- `CONFIRM_VISUAL`：确认草稿中某个图形或公式的含义；
- `INSPECT_REGION`：放大查看草稿局部；
- `REPLAY_CHANGE`：查看书写顺序或修改过程；
- `GIVE_HINT`：按提示等级给出引导；
- `RETEST`：用等价或更简单题复核；
- `FINALIZE`：结束诊断并生成报告。

这能够明确体现大赛要求的工具调用、规划和记忆能力。

## 5.2 草稿观察工具

建议至少实现以下工具：

| 工具 | 功能 |
|---|---|
| `inspect_recent(seconds)` | 查看最近新增内容 |
| `inspect_region(bbox)` | 查看指定局部高清图 |
| `inspect_full_canvas()` | 查看整体布局和解法分支 |
| `compare_draft(t1,t2)` | 判断新增、删除和重画 |
| `replay_region(bbox,t1,t2)` | 查看局部书写顺序 |
| `recognize_region(bbox,mode)` | 识别文字、公式或图形 |
| `verify_math(expression)` | 验证公式、数值和条件 |
| `select_probe(hypotheses)` | 选择最能区分候选错因的问题 |
| `ask_student_to_confirm()` | 在视觉含义不确定时请求确认 |

所有观察结果应返回：

- 原始资产ID；
- 观察区域；
- 识别结果；
- 置信度；
- 警告信息。

## 5.3 确认式追问

多模态模型不应将视觉推断直接写入正式诊断。

例如Agent看到学生画了一条从顶点到底边的线，可以询问：

> “我看到你从A点向BC补了一条线。你是准备把它当作高，使用面积关系吗？”

学生确认后，才形成“尝试面积法”的可靠证据。

若学生否认，则更新为“视觉理解错误”，不影响掌握度。

## 5.4 假设驱动的错因消歧

一道SSA题答错后，系统可能同时保留：

- 不会正弦定理；
- 边角对应错误；
- 反三角函数计算错误；
- 忽略补角；
- 忘记检查三角形存在条件；
- 偶然计算错误。

Agent选择能够最大程度区分这些原因的追问，而不是立即推荐整章重学。

建议比赛版采用可解释的离散证据权重：

| 证据类型 | 建议权重 |
|---|---:|
| 独立完成中档题 | 1.0 |
| 独立完成基础题 | 0.7 |
| 轻提示后完成 | 0.4 |
| 低置信度视觉推断 | 0.1或仅待确认 |
| 教师确认 | 1.2 |
| 无原始依据的模型推断 | 不写入正式状态 |

推荐同时满足“最高候选置信度达到0.8”和“至少两条相对独立证据”后，将结论标记为“较可能薄弱”；证据不足时标记为“待观察”。该阈值属于产品设计参数，不是赛题硬性要求。

### 2. 结构化学生状态优于堆积完整历史

Khan Academy在2025年10月至2026年4月的大规模线上实验中发现，向Tutor提供结构化的近期表现和未掌握前置技能，可以提高学生下一题独立正确率；直接加入未经整理的完整聊天日志最初未产生可测量提升。相关实验累计覆盖超过1500万条会话线程。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

### 3. Tutor应关注学生已经完成的过程

Khan Academy的公开实验还显示，让数学Tutor缩短输出并聚焦学生已经完成的部分，可以降低延迟和过早泄露答案的比例。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

因此，本产品要求Agent观察和追问，但不在草稿纸上补全过程，也不应第一时间完成剩余计算。

### 4. 草稿适合承载元认知过程

EEF关于元认知和自我调节学习的证据综述强调，应在具体学科任务中显式支持学生进行计划、监控和评价。([EEF](https://educationendowmentfoundation.org.uk/education-evidence/guidance-reports/metacognition?utm_source=chatgpt.com))

草稿纸中的“先画什么、使用什么方法、何时修改、为何换解法”，正好对应计划、监控和评价过程；聊天栏可以围绕这些过程提出短追问。

### 5. 数字笔迹具有现实学习价值

一项针对1530名学习障碍学生和25400名普通学生的研究发现，使用数字笔记录数学过程与更高的正确解题概率相关；该结果属于关联性证据，不能直接视为因果结论，但说明保留自然书写过程具有实际研究基础。([Illinois Experts](https://experts.illinois.edu/en/publications/digital-pencil-usage-and-mathematics-performance-among-students-w?utm_source=chatgpt.com))

| 答错后的多轮追问 | 基于候选错因进行确认式追问和微型复测 | P0 |
| 目标分路径 | 根据当前分、目标分、可用时间调整知识优先级 | P0 |
| 变式题或降阶题 | 从同知识点的探针题、前置题和等价题中选择 | P1 |
| 教师复核 | 查看证据链，确认、修改或标记为待观察 | P1 |
| 章节迁移 | 统一章节内容包结构，可导入函数、数列、导数等 | P1 |
| 历史过程数据 | 保存学生状态版本、复测结果和薄弱项变化 | P1 |
| 纸面多次拍照对比 | 对两张照片配准并定位新增内容 | P2 |
| 班级共性分析 | 聚合经教师确认的诊断结论 | P2 |

# 三、需求设计

## 3.1 使用对象

### 学生

学生需要：

- 用接近真实考试的方式画图、列式和推导；
- 不必把数学思路全部转换成聊天文字；
- 在卡住时获得针对当前步骤的提示；
- 做完后知道具体错在哪里；
- 获得与目标分和时间匹配的学习安排；
- 能区分“确定薄弱”和“暂时证据不足”。

### 数学教师

教师需要：

- 快速查看学生具体在哪一步出现问题；
- 区分概念错误、方法错误、计算失误和偶然失误；
- 核查Agent是否误读草稿；
- 修改诊断结论并保留修改记录；
- 查看学生多次诊断之间的变化。

### 教研与内容运营人员

教研人员需要：

- 维护知识点、题型、错因、题目和规则；
- 检查题目标签是否完整；
- 配置诊断探针、解法路径和补弱策略；
- 将同一数据结构迁移到其他章节；
- 通过黄金案例验证规则和模型版本。

### 系统管理员与模型运营人员

管理员需要：

- 查看模型调用、工具调用和失败原因；
- 对比不同模型、提示词和诊断策略；
- 监控成本、延迟、错误率和答案泄漏；
- 管理数据权限、删除请求和模型版本。

## 3.2 核心需求冲突及解决方法

诊断、辅导和复盘对Agent行为的要求不同，应在产品中显式区分三种模式。

| 模式 | 目标 | Agent行为 |
|---|---|---|
| 诊断模式 | 获取尽可能真实的独立能力证据 | 不直接提示解法，只做中性澄清和必要追问 |
| 求助模式 | 帮助学生继续完成当前题目 | 逐级提示，记录使用了哪一级提示 |
| 复盘模式 | 理解完整解法和错误原因 | 可以展示完整分析、正确步骤和变式训练 |

这样可以避免学生在诊断阶段随时索要答案，导致掌握度被高估。

## 3.3 设计目标

1. **自然表达**：学生仍以画图、标注和列式为主要行为。
2. **最小充分测评**：尽量少出题，多利用已有过程证据。
3. **证据可追溯**：所有正式结论都能定位到原题、草稿、回答或复测。
4. **不确定性可见**：识别不确定不能直接转化为知识薄弱。
5. **多设备覆盖**：数字笔用户使用实时草稿，普通设备使用纸面拍照。
6. **章节可迁移**：运行逻辑不写死在“解三角形”章节中。
7. **学生保持主体性**：Agent通过聊天引导，不接管草稿和思考过程。

OECD关于数字评估的研究指出，过程日志能够补充最终结果，帮助理解学生如何完成任务；同时强调，过程数据必须经过适当验证，才能支持可靠推断。因此，停顿、擦改和解法变化只能作为候选证据，不能单独决定诊断结论。([OECD](https://www.oecd.org/en/publications/2023/12/oecd-digital-education-outlook-2023_c827b81a/full-report/digital-assessment_a102e604.html?utm_source=chatgpt.com))

EEF的元认知指导将计划、监控和评价视为重要学习过程，并强调这些策略应嵌入具体学科情境。草稿中的画图、方法选择、检查和改写正好可以承载这些过程，聊天负责促使学生解释与反思。([EEF](https://educationendowmentfoundation.org.uk/education-evidence/guidance-reports/metacognition))

## 3.4 建议验收指标

以下为产品目标，并非赛题硬性指标。

| 维度 | 指标 |
|---|---|
| 使用体验 | 诊断完成率、平均诊断时长、平均题量 |
| 草稿感知 | 关键区域定位成功率、意图识别率、需学生确认比例 |
| 诊断质量 | 知识点Macro-F1、错因Macro-F1、教师一致率 |
| 教学效果 | 下一题独立正确率、复测通过率、提示依赖变化 |
| 安全性 | 答案提前泄漏率、数学错误率、误归因率 |
| 工程质量 | P50/P95响应时间、工具失败率、会话恢复率 |
| 可解释性 | 有完整证据链的正式结论比例 |

Khan Academy近期将下一题独立正确率、响应延迟和认知参与质量作为核心指标，同时监控答案泄漏和数学错误。这比单独评估“模型回答是否流畅”更适合教育Agent。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

# 四、功能设计

## 4.1 学生端功能

### 画像采集

首次进入章节时，通过短对话或表单采集：

- 年级；
- 当前数学成绩区间；
- 目标成绩；
- 每周可投入时间；
- 自认为薄弱的内容；
- 设备类型；
- 是否允许保存草稿过程用于后续诊断。

画像只影响首题选择和计划优先级，不能直接形成“已掌握”结论。

### 轻量测评

支持：

- 选择题；
- 判断题；
- 填空题；
- 简短理由说明；
- 数字草稿；
- 纸面照片；
- 最终答案框。

最终答案应单独提交。草稿用于理解过程，最终答案用于稳定判题，二者不能混为同一种输入。

### 一题一草稿

每道题建立独立草稿对象：

- 当前题草稿与题目、作答、聊天回合绑定；
- 新题不会覆盖上一题草稿；
- 可以查看历史题目的只读草稿；
- 报告可直接跳转到对应草稿时间点；
- 同一题需要补充内容时继续写在原草稿中。

### 极简工具

学生常驻工具只保留：

- 基础笔；
- 画布移动。

学生通过直接划线删除错误，保留真实修改轨迹。新建草稿页、重置本题等低频操作放在二级菜单，并要求确认。

### 主动求助

学生可在任何时刻点击：

- “我卡住了”；
- “帮我看看这一步”；
- “我不确定方法是否可行”；
- “我已经完成，开始诊断”。

不同按钮会改变Agent的观察目标，避免模型无目的地分析整张草稿。

### 报告与学习计划

报告包括：

- 本次覆盖范围；
- 已掌握、基本掌握、较可能薄弱、待观察和未测量；
- 知识点、题型、方法和错因；
- 每项结论的证据；
- 优先补弱顺序；
- 一至四周计划；
- 每个阶段的复测条件。

## 4.2 教师端功能

比赛版教师端只需实现以下纵向切片：

- 查看学生完整会话；
- 查看草稿关键帧和时间轴；
- 查看Agent观察过的区域；
- 查看数学验证结果；
- 查看候选错因及置信度；
- 确认、修改或标记为待观察；
- 输入简短复核理由；
- 生成新的学生状态版本。

教师修改不覆盖AI原结论，系统同时保存：

```text
AI原结论
→ 教师修改结果
→ 修改理由
→ 修改时间
→ 使用的证据
```

## 4.3 内容运营端功能

章节内容包应具备：

- Excel或CSV导入；
- ID唯一性检查；
- 知识点前置关系检查；
- 题目答案和解析完整性检查；
- 题目与K/T/E标签关联检查；
- 诊断规则引用检查；
- 内容版本发布与回滚；
- 黄金案例回归测试；
- 章节复制与迁移。

## 4.4 管理端功能

- 模型与工具配置；
- Agent提示词版本；
- 诊断规则版本；
- 调用成本和延迟；
- 失败会话回放；
- 数据导出与删除；
- 安全事件和权限审计；
- 评测集运行与版本对比。

# 五、流程设计

## 5.1 主诊断流程

```text
创建诊断会话
      ↓
读取学生画像与历史状态
      ↓
确定本轮诊断目标和题量预算
      ↓
选择首道诊断题
      ↓
学生聊天/结构化答案/草稿/照片作答
      ↓
生成近期草稿区域和整页缩略图
      ↓
判题 + 数学验证 + 草稿初步观察
      ↓
形成候选知识、题型、方法和错因
      ↓
证据是否足够？
  ┌───────┴────────┐
  │                │
 否                是
  │                │
查看局部/回放      更新正式学生状态
或进行确认追问      │
  │                │
选择微型复测题      判断是否停止
  └───────┬────────┘
          ↓
生成报告与学习计划
          ↓
安排后续复测
```

## 5.2 实时数字草稿流程

```text
学生开始书写
→ 前端本地实时绘制
→ 追加保存Stroke事件
→ 停笔后计算近期变化包围框
→ 生成近期高清图和整页缩略图
→ Agent结合当前问题初步判断
→ 需要更多证据时调用局部、整页或回放工具
→ 中低置信度通过聊天确认
→ 形成证据对象
```

系统不在每一笔结束后立即调用模型。建议初始触发条件为：

- 连续停笔约2-4秒；
- 累计形成一定面积的新内容；
- 学生主动求助；
- 学生提交最终答案；
- 长时间停顿且前面已经形成可分析内容。

具体阈值应通过真实书写样本调节。

## 5.3 纸面拍照流程

```text
学生拍照或扫码上传
→ 端侧检查清晰度、方向和完整性
→ 服务端裁边、透视校正、去阴影
→ 保存原图和校正图
→ 主多模态模型查看整页
→ 需要精确转录时调用局部OCR或公式识别
→ 识别不确定时请学生确认
→ 与答案、聊天和规则共同形成证据
```

普通电脑端可增加“手机扫码续传”功能：电脑显示二维码，学生用手机拍照后直接上传到当前会话。

## 5.4 错因消歧流程

例如学生在SSA问题中只给出一个角，系统不立即判断“不会正弦定理”。

候选假设可能为：

- 正弦定理公式不会；
- 边角对应关系错误；
- 反三角函数计算错误；
- 忽略补角；
- 忘记检验三角形存在条件；
- 仅为偶然笔误。

随后按信息价值选择动作：

```text
草稿已有正确公式
→ 降低“公式不会”的概率
→ 追问“0°-180°中同一正弦值是否可能对应两个角”
→ 若学生知道补角，再追问三角形内角和条件
→ 用一题微型判断题复测
→ 得到“公式掌握、SSA多解判断薄弱”的结论
```

## 5.5 终止条件

建议满足以下条件时停止继续出题：

- 目标知识范围已经覆盖；
- 最高候选原因达到预设置信度；
- 至少获得两条相对独立证据；
- 下一题预期信息增益较低；
- 达到题量或时间预算；
- 学生主动结束。

单次低置信度视觉观察只能标记为“待观察”。

# 六、交互设计

## 6.1 基本交互原则

### Agent不写入草稿

学生墨迹层只接受学生输入。Agent不能：

- 自动补全公式；
- 绘制辅助线；
- 修改错误步骤；
- 删除学生内容；
- 把标准答案覆盖到草稿中。

Agent只能在聊天栏描述观察结果。必要时可在聊天消息中显示一张局部裁剪图，但不改变原始草稿。

### Agent不在学生连续书写时打断

Agent等待语义停顿、主动求助或提交事件。分析期间显示轻量状态：

```text
草稿已保存
正在查看最近新增内容
需要你确认一处标注
```

### 观察行为透明

学生可以知道：

- Agent是否正在查看草稿；
- 查看了近期内容、整页还是历史过程；
- 哪些证据将写入诊断报告；
- 是否允许保存长期历史。

## 6.2 提示等级

| 等级 | 行为 | 示例 |
|---|---|---|
| L0 澄清 | 只确认视觉或文字含义 | “这里写的是sin B=0.8吗？” |
| L1 定位 | 指出需要检查的区域 | “先检查角B是否只有一个可能值。” |
| L2 概念提示 | 提醒相关概念 | “回想正弦函数在0°到180°内的对称性。” |
| L3 脚手架 | 给出下一步框架 | “先列出两个候选角，再分别检查内角和。” |
| L4 方法提示 | 明确主要方法 | “使用补角关系和A+B<180°进行筛选。” |
| L5 完整讲解 | 展示完整过程 | 仅在复盘模式使用 |

掌握度更新必须记录提示等级。轻提示后完成和独立完成不能赋予相同证据权重。

## 6.3 视觉不确定性处理

| 视觉置信状态 | 系统行为 |
|---|---|
| 高 | 作为候选证据，但仍需数学或对话支持 |
| 中 | 在聊天中确认具体内容 |
| 低 | 不进行错因归因，请学生放大、重写或重拍 |
| 相互矛盾 | 保留冲突证据，转微型复测或教师复核 |

### 确认式追问示例

不推荐：

> “你画了高，说明你准备使用面积法。”

推荐：

> “我看到你从A点向BC补了一条线，并在旁边写了面积公式。你准备把这条线作为高来使用吗？”

## 6.4 不同设备的交互策略

| 设备 | 主输入 | 交互形态 |
|---|---|---|
| 平板 | 数字笔 | 左聊天、右草稿，连续过程观察 |
| 触屏电脑 | 触控笔 | 双栏布局，可折叠聊天栏 |
| 数位板电脑 | 数位板 | 鼠标操作聊天，数位板书写 |
| 普通电脑 | 键盘、鼠标、纸面照片 | 题目与聊天为主，手机扫码传图 |
| 手机 | 拍照、文字、选项 | 单栏纵向，照片卡片与聊天穿插 |

# 七、UI设计

## 7.1 学生作答主界面

桌面端建议比例：

- 聊天区：28%-34%；
- 草稿区：66%-72%。

```text
┌──────────────────────────────────────────────────────────┐
│ 解三角形诊断 · 第2题   诊断模式   草稿已保存   进度 2/-  │
├──────────────────┬───────────────────────────────────────┤
│                  │  题目卡：可折叠                       │
│ Agent聊天         │  ───────────────────────────────────  │
│                  │                                       │
│ 发题              │                                       │
│ 确认式追问        │          学生草稿区域                 │
│ 提示              │                                       │
│ 学生文字回复      │                                       │
│                  │                                       │
│ [输入框] [发送]   │                           [笔] [移动]  │
├──────────────────┴───────────────────────────────────────┤
│ 提交答案： [              ]   [我卡住了] [完成本题]       │
└──────────────────────────────────────────────────────────┘
```

题目卡固定在草稿顶部或采用可折叠浮层，避免学生频繁在聊天和草稿之间滚动。

## 7.2 视觉风格

- 草稿背景使用低对比度米白或浅灰；
- 笔迹为深色单色；
- 正常交互使用中性蓝；
- 待确认使用橙色；
- 红色只用于经过验证的风险和错误；
- 状态不能只依靠颜色表达，应同时显示文字和图标；
- 避免工具栏、动画和装饰抢占数学书写空间。

## 7.3 报告界面

报告采用四层结构：

### 第一层：总体结论

```text
本次使用4道题、3次追问，覆盖8个知识点。
主要优势：正弦定理基本应用、边角对应。
优先问题：SSA多解判断、三角形存在条件。
```

### 第二层：掌握度视图

按知识、题型、方法、错因分栏，状态使用：

- 已掌握；
- 基本掌握；
- 较可能薄弱；
- 待观察；
- 未测量。

### 第三层：证据卡

```text
结论：SSA情形下容易遗漏补角解
状态：较可能薄弱
证据：
1. 首次草稿只写出锐角解
2. 追问时认为反正弦只有一个取值
3. 微型复测中再次遗漏补角
反证：
1. 能正确列出正弦定理
建议：
复习正弦函数对称性，并完成两道存在性筛选题
```

### 第四层：学习计划

计划应显示：

- 周目标；
- 每次任务；
- 预计时间；
- 练习类型；
- 是否需要草稿检查；
- 复测题；
- 达标条件；
- 未达标后的调整动作。

## 7.4 教师复核界面

采用“三栏复核”：

```text
左栏：题目和聊天
中栏：草稿时间轴与关键帧
右栏：AI结论、规则、置信度、教师操作
```

教师点击证据时，中栏自动跳转到对应时间和区域。

# 八、前端设计

## 8.1 技术栈

建议使用：

- React或Next.js；
- PWA；
- Canvas作为主绘制层；
- Pointer Events统一处理鼠标、触摸和数字笔；
- IndexedDB保存本地草稿和待同步事件；
- WebSocket或SSE接收Agent流式消息；
- Web Worker处理轨迹渲染、快照和局部裁剪。

W3C Pointer Events规范为鼠标、数字笔和触摸屏提供统一输入模型，并支持高频原始更新、合并事件等能力，适合作为跨设备数字墨水输入基础。([W3C](https://www.w3.org/TR/pointerevents3/))

## 8.2 笔迹数据模型

```ts
type StrokeEvent = {
  strokeId: string;
  sheetId: string;
  seq: number;
  pointerType: "pen" | "touch" | "mouse";
  startedAt: number;
  endedAt: number;
  points: Array<{
    x: number;
    y: number;
    t: number;
    pressure?: number;
    tiltX?: number;
    tiltY?: number;
  }>;
  viewportTransform: {
    scale: number;
    offsetX: number;
    offsetY: number;
  };
};
```

坐标应使用画布世界坐标保存，避免缩放后重放位置错误。

## 8.3 前端绘制架构

建议分为三个逻辑层：

1. **背景与题目层**：纸面背景、题目引用；
2. **学生墨迹层**：唯一可编辑层；
3. **系统临时层**：保存状态、加载状态和选择框，不写入学生墨迹。

处理方式：

```text
Pointer输入
→ 前端立即绘制
→ 合并高频采样点
→ 形成Stroke事件
→ 写入IndexedDB
→ 批量同步后端
→ 服务端确认event_id
```

绘制不能等待服务器响应。即使网络短暂断开，学生仍应继续书写。

## 8.4 近期变化提取

每个Stroke完成后计算包围框：

$$
B_t=\operatorname{bbox}(stroke_t)
$$

在一个观察时间窗口内合并：

$$
B_{recent}=\bigcup_{i=t-n}^{t}B_i
$$

随后加入适当边距并生成局部高清图。这样比每次传输整张高清画布更节省带宽和模型输入成本。

## 8.5 本地恢复与同步

- 每一笔先写入IndexedDB；
- 每批事件带幂等ID；
- 后端返回最大确认序号；
- 页面刷新后从本地和服务端共同恢复；
- 未同步事件自动重传；
- 草稿截图只是派生数据，原始Stroke为主数据；
- 同一题同一时刻只允许一个可写设备，避免复杂冲突合并。

## 8.6 照片上传

前端先检查：

- 分辨率；
- 模糊度；
- 过曝和欠曝；
- 页面是否完整；
- 图片方向；
- 文件大小。

检测不合格时立即给出明确提示，例如：

> “照片右下角被裁掉，请重新拍摄并保留整张纸边缘。”

## 8.7 建议性能目标

| 项目 | 建议目标 |
|---|---:|
| 本地笔迹可见延迟 | P95低于20ms |
| 草稿自动保存 | 1秒内完成本地持久化 |
| 普通文本首响应 | 2秒内开始流式输出 |
| 草稿视觉分析 | 中位数8秒内给出结果 |
| 页面刷新恢复 | 3秒内恢复当前题 |
| 未确认Stroke丢失 | 0 |

# 十、Agent与模型设计

## 10.1 架构选择

推荐采用：

> **单Tutor Agent + 确定性状态机 + 领域工具。**

在线诊断没有必要让多个Agent相互讨论。多Agent会增加延迟、成本和结果不稳定性。Anthropic的工程经验强调从简单、可组合的模式开始，只在确实需要时增加自主性；LangGraph类运行时适合持久状态、流式、人工介入以及确定性步骤和Agent步骤混合。([Anthropic](https://www.anthropic.com/engineering/building-effective-agents?via=aitoolhunt))

比赛版可以使用：

- FastAPI自建状态机；
- 或轻量LangGraph保存会话状态和中断点。

## 10.2 Agent状态

```json
{
  "mode": "diagnosis",
  "stage": "disambiguating_error",
  "current_question_id": "Q_TRI_027",
  "target_scope": ["K_012", "K_014"],
  "question_budget_remaining": 3,
  "time_budget_seconds": 280,
  "top_hypotheses": [
    {
      "error_id": "E_009",
      "probability": 0.58
    },
    {
      "error_id": "E_013",
      "probability": 0.26
    }
  ],
  "pending_confirmation": {
    "type": "visual_intent",
    "asset_id": "asset_083"
  }
}
```

## 10.3 Agent动作空间

Agent每轮只能选择一个或少量合法动作：

```text
ASK_QUESTION
ASK_REASON
ASK_VISUAL_CONFIRMATION
INSPECT_RECENT
INSPECT_REGION
INSPECT_FULL_CANVAS
REPLAY_REGION
RECOGNIZE_REGION
VERIFY_ANSWER
VERIFY_STEP
GIVE_HINT
SELECT_RETEST
FINALIZE_DIAGNOSIS
GENERATE_PLAN
```

## 10.4 草稿主动观察工具

| 工具 | 输入 | 输出 |
|---|---|---|
| `inspect_recent` | 时间窗口、分辨率 | 最近新增区域图、范围、事件ID |
| `inspect_region` | bbox、图层 | 局部高清图 |
| `inspect_full_canvas` | 缩放等级 | 整页缩略图或高清图 |
| `compare_workspace` | 两个时间点 | 新增、删除和重画区域 |
| `replay_region` | bbox、时间段 | 关键帧或短回放 |
| `recognize_region` | bbox、识别类型 | 文字、公式或结构化结果 |
| `verify_math` | 表达式、条件 | 等价性、数值和约束结果 |
| `select_probe` | 候选错因、预算 | 下一题或追问及选择理由 |

默认上下文只附带：

- 当前题目；
- 最近一次结构化回答；
- 近期变化区域；
- 整页低清缩略图；
- 当前前两至三个候选假设；
- 精简后的学生状态。

Agent需要更多信息时自行调用工具。

## 10.5 模型分工

| 任务 | 模型或工具 |
|---|---|
| 意图判断、短摘要、格式化 | 快速文本模型 |
| 错因分析和下一动作选择 | 强推理模型 |
| 草稿和照片语义理解 | 强多模态模型 |
| 局部文字和公式精确转录 | PaddleOCR-VL或公式识别模型 |
| 数学等价性和数值验证 | SymPy、数值代入、领域规则 |
| 图像裁边、透视和差分 | OpenCV |
| 掌握度更新 | 确定性状态服务 |
| 题目和规则检索 | PostgreSQL结构化查询 |

PaddleOCR-VL官方定位是文档解析和元素识别，覆盖文字、公式、表格、图表及手写内容。因此适合作为局部精确转录工具，不应承担完整的学生认知诊断。([PaddleOCR](https://www.paddleocr.ai/v3.3.1/en/version3.x/algorithm/PaddleOCR-VL/PaddleOCR-VL.html))

## 10.6 Context Compiler

模型上下文不应直接堆积全部历史聊天和全部草稿图像。

Context Compiler按当前决策目标生成上下文：

```text
当前诊断目标
+ 当前题目和标准评分点
+ 最近有效回答
+ 近期草稿区域
+ 已确认的关键证据
+ 前三项候选错因
+ 精简学生状态
+ 可调用工具
```

Khan Academy的线上实验显示，结构化的近期作答历史和未掌握前置技能能够提高下一题独立正确率；直接加入未经整理的完整会话日志最初没有产生可测量改善。这支持“状态提炼后再进入模型”的设计。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

## 10.7 假设驱动诊断

每次错误形成候选集合：

$$
\mathcal H_t=\{H_1,H_2,\ldots,H_n\}
$$

下一动作评分可以采用：

$$
Score(a)=
w_1IG(a)
+w_2Coverage(a)
+w_3TargetValue(a)
-w_4TimeCost(a)
-w_5Interruption(a)
-w_6LeakageRisk(a)
$$

其中：

- $IG$：区分候选错因的预期信息增益；
- $Coverage$：尚未覆盖知识点的价值；
- $TargetValue$：对目标分路径的重要程度；
- $TimeCost$：题量和时间成本；
- $Interruption$：对学生书写的干扰；
- $LeakageRisk$：过早泄露答案的风险。

比赛版不需要训练强化学习模型，可由教研人员给每道诊断探针配置离散区分能力。

## 10.8 掌握度更新

建议第一版采用专家先验与加权Beta更新：

$$
M_k\sim Beta(\alpha_k,\beta_k)
$$

正向证据：

$$
\alpha_k'=\alpha_k+w_e
$$

负向证据：

$$
\beta_k'=\beta_k+w_e
$$

建议权重区间：

| 证据 | 建议权重 |
|---|---:|
| 独立完成中档题 | 1.0 |
| 独立完成基础题 | 0.7 |
| 轻提示后完成 | 0.4 |
| 猜测概率较高的选择题 | 0.2-0.3 |
| 教师确认的关键证据 | 1.2 |
| 学生确认的草稿意图 | 0.5-0.8 |
| 低置信视觉推断 | 不更新或0.1 |
| 无直接证据的模型猜测 | 不更新 |

正式结论建议至少要求：

- 最高候选概率达到约0.8；
- 存在两条相对独立证据；
- 视觉识别不确定已被排除或确认。

这些是可调产品参数。

## 10.9 教学输出门控

在诊断和求助模式下，模型输出前经过检查：

- 是否直接给出最终答案；
- 是否补全学生尚未完成的主要步骤；
- 是否包含未经验证的数学结论；
- 是否将低置信视觉结果写成确定事实；
- 是否使用了不存在的知识点、题型或错因ID；
- 是否超出当前提示等级。

Khan Academy的实验表明，让数学Agent聚焦学生已经完成的部分，而不继续推完剩余解答，能够减少答案泄漏并降低延迟。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

| 等级 | 含义 | 是否允许强更新状态 |
|---|---|---|
| E0 | 原始Stroke、照片、回答 | 否 |
| E1 | 模型或OCR识别结果 | 否 |
| E2 | 学生确认的含义 | 可以 |

- `supports`；

## 11.4 原始数据与派生数据

```text
原始Stroke / 原始照片 / 原始回答
                    ↓
快照 / 裁剪图 / OCR结果 / 视觉描述
                    ↓
证据对象
                    ↓
候选假设
                    ↓
正式诊断结论
                    ↓
学生状态和学习计划
```

任何派生结论都不能覆盖原始数据。模型升级后可以重新运行派生流程。

## 11.5 数据质量校验

导入章节内容包时自动检查：

- ID是否唯一；
- K/T/E引用是否存在；
- 知识前置关系是否有环；
- 每道题是否有答案、解析和难度；
- 诊断题是否配置区分目标；
- 诊断规则是否引用有效对象；
- 同一题是否存在冲突答案；
- 题目来源和授权状态是否记录；
- 三个学生案例能否完整运行。

## 11.6 过程数据使用边界

停顿时间、重写次数和划掉行为只作为辅助信号。示例：

```text
长时间停顿
可能表示不会，也可能表示思考、分心或设备问题
→ 不能直接归因为知识薄弱
→ 只能触发中性询问或增加复测优先级
```

这符合OECD对过程数据“有价值但必须验证”的结论。([OECD](https://www.oecd.org/en/publications/the-uses-of-process-data-in-large-scale-educational-assessments_5d9009ff-en.html?utm_source=chatgpt.com))

# 十二、安全设计

## 12.1 未成年人和个人信息

学生聊天、草稿、照片、学习状态和错因画像都可能构成个人信息。系统应落实：

- 明确告知采集目的、类型和保存期限；
- 只采集完成诊断所必需的数据；
- 提供查询、更正、导出和删除入口；
- 原始草稿与长期学习状态分开授权；
- 对不满14周岁用户取得监护人同意并制定专门规则；
- 学生能够关闭长期过程记录；
- 教师只能查看其授权范围内的学生；
- 用匿名或假名ID进入模型调用链。

《生成式人工智能服务管理暂行办法》要求保护输入信息和使用记录、避免收集非必要个人信息、处理查询更正删除请求，并采取措施防范未成年人过度依赖。个人信息保护法对不满14周岁未成年人数据规定了监护人同意和专门处理规则。([工业和信息化部](https://www.miit.gov.cn/zcfg/qtl/art/2023/art_f4e8f71ae1dc43b0980b962907b7738f.html))

UNESCO的生成式AI教育指南强调人类能动性、数据保护、年龄适配以及教学和伦理适用性验证。([联合国教科文组织非洲能力建设国际研究所](https://www.iicba.unesco.org/en/africa-education-knowledge-platform/guidance-generative-ai-education-and-research))

## 12.2 权限设计

建议采用RBAC结合资源归属校验：

| 角色 | 权限 |
|---|---|
| 学生 | 自己的草稿、报告、计划和删除请求 |
| 教师 | 被授权学生的报告、证据和复核 |
| 教研 | 章节内容，不默认访问实名学生数据 |
| 模型运营 | 脱敏Trace和评测集 |
| 管理员 | 系统配置，敏感数据访问需二次审批 |

## 12.3 Agent工具安全

Tutor Agent只允许调用教育领域白名单工具：

- 不开放任意Shell；
- 不开放任意SQL；
- 不允许读取其他会话；
- 不允许直接写学生状态；
- 不允许直接删除原始证据；
- 工具参数使用JSON Schema验证；
- 每次调用检查session_id、student_id和tenant_id；
- 上传内容统一视为不可信数据；
- 题目、照片和OCR文本中的指令不得改变系统规则。

OWASP将提示注入、不安全输出处理、敏感信息泄露、过度授权和过度依赖列为LLM应用的重要风险。因此，上传内容隔离、工具白名单、输出校验和最小权限应作为基础架构。([OWASP基金会](https://owasp.org/www-project-top-10-for-large-language-model-applications/))

## 12.4 教学安全

- 数学结论优先经过标准答案或验证器；
- 复杂几何证明无法可靠验证时标记“模型判断”；
- 低置信度草稿识别必须确认；
- 诊断模式禁止提前给出完整答案；
- 学生连续求助时逐级开放提示；
- 正式报告显示置信度和替代解释；
- 教师可以纠正高风险结论；
- AI报告明确标识为AI辅助诊断。

## 12.5 安全评估维度

NIST将有效性与可靠性、安全、韧性、透明度、可解释性、隐私和公平性列为可信AI的重要组成部分。本项目测试不能只看模型准确率，还需要覆盖这些维度。([NIST](https://www.nist.gov/trustworthy-and-responsible-ai))

## 14.4 对照实验

| 实验 | 对照组 | 实验组 | 指标 |
|---|---|---|---|
| 草稿价值 | 只看最终答案 | 加入近期草稿 | 错因准确率、待观察率 |
| 主动观察价值 | 一次提交整图 | Agent可看局部和回放 | 成功率、调用次数、时延 |
| 多轮追问价值 | 首次答错直接归因 | 候选错因后追问 | 教师一致率 |
| 结构化状态价值 | 原始完整历史 | 状态摘要 | 下一题独立正确率 |
| 最小测评价值 | 固定六题 | 动态停止 | 题量、耗时、诊断准确率 |
| OCR工具价值 | 主模型直接看图 | 按需OCR | 转录准确率、总成本 |
| 证据链价值 | 只显示结论 | 显示原始证据 | 教师认可率、复核时间 |

## 14.5 安全测试

至少覆盖：

- 学生在草稿中写入“忽略系统规则”；
- 上传图片包含恶意提示词；
- 跨学生会话ID访问；
- Agent请求不存在的工具；
- 模型输出非法K/T/E编号；
- 未验证答案直接写入报告；
- 视觉低置信度却形成确定结论；
- 诊断模式提前泄露答案；
- 日志中出现学生姓名、手机号或访问令牌；
- 删除请求后派生资产未同步清理。

## 14.6 三个核心演示场景

### 场景一：相同错误答案，不同错误原因

两名学生都做错SSA题。

- 学生A草稿中没有写出正弦定理；
- 学生B公式完全正确，只遗漏补角。

系统通过草稿和追问生成不同报告与不同学习计划。

**展示价值**：诊断准确性、错因归因、少题量测评。

### 场景二：实时草稿中的辅助线和方法意图

学生画三角形，从顶点向底边补线，并写出面积公式。

Agent查看最近新增区域后询问：

> “你准备把这条线作为高，使用等面积关系吗？”

学生确认后，Agent引导其标注两侧底边，不直接补全解答。

**展示价值**：草稿主交互、主动观察、确认式追问、答案泄漏控制。

### 场景三：纸面拍照求助与教师复核

学生在纸上写到一半拍照上传。Agent发现学生已分别处理两个三角形，但没有建立公共边关系。学生圈出公共边并再次拍照，系统比较前后照片形成新证据。

教师端随后将“公共边转化薄弱”修改为“待观察”。

**展示价值**：多设备覆盖、照片过程恢复、教师复核、版本化状态。

## 14.7 五分钟演示脚本

| 时间 | 内容 |
|---|---|
| 0:00-0:30 | 痛点：只看答案无法区分为什么错 |
| 0:30-1:00 | 产品形态：左聊天、右草稿，两种输入模式 |
| 1:00-2:20 | 实时完成一题，展示近期草稿观察和确认式追问 |
| 2:20-3:05 | Agent形成多个候选错因并选择微型复测 |
| 3:05-3:50 | 输出知识、题型、错因掌握度和证据链 |
| 3:50-4:25 | 生成目标分驱动的两周学习计划 |
| 4:25-4:45 | 教师查看并修正结论 |
| 4:45-5:00 | 展示Agent工具调用、章节迁移和部署架构 |

## 二、数字草稿与笔迹组件

### 1. perfect-freehand

一个很小的MIT TypeScript库，将坐标点和压感值转换为平滑笔画轮廓，支持真实压感，也可以根据书写速度模拟压感。无依赖，适合构建只有“笔＋移动”的自定义草稿纸。([最佳JavaScript](https://bestofjs.org/projects/perfect-freehand?utm_source=chatgpt.com))

推荐程度：**最高**

推荐实现：

```text
Pointer Events
→ 采集 x、y、time、pressure
→ perfect-freehand生成显示笔画
→ 原始StrokeEvent独立保存
→ Canvas或SVG渲染
```

这样能够同时获得：

- 极简界面；
- 原始时序数据；
- 局部重绘；
- 近期变化检测；
- 回放；
- 不依赖重型白板框架。

### 2. Rnote、Saber、Xournal++

这三个项目适合研究成熟手写软件的交互细节：

- **Rnote**：矢量笔迹、压感、无限画布、固定页和连续页、不同屏幕自适应。([GitHub](https://github.com/flxzt/rnote?utm_source=chatgpt.com))
- **Saber**：Flutter跨平台手写应用，覆盖Android、iOS、Windows、Linux和macOS，适合研究移动端笔迹和文件组织。GPL-3.0。([GitHub](https://github.com/saber-notes/saber?utm_source=chatgpt.com))
- **Xournal++**：成熟的压感手写、草稿纸背景、PDF批注和多格式导出。GPL-2.0。([GitHub](https://github.com/xournalpp/xournalpp?utm_source=chatgpt.com))

这些项目更适合参考：

- 触笔防误触；
- 画布坐标变换；
- 压感笔迹；
- 长页面组织；
- 本地存储；
- 导出和恢复。

GPL代码不宜直接复制到闭源或许可证不兼容的作品中。

### 草稿实现选择

| 方案 | 开发速度 | 过程数据控制 | 许可证 | 建议 |
|---|---:|---:|---|---|
| 自定义Canvas＋perfect-freehand | 中 | 最高 | MIT | **正式方案首选** |
| Excalidraw嵌入 | 快 | 中 | MIT | 快速原型或备用方案 |
| tldraw | 快 | 高 | 自定义生产许可 | 研究和原型，谨慎作为正式依赖 |
| Fork完整笔记软件 | 慢 | 高 | 多为GPL | 不适合比赛Web端 |

## 四、手写数学与照片识别

### PaddleOCR

当前开源项目已覆盖通用OCR、手写文字、文档结构、公式和PaddleOCR-VL，并提供坐标级输出、JavaScript浏览器推理SDK和MCP相关组件。Apache-2.0。适合纸面照片预处理后的文字识别和局部区域转录。([GitHub](https://github.com/PaddlePaddle/PaddleOCR?utm_source=chatgpt.com))

项目中建议只将其作为工具：

```text
主多模态模型判断需要精确识别
→ 裁剪特定区域
→ PaddleOCR识别文字或版面
→ 返回坐标、文本和置信度
```

### UniMERNet

面向真实场景数学公式识别，将公式图片转换为LaTeX，提供不同规模模型、训练代码和交互Demo，Apache-2.0。适合识别局部公式。([GitHub](https://github.com/opendatalab/UniMERNet?utm_source=chatgpt.com))

### Pix2Text / LaTeX-OCR

- **Pix2Text**：同时处理布局、文本和数学公式，能够输出Markdown，适合整页“文字＋公式”混排识别。([GitHub](https://github.com/breezedeus/pix2text?utm_source=chatgpt.com))
- **LaTeX-OCR / pix2tex**：专注于公式图像转LaTeX，MIT，接口和Docker部署较简单。([GitHub](https://github.com/lukas-blecher/LaTeX-OCR?utm_source=chatgpt.com))

建议优先顺序：

1. PaddleOCR负责照片文本、定位和版面；
2. UniMERNet或Pix2Text负责困难公式；
3. 多模态主模型负责解释公式在当前解题过程中的含义；
4. SymPy负责数学等价性验证。

不要让OCR结果直接生成错因结论。

### MathWriting数据集

MathWriting包含在线手写轨迹及对应LaTeX，可用于未来测试在线笔迹识别或训练专用模型。公开资料描述其包含约23万个人工书写样本和40万合成样本。([arXiv](https://arxiv.org/abs/2404.10690?utm_source=chatgpt.com))

比赛期不建议训练识别模型，但可以从中抽取样本测试：

- 轨迹渲染；
- 局部公式识别；
- 不同书写顺序；
- 在线与离线识别差异。

## 六、苏格拉底式教学和错因数据

### SocraticMath

包含苏格拉底式数学教学方法和对话数据，采用“回顾-启发-纠正-总结”的结构，数据覆盖多轮数学辅导、知识标签和难度。适合设计Agent追问策略和提示等级。([GitHub](https://github.com/ECNU-ICALK/SocraticMath?utm_source=chatgpt.com))

### MathDial

提供以学生困惑和数学推理题为基础的教学对话数据，强调“会解题不等于会教学”。适合研究学生错误表达、教师追问和脚手架话术。([GitHub](https://github.com/eth-nlped/mathdial?utm_source=chatgpt.com))

### MathEDU

包含学生最终答案、LaTeX解题过程、正确性、不能完成的原因和专家反馈，和本项目的“过程-错因-反馈”链条较接近。([GitHub](https://github.com/NYCU-NLP-Lab/MathEDU?utm_source=chatgpt.com))

这些项目不适合直接作为高中“解三角形”题库，但可用于：

- 设计Tutor Prompt；
- 构造错误学生模拟器；
- 整理追问类型；
- 训练或评测“定位错误而不泄露答案”；
- 建立提示等级。

## 一、能力对应关系

| Pi Agent能力 | LangGraph实现方式 | 是否现成 |
|---|---|---:|
| 模型自主调用工具 | 模型节点＋ToolNode＋条件边循环 | 基本现成 |
| `read/write/edit/bash`工具 | 自定义工具或Deep Agents文件系统、执行工具 | 需配置 |
| 多轮Agent循环 | `model → tools → model`循环子图 | 现成 |
| 会话保存与恢复 | Checkpointer＋`thread_id` | 现成 |
| 跨会话长期记忆 | LangGraph Store | 现成 |
| 流式输出 | `stream/astream`及事件流 | 现成 |
| 人工批准工具调用 | `interrupt()`暂停，批准后恢复 | 现成 |
| 工具调用拦截 | 工具节点前置策略节点或中间件 | 需设计 |
| 会话分支、回到历史状态 | Checkpoint历史＋新线程分叉 | 底层支持，UI需自建 |
| 上下文压缩 | 摘要节点或Deep Agents自动压缩 | 需配置 |
| `AGENTS.md`上下文 | 启动时自行读取并编译进系统上下文 | 需开发 |
| Skills | 自建技能注册器，或使用Deep Agents Skills | 需配置 |
| Extensions | Python/TS模块、工具注册和事件钩子 | 需开发 |
| Prompt Templates | 模板文件或数据库管理 | 需开发 |
| 多模型供应商 | LangChain模型适配层或自建Model Gateway | 基本现成 |
| TUI、命令和快捷键 | 单独开发前端或CLI | 不提供 |
| SDK/RPC嵌入 | 将编译后的Graph封装成API或SDK | 需封装 |

LangGraph官方将自己定位为底层Agent编排运行时，核心能力是持久执行、流式传输、人工介入和状态持久化；它并不替你规定具体Agent架构。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview?utm_source=chatgpt.com))

Pi则已经提供了工具循环、模型供应商、会话、分支、上下文压缩、Skills、Prompt Templates、Extensions、TUI、RPC和SDK等完整Harness能力。([Pi Dev](https://pi.dev/docs/latest/extensions?utm_source=chatgpt.com))

## 二、最简单的Pi式LangGraph结构

一个基础Pi式Agent可以抽象为：

```text
用户输入
   ↓
加载会话状态和项目上下文
   ↓
调用模型
   ↓
模型是否请求工具？
 ┌──────────────┐
 │ 是           │ 否
 ↓              ↓
权限和参数检查    输出结果
 ↓
调用工具
 ↓
记录工具结果
 ↓
返回模型
```

对应LangGraph：

```python
START
  ↓
load_context
  ↓
agent
  ├── 有工具调用 → approve_tool → tools → agent
  └── 无工具调用 → save_session → END
```

核心状态可以设计成：

```python
class AgentState(TypedDict):
    messages: list
    session_id: str
    user_id: str

    loaded_context: list[str]
    active_skills: list[str]

    current_plan: list[dict]
    tool_permissions: dict

    workspace: dict
    pending_approval: dict | None
    execution_metadata: dict
```

这已经可以构成一个通用Harness，而不仅是固定工作流。

## 三、LangGraph与固定工作流的区别

使用LangGraph不代表所有流程都必须提前画死。

你可以让图中存在一个开放式Agent循环：

```text
Agent节点
  ↓
自主判断需要什么工具
  ↓
调用任意允许的工具
  ↓
根据结果继续推理
  ↓
直到完成任务
```

同时在外部加入确定性约束：

```text
会话开始
→ Agent自主循环
→ 高风险工具需要审批
→ 达到循环上限则停止
→ 输出必须通过Schema验证
→ 结果写入数据库
```

所以LangGraph可以同时实现：

- Pi式开放工具调用；
- Plan-and-Execute；
- ReAct循环；
- 多Agent；
- 固定业务流程；
- 动态路由；
- 人机协同；
- 长周期任务恢复。

LangGraph的Checkpoint会在执行步骤之间保存状态，并支持故障恢复、对话记忆和时间回溯；`interrupt()`可以在任意节点暂停，等待用户或外部系统确认后继续。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/persistence?utm_source=chatgpt.com))

## 二、为什么不建议把完整 Pi 放进断网容器

如果 Pi Agent 整体运行在：

```text
--network none
```

那么它也不能调用云端模型 API。

有三种解决方式。

### 方案A：Pi在可信后端，代码工具在断网容器

这是最推荐的结构。

```text
Pi Agent
  ├─ 调用模型：由后端负责
  ├─ read工具：读取受控虚拟文件系统
  ├─ inspect_draft工具：读取草稿快照
  └─ run_python工具：交给断网容器执行
```

容器中没有：

- 模型API密钥；
- 学生数据库凭证；
- Docker Socket；
- 后端服务凭证；
- 任意互联网访问能力。

即使模型生成恶意Python代码，影响也基本限制在一次沙箱任务内。

### 方案B：Pi也在容器，只允许访问模型网关

容器没有普通互联网，只能访问内部的Model Gateway：

```text
Pi容器
   │
   └─ 只允许访问 model-gateway:8080
                    │
                    └─ 由网关调用云端模型
```

模型密钥保留在网关，不进入Pi容器。

这个方案比完全开放互联网安全，但Pi、会话和执行环境仍耦合在一起，故障恢复和多用户扩展更复杂。

### 方案C：Pi在断网容器，通过Unix Socket访问模型网关

```text
Pi容器
└─ /run/model-gateway.sock
        │
        └─ 宿主机模型代理
```

理论上隔离效果很好，但Pi现有模型适配通常面向HTTP API，需要自定义Provider或代理适配。Pi支持通过Extension增加自定义Provider，因此技术上可行。([GitHub](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md?utm_source=chatgpt.com))

比赛阶段推荐方案A。

## 四、草稿实时挂载可以实现，但不要让Agent持续轮询

宿主机更新只读挂载目录时，容器通常能看到更新后的文件。因此可以把草稿文件实时更新到挂载目录。

但是不建议让Agent执行：

```bash
while true; do
    检查草稿有没有变化
done
```

这会造成：

- CPU浪费；
- 工具调用失控；
- 会话难以暂停；
- 草稿写入一半时被读取；
- 模型不断重复分析；
- Token成本快速增长。

更合理的是事件触发。

```text
学生书写
→ 前端上传Stroke
→ 后端形成新草稿版本
→ 连续停笔3秒或学生点击“我卡住了”
→ 生成snapshot-000123
→ 后端向Pi会话发送事件
→ Pi收到“草稿版本000123可用”
→ Agent决定查看近期、局部还是整页
```

Pi SDK允许应用程序主动向持续会话发送Prompt并订阅消息和工具事件，适合这种事件驱动集成。([GitHub](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/sdk.md?utm_source=chatgpt.com))

### 草稿文件必须版本化

不要反复覆盖一个`current.png`后让Agent直接读取，因为可能出现：

```text
文件还没有写完
→ Agent已经开始读取
→ 得到半张图或不一致的metadata
```

建议：

```text
draft/snapshots/000123/recent.png
draft/snapshots/000123/full.png
draft/snapshots/000123/metadata.json
```

全部写完后，再原子更新：

```json
{
  "snapshot_id": "000123",
  "created_at": "2026-08-04T06:25:00+08:00",
  "stroke_seq_from": 431,
  "stroke_seq_to": 468
}
```

Agent只读取已经提交完成的不可变版本。

```markdown
name: diagnose-math-error
```

运行时：

```text
创建短生命周期执行容器
→ 挂载指定输入文件为只读

→ 禁止网络

→ 执行
→ 捕获stdout、stderr和生成文件
→ 杀死容器
→ 返回结构化结果
```


- 创建大量子进程；

- 无限输出；
- 无限循环；

## 八、容器安全配置

比赛Demo可以采用Rootless Docker。Docker Rootless模式使Docker守护进程和容器都运行在非Root用户命名空间中，可降低守护进程和运行时漏洞风险。([Docker Documentation](https://docs.docker.com/engine/security/rootless/?utm_source=chatgpt.com))

示意配置：

```bash
docker run --rm \
  --network none \
  --read-only \
  --user 10000:10000 \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --security-opt seccomp=/etc/agent-seccomp.json \
  --cpus 0.5 \
  --memory 512m \
  --memory-swap 512m \
  --pids-limit 64 \
  --ulimit nofile=256:256 \
  --ulimit fsize=16384:16384 \
  --tmpfs /tmp:rw,noexec,nosuid,nodev,size=64m \
  --mount type=bind,src=/session/context,dst=/context,readonly \
  --mount type=bind,src=/session/curriculum,dst=/curriculum,readonly \
  --mount type=bind,src=/session/draft,dst=/draft,readonly \
  --mount type=volume,src=session-work,dst=/workspace \
  math-agent-runner:latest
```

还需要外层超时：

```text
单次Python调用：5-10秒
单次工具调用：最长15秒
Agent单轮工具数：最多8-12次
Agent单轮总时间：30-60秒
空闲会话：自动回收
```

Docker容器默认没有资源上限，应显式设置CPU和内存限制；还应限制进程数量，避免资源耗尽。([Docker Documentation](https://docs.docker.com/engine/containers/resource_constraints/?utm_source=chatgpt.com))

Docker默认Seccomp策略会阻止部分高风险系统调用，但对执行模型生成代码的场景，仍应保留默认Seccomp或使用经过测试的更严格配置，不能使用`seccomp=unconfined`。([Docker Documentation](https://docs.docker.com/engine/security/seccomp/?utm_source=chatgpt.com))

### 生产环境建议

普通Docker容器仍然共享宿主机内核。若未来允许大量学生、多租户和任意模型生成代码，应考虑：

- gVisor；
- Kata Containers；
- Firecracker microVM。

gVisor提供OCI兼容的`runsc`运行时，在容器与宿主操作系统之间增加用户态应用内核，专门面向不可信代码和多租户隔离，可直接与Docker或Kubernetes集成。([gVisor](https://gvisor.dev/docs/?utm_source=chatgpt.com))

Firecracker使用KVM微型虚拟机，为每个工作负载增加虚拟机边界，隔离强度更高，但部署复杂度也更高。([Firecracker](https://firecracker-microvm.github.io/?utm_source=chatgpt.com))

比赛阶段用Rootless Docker即可；商业化后优先评估gVisor。

## 十一、这个方案的核心优势

从比赛角度看，它能明确展示大赛要求的Agent特征：工具调用、规划、记忆和自主执行。大赛官网明确要求作品至少体现工具调用、规划或记忆中的一种能力，并鼓励使用开源工具；这一架构在技术实现和创新性两项上都容易形成清晰叙事。`大赛官网信息.txt`

从产品角度看，它有四个优点：

1. **工具可组合**：以后增加几何验证、题目检索或图像识别，只需增加工具和Skill。
2. **上下文透明**：题库、画像、草稿和规则都能在文件层追踪。
3. **安全边界清晰**：模型自主性限制在沙箱和工具白名单内。
4. **便于复现评测**：冻结同一目录快照，就能重复运行不同模型和Prompt。

## 十二、最终建议

可以把系统正式定义为：

> **基于Pi Harness的沙箱化教学Agent：每个诊断会话拥有一个版本化的虚拟教学工作区，课程资料、学生状态和草稿过程以只读文件形式提供；Tutor Agent依据Prompt和Skills自主读取证据、调用数学工具和执行受限代码，所有状态修改通过结构化提案提交，由可信后端验证后生效。**

具体实现优先选择：

```text
可信层
├─ FastAPI / Node后端
├─ Pi SDK
├─ 模型网关
├─ 数据库与对象存储
└─ 输出及状态校验

不可信执行层
├─ Rootless Docker
├─ network none
├─ Python + SymPy
├─ 只读上下文挂载
├─ 临时可写工作区
└─ 严格资源与时间限制
```

最重要的两条原则是：

> **Skills负责教学纪律，Extension负责工具权限，沙箱负责最终安全。**

> **文件可以作为Agent接口，但数据库和对象存储仍应是系统事实来源。**


Agent只有真正需要时才读取详细规则。

### 第三层：工作区文件

教材、题库、历史Session、学生详细画像和草稿都不自动进入上下文。

Agent自己决定：

```text
是否查看详细画像
是否查看旧题
是否查看完整教案
是否搜索题库
是否渲染草稿
是否检查笔迹顺序
```

这才是真正的Context Engineering，而不是预先替Agent决定所有数据路径。Anthropic和Google都强调避免把原始历史和无关资料一次性放入上下文，应让Agent按需要加载高价值信息。([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents?open_in_browser=true&utm_source=chatgpt.com))

## 五、草稿信息就应该是文件

这一部分你的思路是正确的。

草稿可以同时保存两类表示：

```text
draft/strokes.jsonl
draft/latest.png
```

`strokes.jsonl`记录：

```json
{"seq":1,"stroke_id":"s1","x":152,"y":238,"t":0,"pressure":0.42}
{"seq":2,"stroke_id":"s1","x":155,"y":241,"t":12,"pressure":0.47}
```

`state.json`记录：

```json
{
  "version": 37,
  "last_stroke_seq": 814,
  "last_update": "2026-08-04T06:38:21+08:00",
  "recent_bbox": [120, 180, 740, 630]
}
```

图片不需要由前端不断生成，可以由Agent按需调用：

```bash
python scripts/render_draft.py --output tmp/full.png
python scripts/render_recent.py --seconds 20 --output tmp/recent.png
python scripts/render_draft.py \
  --from-seq 620 \
  --to-seq 814 \
  --output tmp/change.png
```

`observe-draft` Skill负责告诉Agent：

```text
默认先看最近新增内容；
不确定时再看整张草稿；
只有需要判断修改顺序时才检查矢量轨迹；
不要默认分析所有历史Stroke；
对视觉含义不确定时通过聊天确认。
```

这样没有`inspect_recent`、`inspect_region`、`replay_draft`等一组人为工具，只有：

```text
read
bash
固定脚本
```

### 图片如何重新交给模型

Pi支持在RPC消息中附加图片，也支持通过文件参数向模型提供图片。([GitHub](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/usage.md?utm_source=chatgpt.com))

可以采用一个非常薄的约定：

```text
Agent执行：
python scripts/render_recent.py --output tmp/recent.png

脚本输出：
IMAGE:tmp/recent.png
```

宿主程序看到`IMAGE:`标记后，把对应PNG作为图片结果加入当前Pi Session。

若你愿意做一个极薄的Pi Extension，也只需要让`read tmp/recent.png`返回图片内容。它仍然叫`read`，不增加新的模型工具。Pi的工具结果类型本身支持文本和图像内容。([GitHub](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/extensions/types.ts?utm_source=chatgpt.com))

所以工具集仍然是：

```text
read
bash
```

## 六、一题一Session是合理的

这不是把上下文割裂，而是在建立自然的认知任务边界。

每题建立：

```text
session-001：题目1
session-002：题目2
session-003：题目3
```

优势是：

- 当前Agent不会被前几题的长对话污染；
- 每题的草稿、提示和作答轨迹天然绑定；
- 可以独立复盘某一道题；
- 可以分别运行不同Prompt或模型进行评测；
- Session本身就是完整的原始证据。

Pi Session采用JSONL保存，并支持树形分支和恢复，适合保留完整题目过程。([GitHub](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/session.md?utm_source=chatgpt.com))

### 历史不是放进当前对话，而是作为文件可读

当前题目的Agent初始只看到：

```text
学生摘要
当前题目
当前草稿
```

历史通过：

```text
history/index.md
history/sessions/*.jsonl
```

按需访问。

`history/index.md`可以很简单：

```markdown
# 历史题目索引

- Q001 正弦定理基础：独立完成，未使用提示
- Q002 SSA判断：遗漏补角，经一次追问修正
- Q003 面积公式：公式正确，边角对应错误
- Q004 余弦定理：计算失误，无概念性问题
```

Agent如果认为需要确认SSA问题，才继续执行：

```bash
grep -n "SSA" history/index.md
cat history/sessions/q0002.jsonl
```

不需要向量数据库，也不需要专门的历史检索工具。

## 七、异步画像Agent对应Dream机制

你提到的“类似Dream系统”非常准确。

Anthropic的Dreams把记忆整理作为异步任务：

```text
旧记忆
＋若干历史Session
→ 后台Agent整理
→ 生成新的记忆版本
```

而且不会覆盖原始记忆，而是产生一个独立输出版本。([Claude Platform](https://platform.claude.com/docs/en/managed-agents/dreams?utm_source=chatgpt.com))

在你的系统中可以直接对应为：

```text
教学Agent完成一道题
        ↓
保存题目Session和草稿
        ↓
异步启动画像更新Agent
        ↓
读取：
├─ 当前student/summary.md
├─ 当前student/detail/
├─ 新题Session
├─ 本题草稿
└─ 教案中的知识点和错因定义
        ↓
输出：
student_versions/v0018/
├─ summary.md
├─ profile.md
├─ mastery.json
├─ misconceptions.md
└─ update_report.md
        ↓
将student/current指向v0018
```

画像更新Agent可以稍微延后几秒运行，但下一个题目Session启动时，通常已经能读到最新摘要。

### 不需要主Agent显式“提交掌握度更新”

教学Agent不需要调用：

```text
update_mastery()
update_profile()
append_evidence()
```

因为它本身产生的Session已经包含：

- 题目；
- 学生答案；
- 草稿；
- 查看过的资料；
- 使用过的脚本；
- 提示次数；
- Agent的判断；
- 学生对追问的回答。

画像更新Agent直接从原始Session中提取即可。

这和OpenAI目前的沙箱记忆设计也相似：会话结束后先提取单次会话摘要和原始记忆，再由另一个整理阶段合并到长期记忆文件。([OpenAI GitHub Pages](https://openai.github.io/openai-agents-python/sandbox/memory/?utm_source=chatgpt.com))

## 八、画像更新分成“快更新”和“Dream整理”

为了兼顾“较实时”和“长期稳定”，可以保留两种频率，但仍然只用同一个画像Agent逻辑。

### 每题结束后的快更新

```text
输入：上一版本画像＋本题Session
输出：新版本画像
```

主要更新：

- 本题涉及的知识点；
- 是否独立完成；
- 使用了何种提示；
- 暂时性错因；
- 当前学习进度。

### 多题后的Dream整理

例如每完成5题或一次诊断结束后：

```text
输入：当前画像＋最近若干Session
输出：重新整理后的紧凑画像
```

主要完成：

- 合并重复结论；
- 处理前后矛盾；
- 区分偶然失误和稳定问题；
- 删除过时的临时判断；
- 生成更短的`summary.md`；
- 保留原始Session作为证据。

这比每次都让主Agent直接修改长期画像更可靠。近期研究也提示，持续反复重写长期记忆可能产生退化，因此原始会话应该作为一等证据，记忆整合应版本化并保留回退能力。([arXiv](https://arxiv.org/abs/2605.12978?utm_source=chatgpt.com))

## 九、最终精简架构

最终系统可以压缩成这样：

```text
                           ┌────────────────┐
                           │ 学生画像 Agent │
                           │ 异步/Dream式   │
                           └───────▲────────┘
                                   │读取Session
                                   │生成新画像
┌──────────┐      ┌────────────────────────────────┐
│ 学生前端 │─────▶│ 一题一个 Pi Agent Session       │
│聊天+草稿 │◀─────│                                │
└──────────┘      │ Prompt                         │
                  │ ├─ 当前题目                    │
                  │ ├─ 当前教学模式                │
                  │ └─ 学生摘要                    │
                  │                                │
                  │ Files                          │
                  │ ├─ 教案和题库                  │
                  │ ├─ 学生详细信息                │
                  │ ├─ 历史Session                 │
                  │ ├─ 草稿Stroke                  │
                  │ └─ 固定脚本                    │
                  │                                │
                  │ Skills                         │
                  │ ├─ 草稿观察                    │
                  │ ├─ 错因诊断                    │
                  │ ├─ 分级引导                    │
                  │ └─ 练习选择                    │
                  │                                │
                  │ Tools                          │
                  │ ├─ read                        │
                  │ └─ bash                        │
                  └────────────────────────────────┘
```

这套架构的核心不是“把复杂系统隐藏在工具后面”，而是：

> **让模型生活在一个为教学任务组织好的文件系统中。**

它能自主：

- 阅读教案；
- 查询题库；
- 查看学生历史；
- 渲染草稿；
- 检查笔迹变化；
- 运行Python；
- 验证数学表达式；
- 判断需要继续追问还是提示。

而系统真正需要做的事情只有：

- 准备上下文；
- 同步文件；
- 保存Session；
- 异步整理画像；
- 限制环境资源。

因此，方案应从之前的“领域工具Agent”修正为：

> **文件系统原生的教学Agent：一题一Session，Prompt提供当前任务，Files提供外部记忆，Skills提供按需教学方法，Shell提供通用计算能力，Dream Agent负责跨Session异步画像整合。**

这比LangGraph状态机或大量自定义工具更符合你当前想要的Pi Agent路线。

# 一、记忆结构：Session、连续性包和长期画像

## 1. 当前题目 Session

每道题创建一个独立 Pi Session：

```text
question-session-20260804-007
├─ 当前题目
├─ 本题教学模式
├─ 学生日内连续性摘要
├─ 当前长期画像摘要
├─ 聊天记录
├─ 草稿轨迹
├─ Agent查看过的草稿片段
└─ 工具执行结果
```

Pi原生将Session保存为JSONL，并以`id/parentId`形成树形结构，因此可以保存完整过程、分支和恢复信息。Pi SDK也支持程序化创建独立`AgentSession`，适合一题一个Session。([GitHub](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/session.md?utm_source=chatgpt.com))

## 2. 日内连续性包

日内连续性包不是画像，也不需要复杂推断。它只描述“当前连续学习上下文”。

建议命名为：

```text
continuity.md
```

内容控制在约150-300字：

```markdown
# 当前学习连续性

日期：2026-08-04

今日已完成：7题
当前连续完成：4题
今日已学习：31分钟
最近一次休息：18分钟前

上一题：
- 题型：SSA三角形个数判断
- 结果：经一次追问后完成
- 主要过程：能够正确使用正弦定理，但首次遗漏补角
- 使用提示：L1定位提示
- 未闭合问题：下一题继续观察是否主动检查补角和内角和条件

当前建议：
- 不重复讲解正弦定理基础公式
- 下一题优先验证多解判断是否已经迁移
```

下一题启动时直接把它加入提示词：

```text
长期画像摘要
＋
今日日内连续性包
＋
当前题目
```

这样下一题Agent知道：

- 今天做了多少题；
- 是否已经连续学习很久；
- 上一题发生了什么；
- 当前还需要观察什么；
- 哪些内容不应重复追问。

但它不会把“上一题犯错”直接当作长期薄弱结论。

## 3. 连续性包如何生成

不需要再增加一个复杂Agent。可以在每题Session关闭时执行一次固定压缩：

```text
Session结束
→ 从Session中提取题目、结果、提示等级和未闭合问题
→ 更新今日计数
→ 重写continuity.md
```

其中：

- 题数、时间、连续题数由程序确定性统计；
- 上一题摘要可以使用一次低成本模型压缩；
- 未闭合问题来自教学Agent最后的诊断判断；
- 不修改长期画像。

日内连续性包可以不断覆盖，因为它是临时状态。原始Session不覆盖。

## 4. 每日画像Agent

每天结束或长期空闲后，再运行独立画像Agent：

```text
旧画像版本
＋
今日所有题目Session
＋
今日continuity.md
＋
知识点、题型和错因定义
          ↓
画像更新Agent
          ↓
新的画像版本
```

输出：

```text
profile/
├─ current -> versions/2026-08-04/
└─ versions/
    ├─ 2026-08-03/
    └─ 2026-08-04/
        ├─ summary.md
        ├─ mastery.md
        ├─ misconceptions.md
        ├─ strategies.md
        └─ update_report.md
```

Claude Dreams的公开设计就是异步读取旧记忆和历史Sessions，生成一个与输入分离的新记忆存储；输入不会被修改，可以审查或丢弃输出。([Claude Platform](https://platform.claude.com/docs/en/managed-agents/dreams?utm_source=chatgpt.com))

OpenAI公开的Sandbox Memory也将对话Session和长期记忆分开：运行记录先被提取为摘要，再由独立整理阶段合并到`MEMORY.md`和`memory_summary.md`，并在下一次运行中渐进式读取。([OpenAI GitHub Pages](https://openai.github.io/openai-agents-python/sandbox/memory/?utm_source=chatgpt.com))

所以结构应当是：

```text
教学Agent：只产生原始Session和题内判断
连续性压缩：维持日内短期衔接
画像Agent：每日整合长期模式
```

# 二、企业多用户和高并发

## 1. 一题一Session不等于一题永久占用一个容器

需要区分：

- **Session**：逻辑状态和文件；
- **Sandbox**：临时计算资源；
- **Workspace**：可持久化文件快照。

企业环境中，不应为每个学生永久保留一个运行中的容器。

推荐模式是：

> **工作区持久化，计算环境按需租用。**

```text
学生发送消息
→ 恢复该题Session和Workspace
→ 分配一个空闲Sandbox
→ Pi执行当前轮次
→ 保存Session和Workspace差异
→ 空闲一段时间后释放Sandbox
```

下一次学生继续交流时，再恢复。

OpenAI公开的Sandbox Agents设计同样强调持久Workspace、快照、启动、停止和恢复，使文件型Agent能够规模化运行。([OpenAI GitHub Pages](https://openai.github.io/openai-agents-python/sandbox/guide/?utm_source=chatgpt.com))

## 2. 推荐的企业级结构

```text
                    ┌──────────────────────┐
学生端 ────────────→│ API / WebSocket网关 │
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │ Session调度与消息队列 │
                    └───────┬───────┬──────┘
                            │       │
                 交互高优先级│       │每日低优先级
                            │       │
                ┌───────────▼──┐  ┌─▼─────────────┐
                │ 教学Sandbox池 │  │ 画像Agent池   │
                └───────────┬──┘  └─┬─────────────┘
                            │       │
                    ┌───────▼───────▼────────┐
                    │ Session / Workspace存储 │
                    │ 对象存储＋元数据数据库   │
                    └────────────────────────┘
```

核心组件不多：

1. 网关；
2. Session调度器；
3. Sandbox池；
4. Workspace存储；
5. 模型代理；
6. 每日画像队列。

## 5. Sandbox池而不是即时冷启动

低并发Demo可以每次直接启动容器。

企业场景采用预热池：

```text
空闲Sandbox
├─ Pi运行环境已加载
├─ Python/SymPy已安装
├─ Skills已缓存
└─ 公共内容包已挂载
```

请求到达后：

```text
申请Sandbox租约
→ 挂载当前Session工作区
→ 创建Pi AgentSession
→ 执行
→ 保存
→ 清理用户可写层
→ 归还Sandbox
```

需要确保：

- 一个Sandbox同时只服务一个Session；
- 一个Session同时只允许一个写入租约；
- 归还前彻底清理可写层；
- 公共只读层可以保留缓存。

## 6. 消息串行化

同一道题的Session不能同时处理两条学生消息，否则可能出现：

```text
消息A正在查看草稿
消息B又提交了新草稿
两轮同时修改Session
→ 顺序和上下文不一致
```

因此每个Session维护一个顺序队列：

```text
session_id → message queue
```

规则：

- 不同学生、不同题目可以并行；
- 同一个Session内部串行；
- 新消息可以作为steering message排队；
- 每个事件携带单调递增`event_id`；
-重复事件幂等处理。

Pi本身支持在Agent工作期间排队steering或follow-up消息，这一机制适合接入Web端消息队列。([GitHub](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md?utm_source=chatgpt.com))

## 7. 教学任务和画像任务分池

教学任务要求低延迟，画像任务不要求立即完成。

建议两条队列：

```text
interactive-teaching    高优先级
daily-profile-update    低优先级
```

当系统繁忙时：

- 先保证学生当前聊天；
- 画像更新可以延后；
- 夜间增加画像Worker；
- 不允许Dream任务占满交互Sandbox。

Kubernetes可以按CPU、内存或自定义指标横向扩展工作负载；事件驱动场景也可以按消息队列长度扩展Worker数量。([Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/?utm_source=chatgpt.com))

实际扩容指标优先使用：

```text
等待中的教学消息数
活跃Session数
Sandbox平均占用时间
模型调用并发数
P95首响应延迟
```

不要只看CPU，因为Agent大量时间可能在等待模型API。

## 8. 企业隔离单位

建议三级隔离：

```text
企业/学校 tenant
  └─ 学生 student
       └─ 题目 session
```

文件路径必须包含内部不可猜测ID：

```text
/tenants/<tenant-id>/students/<student-id>/sessions/<session-id>/
```

Sandbox每次只挂载一个题目Session，以及该学生被允许读取的历史摘要。不能直接挂载整个企业目录。

# 三、笔迹时间轴不应由模型直接从原始JSON中猜

这是当前设计中最关键的技术问题。

原始`strokes.jsonl`适合：

- 精确存储；
- 重放；
- 渲染；
- 算法处理。

但不适合直接给模型阅读。几万行坐标无法让模型稳定判断：

- 哪段对应一个完整书写动作；
- 哪几段属于同一个公式；
- 哪些空白时间应该忽略；
- 哪些空间上相距很远但语义相关；
- 哪个时间范围值得渲染。

解决方法不是增加很多工具，而是给原始轨迹建立一个**多粒度时间轴索引**。

仍然只保留：

```text
read
bash
```

Agent通过Skill学习如何使用一个固定脚本。

# 四、轨迹分层：Stroke、Burst、Episode、Milestone

## 1. Stroke

一次落笔到抬笔：

```json
{
  "stroke_id": "s182",
  "start_ms": 38120,
  "end_ms": 38740,
  "bbox": [510, 280, 615, 332],
  "point_count": 47,
  "ink_length": 136.4
}
```

## 2. Burst

若干时间和空间上连续的Stroke。

例如：

```text
写“sin B =”
```

虽然包含多个字母和符号，但应视作一个书写Burst。

分组参考：

- 前后时间间隔较小；
- 包围框距离较近；
- 与上一笔区域重叠或相邻；
- 书写方向连续；
- 画布没有大幅移动。

阈值不能只用固定的“5秒”。应同时考虑时间和空间：

```text
时间间隔较短
且
空间距离较近
→ 合并

时间间隔稍长
但
仍在同一公式区域继续书写
→ 可能合并

时间间隔很短
但
突然跳到画布远端
→ 分开
```

## 3. Episode

若干语义上可能属于同一步骤的Burst：

```text
画三角形
写已知条件
列正弦定理
求出候选角
划掉错误结果并重写
```

Episode不要求模型事先识别数学语义，可以先由以下信号划分：

- 长停顿；
- 大幅空间跳转；
- 撤销或划除；
- Agent发出新提示；
- 学生提交回答；
- 画布视口切换；
- 新建明显独立区域。

## 4. Milestone

关键时刻的全局快照：

- 开始答题；
- 第一次停顿求助；
- Agent提示前；
- Agent提示后；
- 提交答案；
- 修改答案；
- 完成本题。

最终层级：

```text
Milestone
  └─ Episode
       └─ Burst
            └─ Stroke
                 └─ Point
```

模型一般只操作Episode和Burst ID，不直接操作毫秒时间戳。

# 六、让Agent选择“片段ID”，而不是选择时间戳

Skill中应明确：

```markdown
# 草稿观察原则

1. 不要直接读取完整strokes.jsonl。
2. 首先读取draft/timeline.md。
3. 根据当前教学问题选择最小的相关Episode或Burst。
4. 默认从单个Episode开始，不要直接渲染整个答题过程。
5. 信息不足时向前或向后扩展一个相邻片段。
6. 若两个片段空间距离较大，使用分面渲染，不要生成巨大的联合包围框。
7. 只有判断书写顺序时才生成回放或关键帧。
8. 原始时间戳仅用于脚本内部。
```

模型执行：

```bash
python scripts/draft.py render --episode E04
```

或：

```bash
python scripts/draft.py render \
  --bursts B17,B18,B19 \
  --mode delta
```

而不是：

```bash
python scripts/render.py --start 162.4 --end 264.7
```

# 七、解决“跨度太大”和“空白太多”

## 1. 使用有效书写时间，而不是墙上时间

假设：

```text
02:00 写了三笔
02:05-03:40 停顿
03:41 又写了两笔
```

如果按时间连续渲染，会包含96秒无用空白。

脚本应提供：

```text
wall_time：真实时间
active_time：仅有笔迹事件的时间
```

默认按`active_time`压缩展示。

回放可以显示：

```text
片段1
── 停顿96秒 ──
片段2
```

不需要生成96秒静止画面。

## 2. 空间不连续时分面展示

如果学生先在左上画图，后在右下列式，联合包围框可能包含大量空白。

不要这样：

```text
┌──────────────────────────┐
│ 左上图形                 │
│                          │
│                          │
│                 右下公式 │
└──────────────────────────┘
```

应输出：

```text
┌─────────────┬─────────────┐
│ 片段A 左上  │ 片段B 右下  │
│ 00:21       │ 00:34       │
└─────────────┴─────────────┘
```

每个面板带：

- Episode/Burst编号；
- 相对时间；
- 顺序箭头；
- 必要的上一状态淡化背景。

## 3. Delta模式

默认不是展示整张草稿，而是：

```text
已有内容：浅灰
本片段新增：黑色
本片段删除或划除：虚线标记
```

这样模型能直接判断“刚刚发生了什么”。

## 4. Contact Sheet

当模型还不知道应该看哪个Episode时，脚本生成多个小预览：

```bash
python scripts/draft.py contact-sheet \
  --episodes E01:E07 \
  --output tmp/timeline-overview.png
```

一张图包含：

```text
E01 画图
E02 标注
E03 初次列式
E04 修改
E05 提示后补写
E06 重新计算
E07 最终提交
```

模型先看总览，再选择局部。

# 八、时间轴选择评分

脚本可以给每个候选片段计算一个简单评分，而不需要额外模型：

$$
S =
w_rR+
w_fF+
w_nN+
w_cC+
w_aA
-
w_iI
-
w_bB
-
w_sL
$$

其中：

- $R$：时间新近程度；
- $F$：与当前关注空间区域的重叠程度；
- $N$：新增笔迹比例；
- $C$：修改、删除或重写信号；
- $A$：与Agent消息、求助或提交事件的邻近程度；
- $I$：无操作时间比例；
- $B$：联合图片中的空白比例；
- $L$：片段长度和图像成本。

Agent不需要知道公式，只看到脚本输出：

```text
当前建议片段：

1. E05 score=0.89
   原因：最近、提示后新增、区域紧凑

2. E04 score=0.74
   原因：存在明显删除和重写

3. E03 score=0.51
   原因：首次完整列式
```

Agent可以接受建议，也可以根据教学意图选择其他片段。

# 九、根据教学意图改变选择策略

时间轴脚本接受一个简单`intent`参数：

```bash
python scripts/draft.py suggest --intent stuck
python scripts/draft.py suggest --intent correction
python scripts/draft.py suggest --intent method-change
python scripts/draft.py suggest --intent after-hint
python scripts/draft.py suggest --intent final-review
```

对应策略：

| 意图 | 优先查看 |
|---|---|
| `stuck` | 最后一个完整Burst＋其前一相关Burst |
| `correction` | 删除、划除和重写评分最高的Episode |
| `method-change` | 空间跳转、大停顿或公式结构明显变化前后 |
| `after-hint` | Agent提示之后的第一个Episode，并附提示前最后一个Episode |
| `final-review` | Milestone快照＋所有Episode的Contact Sheet |
| `visual-confirm` | 当前区域最小可辨识Burst |
| `history-compare` | 当前Episode＋历史相似题的最终Milestone |

这仍然只是一个脚本，不增加新的模型工具。

# 十一、与“在线容器环境”的对应关系

我无法查看当前ChatGPT产品后台的私有实现，但OpenAI公开的Sandbox Agents文档已经描述了非常接近的模式：

- Agent工作在真实文件系统中；
- 可以使用Shell和文件工具；
- Workspace可以持久化；
- 可以保存快照；
- 可以暂停、恢复和迁移；
- 长期Memory与Conversation Session分离；
- 多个Agent可以使用不同Memory布局隔离。([OpenAI GitHub Pages](https://openai.github.io/openai-agents-python/sandbox/memory/?utm_source=chatgpt.com))

对你们的产品而言，可以把每道题理解为一次这样的在线工作环境：

```text
题目开始
→ 创建或恢复Workspace
→ Pi Agent进入
→ 学生聊天和草稿不断进入环境
→ Agent按需读文件和运行脚本
→ 题目结束
→ 保存Session与Workspace快照
→ 释放计算资源
→ 下一题载入连续性包和最新画像
```

# 十二、最终收敛

推荐将系统正式定义为：

> **一题一Session的文件系统原生教学Agent。教学Agent在短生命周期在线沙箱中，通过Prompt、Skills、文件和Shell自主完成观察、推理和引导；日内连续性包承担题目间的即时衔接；独立画像Agent每日异步整合历史Session并生成新的长期画像版本。企业场景通过持久Workspace、临时Sandbox租约、只读公共内容包和消息队列实现多租户与高并发。**

笔迹侧最重要的设计不是让模型理解完整JSON，而是：

> **原始轨迹用于存储，分层时间轴用于导航，预览图用于选择，局部渲染用于理解。**

即：

```text
Point
→ Stroke
→ Burst
→ Episode
→ Milestone
```

模型先选择Episode，再逐步展开Burst，不直接猜测时间戳。这样既保持极简工具集，也能让Agent具备真正主动、智能的草稿观察能力。

## 一、需要生成的四类教学图

### 1. 学生草稿引用图

优先使用学生自己的表达作为讲解基础：

- 裁剪学生刚写的公式；
- 展示提示前后两个草稿片段；
- 突出划除、改写或新增内容；
- 并排展示两种解法；
- 放大看不清的局部。

系统生成的是**派生讲解图**，不修改学生原草稿，符合当前“Agent只在聊天栏引导、不写入草稿”的设计。`草稿纸设计方案.txt`

例如：

```text
你前面这一步列式是正确的：

[学生草稿局部图]

问题出现在求出第一个角以后。这里还需要考虑补角：

[补角关系示意图]
```

### 2. 规范数学示意图

适合解释：

- 三角形边角关系；
- 辅助线；
- 圆、切线、弦；
- 坐标系；
- 向量；
- 立体几何投影；
- 数轴和区间。

这类图应由确定性代码绘制，不使用通用文生图模型。文生图容易出现角标、公式、长度和几何关系错误。

### 3. 函数与数据图像

适合生成：

- 函数图像；
- 参数变化；
- 零点和交点；
- 单调区间；
- 导数与原函数关系；
- 统计图；
- 数值验证结果。

SymPy可以生成二维、三维、参数和隐式函数图，并可通过Matplotlib输出；Matplotlib能够保存PNG、SVG、PDF等格式。([Matplotlib](https://matplotlib.org/stable/api/_as_gen/matplotlib.pyplot.savefig.html?utm_source=chatgpt.com))

### 4. 分步过程图

不要把所有信息一次堆到一张图里，可以生成三到四个连续小图：

```text
① 标出已知条件
② 添加辅助线
③ 建立数量关系
④ 筛选最终结果
```

这类“分面图”比动画更容易实现，也更适合学生按自己的速度阅读。

## 五、`visual-explanation` Skill的核心规则

Skill不需要很长，重点规定决策原则：

```markdown
---
name: visual-explanation
description: 当数学关系涉及空间结构、函数变化、步骤转换或学生草稿局部时，用于生成与讲解紧密对应的教学图。
---

# 教学可视化原则

1. 先判断图形是否能减少文字解释或揭示关键关系。
2. 简单计算、定义回忆和一句话可以说明的问题不生成图片。
3. 优先引用学生自己的草稿，再考虑生成规范图。
4. 不修改学生原始草稿，只生成派生裁剪图或讲解副本。
5. 每张图只表达一个主要概念。
6. 图中的标记必须与正文使用相同字母和符号。
7. 相关说明应紧邻对应图片。
8. 不添加与教学目标无关的装饰。
9. 几何和函数关系必须用代码生成，不使用文生图。
10. 图片生成后先自行查看，确认标签、方向和公式无误。
11. 图像不能替代追问；诊断模式下不得借图直接泄露完整答案。
```

这基本涵盖多媒体学习中的相关性、连贯性和空间邻近原则。([Wiley Online Library](https://onlinelibrary.wiley.com/doi/full/10.1111/jcal.12197?utm_source=chatgpt.com))

## 一、使用 Markdown 自定义链接作为引用协议

不建议让模型输出复杂 JSON 或可执行前端组件。最简洁的方式是复用 Markdown 链接语法，定义两个自有 URI Scheme：

```text
draft://    引用草稿
asset://    引用生成的图片
```

### 引用 Episode

```markdown
你在[这一步](draft://sheet/q007/episode/E04?version=47&intent=attention&view=delta)
已经正确列出了正弦定理。
```

### 引用 Burst

```markdown
注意[这里写出的第二个角](draft://sheet/q007/burst/B19?version=47&intent=correct&view=ink)。
```

### 引用时间段

```markdown
从[第一次列式到重新计算](draft://sheet/q007/time/166000-198000?version=47&intent=compare&view=delta)
可以看出你改换了思路。
```

### 引用空间区域

```markdown
请检查[右下角这一块](draft://sheet/q007/region/R03?version=47&intent=error&view=area)。
```

模型看到的只是普通 Markdown；前端解析后不会进行网页跳转，而是驱动右侧草稿纸。

## 二、引用目标的层级

建议支持五种目标：

| 类型 | 示例 | 用途 |
|---|---|---|
| Episode | `E04` | 引用一个完整解题阶段 |
| Burst | `B19` | 引用一组连续书写内容 |
| Stroke | `S182` | 精确引用某一笔或辅助线 |
| Region | `R03` | 引用空间区域 |
| Time Range | `166000-198000` | 引用一个原始时间区间 |

实际使用优先级应是：

```text
Episode
→ Burst
→ Region
→ Stroke
→ 原始时间段
```

模型应优先引用稳定的片段ID。时间段作为补充，因为直接选择时间可能包含大量停顿或空间上分散的内容。

对于时间段引用，系统不应简单计算一个巨大包围框，而应：

```text
时间段
→ 找到覆盖的Stroke
→ 按空间连通性分组
→ 得到一个或多个区域
→ 分别高亮
```

这样即使学生先在左上画图、后在右下列式，也不会高亮中间的大块空白。

## 三、引用必须固定草稿版本

URI中应包含：

```text
version=47
```

原因是学生可能在Agent回复后继续书写、划除或修改内容。

完整引用对象实际上是：

```ts
type DraftReference = {
  sheetId: string;
  version: number;

  target:
    | { type: "episode"; id: string }
    | { type: "burst"; id: string }
    | { type: "stroke"; id: string }
    | { type: "region"; id: string }
    | { type: "time"; startMs: number; endMs: number };

  intent: "attention" | "correct" | "error" | "relation" | "compare";
  view: "ink" | "area" | "delta" | "historical";
};
```

当引用的笔迹之后已被划掉时，点击引用可以：

1. 切换到对应历史版本；
2. 或在当前草稿上以半透明“幽灵笔迹”显示；
3. 退出引用后恢复当前版本。

原始Stroke事件不能删除，否则历史引用会失效。

## 四、颜色不要让模型任意指定十六进制值

模型可以附加颜色语义，但不应输出：

```text
color=#FF7733
```

应输出语义化的`intent`：

| intent | 建议显示 | 含义 |
|---|---|---|
| `attention` | 黄色或橙色 | 请关注 |
| `correct` | 绿色 | 该步骤正确 |
| `error` | 红色 | 已确认的问题 |
| `relation` | 蓝色 | 两处内容存在关系 |
| `compare` | 紫色 | 前后或两种方法对比 |

这样可以统一主题、支持深色模式和无障碍配色，也避免模型随意生成难以辨认的颜色。

还应同时使用线型或图标表达状态，不能只依赖颜色：

- 正确：绿色实线＋对勾；
- 待关注：黄色脉冲＋感叹号；
- 错误：红色虚线＋叉号；
- 关联：蓝色编号或连线。

## 五、草稿高亮必须位于独立覆盖层

草稿画布建议分成：

```text
背景层
学生墨迹层
历史幽灵层
引用高亮层
交互状态层
```

引用高亮层只负责：

- 包围区域；
- 对目标Stroke着色；
- 降低无关内容透明度；

聊天前端可采用：

```text

├─ 块级公式
```

数学公式建议使用 KaTeX：



## 十一、引用的生命周期

建议区分三种状态：

- **临时引用**：悬停时显示，鼠标移开即消失；
- **固定引用**：点击后保持，学生再次点击关闭；
- **证据引用**：进入诊断报告，长期保存且不可随意失效。

Agent日常讲解默认使用临时或固定引用；正式错因和掌握度报告使用证据引用。

# 设计理念、设计思路与方案选择依据

## 一、设计理念

本方案的核心设计理念是：

> **让学生继续以最自然的数学方式思考，让 Agent 主动适应学生，而不是让学生适应 Agent。**

高中数学学习和考试中，学生真正的思考过程往往不发生在聊天框或最终答案中，而发生在草稿纸上：画图、标条件、列公式、尝试不同方法、划掉错误步骤、重新计算，这些过程包含了大量能够反映学生知识掌握和解题策略的信息。

传统聊天式数学 Agent 更多依赖学生主动用文字描述问题，或者根据最终答案判断对错。这种方式容易丢失解题过程，也难以区分“知识不会”“方法选择错误”“条件遗漏”“计算失误”等不同原因。而赛题本身正要求系统通过少量题目完成知识诊断，并尽量把错误归因到具体知识点、题型和错因，而不是给出泛化的“基础薄弱”结论。`高中数学知识掌握诊断与学习规划Agent赛题说明_参赛者版.md`

因此，本方案不把聊天框作为学生主要数学表达空间，而采用：

> **草稿主交互，聊天主引导。**

学生仍然像平时做题一样在草稿纸上思考；Agent则通过聊天提出问题、进行确认、提供适度提示和完成诊断。

草稿不是一个附加的手写输入组件，而是整个系统的核心过程证据入口。`草稿纸设计方案.txt`

---

## 二、总体设计思路

整体设计遵循三个原则：

### 1. 保持学生原有解题行为

系统尽可能不改变学生本来的数学学习方式。

学生看到题目后：

> 阅读题目  
> → 在草稿纸上画图、列式和计算  
> → 必要时与 Agent 对话  
> → 提交结果

而不是：

> 阅读题目  
> → 把自己的完整思路重新组织成文字  
> → 输入聊天框  
> → 等待 Agent 判断

这样可以降低额外的表达负担，同时保留更真实的解题过程。

---

### 2. 让 Agent 主动获取需要的信息

系统不把所有草稿、全部历史记录、完整画像和所有课程资料一次性塞给模型。

Agent首先获得当前最重要的信息，包括：

- 当前题目；
- 当前教学目标；
- 学生长期画像摘要；
- 当天学习连续性摘要。

其他信息全部作为文件存在于 Agent 的工作环境中。

当 Agent 判断需要更多信息时，再自主读取：

- 学生详细画像；
- 历史题目 Session；
- 教案和知识资料；
- 题库；
- 草稿时间轴；
- 某一段具体草稿；
- 数学计算或验证结果。

因此系统形成：

> **Prompt 提供当前任务，Files 提供外部记忆，Skills 提供行为方法，Shell 提供通用执行能力。**

而不是为每一个教学动作设计一个独立的专用工具。

---

### 3. 把实时教学和长期画像分开

系统将学生状态划分为三个不同层次：

> 当前题目状态  
> → 当天学习连续性  
> → 长期学生画像

当前题目由教学 Agent 负责。

题目结束后，只生成一个轻量的日内连续性摘要，例如：

- 今天已经完成多少题；
- 上一题做了什么；
- 是否使用提示；
- 上一题还有什么需要继续观察。

这些信息直接进入下一题的新 Session。

长期画像则不由教学 Agent 实时修改，而由独立的画像 Agent 定期读取一段时间内的多个 Session，再统一整理学生长期稳定的知识掌握、错因和学习特点。

因此形成：

> **教学 Agent 负责“现在怎么教”，画像 Agent 负责“长期怎么看这个学生”。**

这样可以避免学生某一道题中的偶然失误立即污染长期画像。

# 三、该方案主要解决了什么问题

## 1. 解决“只知道做错，不知道为什么错”

赛题明确指出，学生可能只是公式适用条件不清，却被笼统判断为基础薄弱；也可能只是计算失误，却被误判为知识点不会。`高中数学知识掌握诊断与学习规划Agent赛题说明_参赛者版.docx`

仅依靠最终答案，很难区分：

> 不会公式  
> 方法不会选择  
> 方法正确但代入错误  
> 漏掉分类讨论  
> 条件理解错误  
> 单纯计算失误  
> 偶然笔误

加入草稿过程后，Agent可以同时观察：

> 最终结果  
> ＋ 使用了什么公式  
> ＋ 画了什么图  
> ＋ 解题步骤顺序  
> ＋ 修改了什么  
> ＋ 被提示后如何继续

从而把诊断从“结果诊断”推进到“过程诊断”。

---

## 2. 解决传统聊天式辅导表达成本过高的问题

很多数学过程很难自然地通过聊天表达。

例如学生可能只需要在图中补一条辅助线、写一个公式，就已经表达了自己的思路。如果要求学生解释：

> “我从 A 点作 BC 的高，然后准备用面积关系……”

实际上增加了与真实数学学习无关的表达成本。

草稿纸使学生可以直接用数学语言表达，Agent负责主动理解和追问。

因此产品不是要求学生“把数学翻译成自然语言”，而是让模型学习理解学生原本就在使用的数学表达。

---

## 3. 解决 Agent 对学生状态判断过早的问题

单次错误不能稳定代表长期知识水平。

因此系统不采用：

> 一题答错  
> → 立即更新长期画像  
> → 判断学生不会某知识点

而采用：

> 当前题产生证据  
> → 下一题继续验证  
> → 多个 Session 累积  
> → 长期画像 Agent 定期综合  
> → 形成更稳定判断

这样能够更好地区分：

- 临时失误；
- 当前状态不好；
- 提示后可以完成；
- 长期稳定薄弱。

---

## 4. 解决 Agent 上下文越来越长的问题

如果把学生所有历史聊天、所有草稿、所有课程材料持续加入上下文，随着使用时间增长，Agent会面对越来越大的上下文。

本方案把长期信息放入文件系统，只把必要摘要直接放进 Prompt。

形成：

> 摘要先进入上下文  
> → Agent发现需要更多信息  
> → 再读取对应文件  
> → 只查看与当前问题相关的内容

这样历史可以不断积累，而当前 Session 仍保持相对简洁。

---

## 5. 解决草稿过程信息量过大的问题

原始数字笔迹可能包含大量坐标和时间信息，直接把完整 JSON 交给模型既浪费上下文，也很难理解。

因此设计：

> Point  
> → Stroke  
> → Burst  
> → Episode  
> → Milestone

模型通常不直接处理大量原始坐标，而先阅读草稿时间轴，再选择最值得查看的片段。

形成：

> 原始轨迹负责保存  
> → 时间轴负责导航  
> → 预览负责选择  
> → 局部图片负责理解

这样既保留完整数据，又避免让模型一次处理所有信息。

---

## 6. 解决聊天和草稿两个界面彼此割裂的问题

如果左边聊天、右边草稿只是简单并排，Agent即使说：

> “你这里有问题。”

学生仍不知道“这里”具体在哪里。

因此设计“草稿可寻址引用”。

Agent可以在聊天中引用：

- 某个 Episode；
- 某个 Burst；
- 某组笔迹；
- 某个区域；
- 某个时间段。

学生点击聊天中的引用后，草稿自动定位并高亮对应区域。

因此交互变成：

> Agent说“这里”  
> → 系统真的可以指出“这里”。

聊天和草稿由此成为一个整体，而不是两个独立组件。

## 7. 解决数学讲解只有文字、不够直观的问题

教学 Agent 的输出不仅支持普通 Markdown，还可以：

- 输出数学公式；
- 引用学生自己的草稿；
- 高亮相关草稿区域；
- 在运行环境中生成数学图；
- 在聊天对应位置插入图像。

因此一次讲解可以自然组成：

> 文字  
> ＋ 公式  
> ＋ 学生草稿引用  
> ＋ 几何图或函数图  
> ＋ 下一步引导问题

既提高解释能力，又不需要 Agent 修改学生原始草稿。

# 四、为什么选择“一题一个 Session”

每一道数学题本身就是一个相对完整的认知任务。

如果整个诊断过程始终使用一个超长 Session：

> 第1题  
> → 第2题  
> → 第3题  
> → ……  
> → 第20题

前面大量聊天、工具结果和草稿分析会不断累积，最终影响当前题目的上下文质量。

因此选择：

> **一题一 Session。**

每一道题独立保存：

- 题目；
- 聊天；
- 草稿；
- Agent观察过程；
- 提示情况；
- 最终结果。

题目之间通过“日内连续性摘要”和“长期画像摘要”保持联系。

于是既得到：

> **题内上下文完整**

又保持：

> **题间上下文简洁**

同时每个 Session 本身还可以作为日后画像更新、教师复核和模型评测的完整原始证据。

# 五、为什么选择 Pi Agent 式文件系统架构

本方案没有选择为 Agent 建立大量复杂领域工具，而是尽可能保持通用 Agent 的自主能力。

核心工具保持精简，例如：

> 文件读取  
> Shell / Python

课程资料、历史记录、学生信息、草稿数据和教学规则，都通过工作目录暴露给 Agent。

选择这种架构主要有四个原因。

### 第一，模型本身已经非常熟悉文件和命令行

与其要求模型学习大量新的领域 API，不如使用它已经非常熟悉的：

> 文件  
> Markdown  
> JSON  
> Python  
> Shell

降低Agent理解工具的成本。

### 第二，能力具有天然组合性

例如查看学生草稿可以组合成：

> 阅读时间轴  
> → 选择 Episode  
> → 执行渲染脚本  
> → 查看图片

数学验证可以：

> 写 Python  
> → 使用 SymPy  
> → 查看结果

不需要给每种操作分别定义新的工具。

### 第三，新的能力容易加入

以后需要：

- 新的数学绘图；
- 新的题库检索；
- 新的草稿分析；
- 新的章节；
- 新的统计功能；

可以通过增加资料、脚本或 Skill 实现，而不需要重新设计整个 Agent API。

### 第四，更接近真正的自主 Agent

系统规定的是：

> Agent 有哪些资源、哪些原则、哪些能力和哪些边界。

而不是：

> 系统提前规定 Agent 每一步必须做什么。

教学过程因此能够根据不同学生表现动态变化。

# 六、为什么选择 Skills，而不是复杂工作流

数学教学并不存在唯一固定流程。

同一个错误答案可能由不同原因产生，同一种知识薄弱也可能需要不同的追问方式。

因此如果把教学过程完全写成：

> 如果 A → 做 B  
> 如果 B → 做 C  
> 如果 C → 做 D

最终会形成大量复杂分支。

本方案更倾向于把教学方法写成 Skills，例如：

- 如何观察草稿；
- 如何进行错因诊断；
- 如何进行苏格拉底式追问；
- 如何控制提示强度；
- 如何选择下一题；
- 什么时候应该生成图示。

Agent根据当前情况按需读取相应 Skill。

因此：

> **代码负责能力边界，Skill负责行为原则，模型负责当前决策。**

这样能够保持架构简单，同时保留教学过程需要的灵活性。

# 七、为什么教学 Agent 不直接修改长期画像

教学 Agent 的目标是：

> 让当前这道题的教学和诊断尽可能准确。

画像 Agent 的目标则是：

> 从很多题和较长时间跨度中判断学生真正稳定的学习特征。

两者所需视角不同。

如果教学 Agent 在每道题结束后直接修改长期画像，很容易：

> 单次失误  
> → 被长期保存  
> → 后续题目继续强化这一错误判断

因此选择：

> Session 作为原始事实  
> → 日内连续性摘要负责短期衔接  
> → 画像 Agent 定期从多 Session 中重新综合

这是一种“原始记录与长期记忆分离”的设计。

这是一个重要的产品边界。

- 修改公式；
- 擦除错误；
- 补全步骤；

因此学生原始墨迹始终只允许学生自己产生。

Agent可以：

> 引用  
> 高亮  
> 放大  
> 生成讲解副本  
> 生成新的示意图

但不能改变原始草稿。

因此产品不追求：

而追求：

> 每一道题获取尽可能高价值的信息。

一题中除了正确与否，还可以获得：

- 解法选择；
- 草稿过程；
- 提示依赖；
- 错误位置；
- 修改行为；
- 对追问的回答。

如果仍有多个可能错因，再针对最需要区分的问题选择下一题。

因此总体路线是：

> 少量题目  
> ＋ 丰富过程证据  
> ＋ 针对性追问  
> ＋ 必要时微型复测

最终以更少题量获得更具体的诊断。

# 十、整个方案最终形成的差异化

本方案最终不是一个“会做数学题的聊天机器人”。

其核心区别在于四个能力：

### 1. 草稿过程可观察

不仅知道学生最后答了什么，还能够观察学生是怎样一步步得到答案的。

### 2. 错因判断可消歧

> **让草稿成为学生思维与 Agent 之间的共享媒介，让 Session 成为学习过程的原始记忆，让画像 Agent 从长期历史中形成稳定认知，让教学 Agent 始终专注于学生此刻正在解决的问题。**

最终解决的并不是“AI如何把数学题讲得更完整”，而是：

> **AI如何在尽量不改变学生自然学习行为的情况下，真正理解学生正在怎样思考，并据此完成更少题量、更准确、更可解释的个性化诊断与教学。**

> → 最终答案  
> → Agent观察过程  
> → 追问与验证  
> → 错因判断  
> → 下一题或教学引导  
> → 掌握度诊断  
> → 学习计划

因此，系统关注的不只是：

> **“学生答错了什么。”**

更关注：

> **“学生是怎样一步一步走到这里的。”**

赛题本身要求通过少量题目和追问完成诊断，并尽量把学生错误定位到具体知识点、题型和错因，而不是只给出泛化的“基础薄弱”结论。`高中数学知识掌握诊断与学习规划Agent赛题说明_参赛者版.md`

---

# 二、核心设计理念

整个方案建立在一个核心理念之上：

> **让学生继续使用最自然的数学学习方式，让 Agent 主动适应学生，而不是让学生适应 Agent。**

高中数学学习过程中，大量真正的思考并没有被学生表达成自然语言，而是直接存在于：

- 图形；
- 辅助线；
- 条件标注；
- 数学公式；
- 推导过程；
- 划除；
- 重写；
- 方法切换；
- 计算过程。

如果要求学生将这些过程重新组织成聊天文字，不仅增加额外负担，也会改变学生本来的解题方式。

因此本方案采用：

> **草稿主交互，聊天主引导。**

学生仍然按照真实学习和考试习惯：

> 看题  
> → 画图  
> → 列式  
> → 推导  
> → 修改  
> → 得出答案

Agent则在必要的时候：

> 观察  
> → 判断  
> → 追问  
> → 提示  
> → 验证  
> → 再观察

草稿不是附加输入方式，而是整个系统理解学生思维过程的重要入口。`草稿纸设计方案.txt`

---

# 三、该方案主要解决的问题

## 1. 解决“知道做错，但不知道为什么错”

只看最终答案，通常无法判断学生究竟是：

- 不会知识点；
- 不理解公式条件；
- 不会选择方法；
- 分类讨论遗漏；
- 边角对应错误；
- 计算失误；
- 偶然笔误。

例如两名学生得到相同错误答案：

学生A可能连正弦定理都没有正确列出；

学生B可能公式完全正确，只是在 SSA 情形下遗漏了补角。

如果只看答案，两个人可能得到相同诊断。

如果加入草稿过程：

> 最终答案  
> ＋ 使用公式  
> ＋ 图形  
> ＋ 中间步骤  
> ＋ 修改行为  
> ＋ 后续追问

就有机会形成不同的错因判断。

因此系统从：

> **结果诊断**

进一步转向：

> **过程诊断。**

---

## 2. 解决传统聊天式数学 Agent 表达成本过高的问题

数学思维并不天然适合全部通过聊天表达。

学生画一条辅助线，可能已经表达完整的解题意图。

如果要求学生再输入：

> “我准备从A点向BC作高，然后利用面积关系……”

实际上增加了额外认知负担。

本方案让学生继续直接使用：

> 图  
> 公式  
> 符号  
> 草稿

Agent主动理解这些信息。

也就是：

> **不是要求学生把数学翻译成自然语言，而是让 Agent 学会理解学生本来就在使用的数学语言。**

---

## 3. 解决一次错误导致画像误判的问题

单道题不能代表长期掌握情况。

因此系统不采用：

> 一题答错  
> → 马上认定知识薄弱  
> → 永久写入画像

而采用：

> 当前题产生证据  
> → 后续题继续验证  
> → 多个 Session 积累  
> → 长期画像 Agent 综合  
> → 判断是否形成稳定问题

从而区分：

- 偶然错误；
- 当前状态问题；
- 提示后能够完成；
- 持续出现的稳定错因。

---

## 4. 解决 Agent 长期使用后上下文越来越大的问题

如果学生学习几十甚至几百道题以后，把：

- 全部聊天；
- 全部草稿；
- 全部历史题目；
- 全部教案；
- 全部画像；

全部放入当前模型上下文，会导致大量无关信息干扰当前任务。

因此本方案采用：

> **高价值摘要直接进入 Prompt，详细信息按需读取。**

Agent首先获得：

- 当前题目；
- 当前教学目标；
- 长期画像摘要；
- 当天连续性摘要。

需要更多信息时，再自主读取：

- 详细画像；
- 历史 Session；
- 教案；
- 题库；
- 草稿时间轴；
- 具体草稿片段。

形成：

> 摘要导航  
> → 按需展开  
> → 局部使用

而不是一次性塞入全部历史。

---

## 5. 解决原始笔迹数据模型难以理解的问题

数字草稿可能产生数万甚至数十万笔迹坐标。

如果直接把完整 JSON 提供给模型，模型很难判断：

- 哪些笔迹属于一个公式；
- 哪些属于一个解题步骤；
- 哪些停顿有意义；
- 哪些空间跳跃表示换区域；
- 应该查看哪一个时间范围。

因此将原始过程分层组织为：

> Point  
> → Stroke  
> → Burst  
> → Episode  
> → Milestone

原始轨迹负责保存真实数据；

时间轴负责导航；

预览负责选择；

局部图片负责理解。

即：

> **原始轨迹用于存储，结构化时间轴用于导航，图片用于模型理解。**

---

## 6. 解决聊天和草稿彼此割裂的问题

如果Agent回复：

> “你这里可能出了问题。”

学生需要知道“这里”到底在哪里。

因此系统设计草稿可寻址引用机制。

Agent可以在聊天回复中引用：

- Episode；
- Burst；
- 某组笔迹；
- 某个区域；
- 某个时间段。

学生点击引用：

> 聊天中的“这里”  
> → 草稿自动定位  
> → 对应区域高亮

这样聊天与草稿真正成为一个统一教学界面。

---

## 7. 解决纯文字讲解不够直观的问题

教学回复支持：

> Markdown文字  
> ＋ 数学公式  
> ＋ 草稿引用  
> ＋ 草稿高亮  
> ＋ Agent生成的教学图

因此讲解不再只是长段文字。

例如：

> “你在这里已经正确列出了正弦定理。”

点击“这里”：

→ 草稿对应公式高亮。

随后聊天中直接显示公式：

$$
\frac{a}{\sin A}=\frac{b}{\sin B}
$$

然后插入Agent生成的几何示意图。

最后继续追问：

> “这两个候选角都一定能够构成三角形吗？”

形成真正的图文互动教学。

---

# 四、总体设计原则

## 1. 学生保持主体性

Agent：

- 不替学生写草稿；
- 不替学生补辅助线；
- 不修改学生公式；
- 不删除学生内容。

学生墨迹始终属于学生本人。

Agent只能：

- 观察；
- 引用；
- 高亮；
- 生成讲解副本；
- 生成独立示意图；
- 通过聊天引导。

因为只有保持草稿原始性，草稿才能继续作为学生真实思维过程的证据。`草稿纸设计方案.txt`

---

## 2. 少题量，深过程

赛题要求的是聊天式轻量测评和自适应诊断，而不是重新做一整张试卷。`高中数学知识掌握诊断与学习规划Agent赛题说明_参赛者版.md`

因此系统追求：

> **每一道题获取更多有效信息。**

除了答案正确与否，还利用：

- 解题方法；
- 草稿过程；
- 提示依赖；
- 修改行为；
- 错误位置；
- 学生对追问的回答。

然后根据当前证据决定：

> 继续追问？

还是：

> 换一道针对性诊断题？

最终通过较少题目获得足够诊断证据。

---

## 3. 先形成假设，再主动消歧

Agent不应看到错误后立即决定错因。

推荐过程：

> 观察学生过程  
> → 形成几个可能原因  
> → 判断当前缺什么证据  
> → 观察草稿 / 追问 / 微型复测  
> → 排除部分假设  
> → 再形成判断

所以诊断过程本质上是：

> **观察 → 假设 → 求证 → 消歧 → 结论**

---

## 4. 最小而准确的能力集

本方案不为每一种业务行为都设计Agent工具。

而是尽可能采用：

> 文件  
> Prompt  
> Skills  
> Shell  
> Python

课程资料是文件；

学生详细画像是文件；

历史Session是文件；

草稿是文件；

题库和教案是文件；

数学处理和绘图通过固定脚本完成。

Agent只需要很少的通用能力。

核心理念是：

> **通过一个精心设计的环境让Agent自主完成任务，而不是用大量工具预先规定Agent每一步怎么走。**

---

# 五、为什么选择 Pi Agent 式架构

本系统采用一个轻量的通用 Agent Harness 作为教学 Agent 底层。

Agent生活在一个面向当前题目的隔离工作环境中。

这个环境包含：

> Prompt  
> Files  
> Skills  
> Shell / Python

Agent可以自主：

- 阅读教案；
- 查看题库；
- 阅读学生历史；
- 查看草稿；
- 运行数学验证；
- 生成图像；
- 判断下一步应该观察、追问还是提示。

选择这一方案的原因主要有四个。

### 第一，模型本身熟悉文件系统

模型已经熟悉：

- Markdown；
- JSON；
- Python；
- Shell；
- 文件路径。

相比大量自定义领域API，学习成本更低。

### 第二，能力天然可以组合

例如：

> 查看时间轴  
> → 找到Episode  
> → 调用脚本渲染  
> → 查看图片

不需要分别定义大量领域工具。

### 第三，系统扩展简单

未来新增：

- 新章节；
- 新教案；
- 新绘图方式；
- 新诊断方法；
- 新数学验证；

可以主要通过：

> 文件  
> 脚本  
> Skill

扩展，而不是修改整个Agent架构。

### 第四，保留真正的Agent自主性

系统给Agent：

> 环境  
> 资源  
> 原则  
> 能力  
> 安全边界

而不是提前写死：

> 第一步必须做A  
> 第二步必须做B  
> 第三步必须做C

不同学生可以自然产生不同教学过程。

---

# 六、为什么使用 Skills 而不是复杂状态机

数学教学不存在一个固定流程。

同样的错误答案可能来自完全不同的原因。

因此不希望将所有教学策略写成大量：

> IF → ELSE → IF → ELSE

而是把稳定的教学方法写成 Skills。

例如：

- 如何观察草稿；
- 如何诊断错因；
- 如何追问；
- 如何控制提示等级；
- 如何选择练习；
- 什么时候应该生成示意图。

Agent遇到相应情景时自行读取和执行。

形成：

> **代码定义边界，Skill定义原则，Agent负责决策。**

---

# 七、为什么选择“一题一 Session”

每一道数学题本身就是一个相对独立的认知任务。

如果几十道题都放在同一个Session里：

> 前面大量聊天  
> ＋ 工具结果  
> ＋ 草稿观察  
> ＋ 图片  
> ＋ 推理历史

会不断污染当前上下文。

因此采用：

> **一题一个独立 Session。**

每一道题保存完整：

- 题目；
- 聊天；
- 草稿；
- Agent行为；
- 提示；
- 最终结果。

题目结束：

> 保存Session  
> → 生成短期连续性摘要  
> → 创建下一题Session

因此兼顾：

> **题内完整**

和：

> **题间简洁。**

---

# 八、为什么将教学 Agent 与画像 Agent 分离

系统存在两个不同时间尺度的问题。

教学 Agent关注：

> **学生现在这道题发生了什么？**

画像 Agent关注：

> **这个学生在几十道题甚至几天时间里表现出了什么稳定规律？**

因此两者分开。

教学 Agent：

> 当前题观察  
> → 教学  
> → 诊断  
> → 保存原始Session

画像 Agent：

> 多Session  
> → 长期综合  
> → 矛盾整理  
> → 判断稳定薄弱  
> → 更新学生画像

这样避免单题偶然现象直接污染长期状态。

---

# 九、三级记忆结构

系统最终形成三个时间尺度。

## 第一层：题内记忆

当前Pi Session。

包含：

> 当前题目  
> → 聊天  
> → 草稿  
> → Agent观察  
> → 本题判断

题目结束后封存。

---

## 第二层：日内连续性记忆

一道题结束后形成短摘要，例如：

> 今日已完成7题  
> 上一题使用一次提示  
> 正弦定理列式正确  
> SSA补角仍需继续观察  
> 下一题不要重复检查公式基础

下一题直接把它加入Prompt。

因此：

> 上一题Session  
> → 连续性摘要  
> → 下一题Session

---

## 第三层：长期学生画像

每天或周期性：

> 多个Session  
> ＋ 旧画像  
> → 画像Agent  
> → 新画像

长期画像记录：

- 稳定掌握内容；
- 稳定薄弱内容；
- 常见错因；
- 方法习惯；
- 提示依赖；
- 学习变化趋势。

---

# 十、整体产品流程

完整学习流程为：

> 学生进入系统  
> → 读取长期画像摘要  
> → 读取今日连续性摘要  
> → 确定当前诊断目标  
> → 选择第一道题  
> → 创建独立Session  
> → 学生通过草稿和聊天作答  
> → Agent观察草稿过程  
> → 形成候选判断  
> → 必要时追问或提示  
> → 学生继续作答  
> → 判断本题结果  
> → 保存Session  
> → 更新日内连续性摘要  
> → 自适应选择下一题  
> → 创建新的Session  
> → 继续诊断  
> → 达到诊断目标  
> → 生成掌握度报告  
> → 生成1-4周学习计划  
> → 后续复测  
> → 每日画像Agent更新长期画像  
> → 下一次学习继续使用新画像

赛题要求最终完成掌握度报告、错因归因和1-4周学习计划，因此这一闭环直接覆盖赛题核心目标。`高中数学知识掌握诊断与学习规划Agent赛题说明_参赛者版.docx`

---

# 十一、单题教学流程

一道题内部：

> 创建Session  
> → 注入当前题目  
> → 注入学生摘要  
> → 注入日内连续性信息  
> → 学生开始书写  
> → 笔迹持续记录  
> → 时间轴持续更新  
> → Agent根据当前教学需要决定是否观察  
> → 选择草稿Episode/Burst  
> → 查看对应草稿  
> → 判断当前状态  
> → 与学生对话  
> → 学生继续书写  
> → Agent再次观察  
> → 必要时执行数学验证  
> → 必要时进行提示  
> → 必要时生成图示  
> → 完成本题  
> → 保存Session

核心循环：

> **学生行动 → Agent观察 → Agent引导 → 学生继续行动。**

---

# 十二、草稿处理流程

学生书写：

> 原始点数据  
> → Stroke  
> → Burst  
> → Episode  
> → Milestone  
> → 时间轴索引

Agent首先看到的是：

> 草稿时间轴

然后：

> 判断当前最相关片段  
> → 查看局部预览  
> → 信息不足则扩大范围  
> → 必要时查看前后过程  
> → 最后才查看完整草稿

因此避免将整个草稿一次交给模型。

---

# 十三、草稿引用流程

Agent在回复中需要指向学生过程时：

> 选择Episode / Burst / Region  
> → 在Markdown中加入引用  
> → 前端识别引用  
> → 学生点击  
> → 草稿自动定位  
> → 对应笔迹或区域临时高亮

引用可以表达不同语义：

> 关注这里  
> 正确步骤  
> 已确认问题  
> 对比前后变化  
> 两处内容存在联系

高亮只存在于系统覆盖层。

不修改学生原始墨迹。

---

# 十四、图文教学流程

Agent首先判断：

> 纯文字是否已经足够？

如果不够：

> 优先引用学生草稿

仍然需要新的视觉解释：

> Agent调用环境内脚本  
> → 生成SVG / PNG  
> → 在Markdown回复中引用  
> → 前端在对应文字位置展示

于是一次完整回复可以是：

> 文字说明  
> → 草稿引用  
> → 数学公式  
> → 教学图  
> → 引导问题

实现真正的图文混合讲解。

---

# 十五、自适应诊断流程

当前题结束：

> 汇总答案  
> → 汇总草稿证据  
> → 汇总追问结果  
> → 判断哪些候选问题已经确认  
> → 判断哪些仍存在不确定性  
> → 判断当前诊断目标是否已有足够证据

如果不足：

> 选择信息价值最高的下一题

如果需要确认某个具体错因：

> 选择小型复测题

如果某项能力已有稳定证据：

> 不继续重复测量

最终达到：

> **以尽量少的题目获得尽量高质量的诊断证据。**

---

# 十六、长期画像流程

每天产生：

> Session 1  
> Session 2  
> Session 3  
> ……  
> Session N

这些Session保留原始事实。

每日异步启动画像 Agent：

> 读取旧画像  
> → 阅读当天Session  
> → 综合多题证据  
> → 处理矛盾  
> → 区分偶然失误与稳定问题  
> → 更新掌握情况  
> → 更新常见错因

# 十九、企业多用户运行思路

“一题一Session”是逻辑隔离单位，而不是意味着每一道题永久占用一个运行容器。

企业环境采用：

> **Session持久化，运行环境按需分配。**

学生发送消息：

> 找到当前Session  
> → 恢复工作区  
> → 分配一个空闲Sandbox  
> → 恢复教学Agent  
> → 处理当前一轮  
> → 保存Session和文件变化  
> → 返回结果  
> → 空闲后释放Sandbox

下一次学生继续时：

> 再次恢复。

因此：

> 不同学生之间可以并行；

但：

> 同一道题内部仍保持顺序执行。

实时教学任务优先；

长期画像更新、报告生成等任务异步运行。

# 二十一、方案的核心差异化

本项目最终不是一个：

> **“会解数学题的聊天机器人”。**

而是一个：

> **“能够观察学生真实解题过程，并围绕这个过程持续进行诊断和教学的 Agent。”**

核心差异集中在四点。

### 草稿过程可观察

Agent不仅知道答案，还能够观察学生是怎样完成这道题的。

### 诊断假设可消歧

Agent不会因为一次错误直接下结论，而是通过过程、追问和复测逐步确认。

### 教学证据可引用

聊天中的“这里”“这一步”“你刚才修改的位置”都可以真正对应到学生草稿中的具体位置。

### 学生画像可持续演化

单题Session保存事实；

日内摘要保存近期状态；

画像Agent负责长期整合。

因此，最终的产品理念可以概括为：

> **让草稿成为学生思维与 Agent 之间的共享媒介，让 Session 成为学习过程的原始记忆，让画像 Agent 从长期历史中形成稳定认知，让教学 Agent 始终专注于学生此刻正在解决的问题。**

整个方案最终解决的，不只是：

> **“AI怎样把一道数学题讲清楚。”**

而是：

> **“AI如何在尽量不改变学生自然学习行为的情况下，理解学生正在怎样思考，用尽可能少的题目获得足够有效的过程证据，并据此完成更准确、更可解释、更连续的个性化诊断与教学。”**
