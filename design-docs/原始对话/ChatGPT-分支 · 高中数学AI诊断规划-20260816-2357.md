## 一、正式赛题到底要求什么

### 1. 题目范围很小

主办方指定的试点章节只有：

**高中数学--解三角形**

提供了五组资料：

1. 解三角形入门题型  
2. 中线、角平分线、高线问题  
3. 外接圆、内切圆和多三角形问题  
4. 最值、范围问题  
5. 定理和模型问题  

另外提供一个 Excel 数据模板。

因此，目前不需要处理高中数学五本教材，也不需要覆盖函数、导数、数列、解析几何等全部章节。

---

### 2. 真正的核心任务

系统需要完成以下闭环：

```text
采集学生基本情况
        ↓
用少量题目进行初步测评
        ↓
根据答题情况动态调整下一题
        ↓
答错后追问，判断具体错因
        ↓
定位知识点、题型、方法和错误原因
        ↓
生成掌握度报告
        ↓
生成 1-4 周个性化学习计划
```

重点是“诊断”，不是普通题目答疑。

例如学生答错一道正弦定理题，系统不能只说：

> 你的解三角形基础比较薄弱。

而应判断成：

> 学生能够识别正弦定理，但在已知两边及其中一边对角时，遗漏了三角形可能存在两个解的分类讨论。

并给出判断证据和补救练习。

---

| 测评题/题库 | 80 道 |

核心关系是：

```text
题目
 ├─ 对应知识点 ID
 ├─ 对应题型 ID
 ├─ 对应常见错因 ID
 ├─ 难度

```

Excel 模板已经预设了这些表：

所以这个项目的数据基础应该是结构化 Excel/数据库，RAG 只是辅助检索手段。

1. 能否把五份资料结构化。

## 二、队友初版目前做了什么

```text

        ↓
OCR、公式标准化、意图识别
        ↓
RAG 检索
        ↓
根据意图路由到多个 Workflow
        ↓
Markdown / Word / PDF / LaTeX 输出
```

目前设计文档中实际上包含五至六类功能：

- 教案生成
- 题目解析
- 高考模拟组卷
- 知识点诊断
- 学情规划
- 问题整理归档

1. 初始出题；
2. 答题与错误分类；
3. 多轮追问；
4. 生成热力图和诊断报告。

错误被粗分为：

## 三、初版目前最主要的问题

### 1. 项目范围严重扩大

正式赛题要求的是：

> 解三角形章节诊断与学习规划。

当前初版变成了：

> 全高中数学、多模态答疑、教案、整卷组卷、错题本、长期记忆、文档输出平台。

按群通知的 8 月 20 日截止时间，目前不足三周。继续按现有范围开发，很容易出现所有功能都有流程图，但没有一个功能真正跑通。

---

### 2. 主次关系反了

赛题评分核心是：

- 数据结构化；
- 自适应测评；
- 错因归因；
- 掌握度计算；
- 学习计划；
- 可解释性。

而当前文档大量篇幅用在：

- BGE 768 维；
- Milvus/Qdrant；
- HNSW；
- Subword；
- TopK；
- PDF/Word/LaTeX；
- 高考试卷排版。

这些可以作为技术说明，但并不能直接证明诊断准确。

评委更可能追问：

> 为什么这道题答错就判断为“余弦定理使用条件错误”？  
> 下一题为什么出这一道？  
> 掌握度 62 分是怎么算出来的？  
> 计划为什么先补这个知识点？

当前设计还没有充分回答这些问题。

---

### 3. RAG 不能代替诊断规则

当前初版基本思路是：

```text
题目向量化
→ 找相似题
→ 交给 LLM 推理
```

这适合答疑，却不足以完成稳定诊断。

更合理的分工应当是：

```text
结构化数据库
负责题目标签、知识点关系、错因和诊断规则

工作流条件分支
负责自适应选题和状态推进

RAG
负责检索教材解释、例题和补弱资源

LLM
负责自然语言追问、解析和报告生成
```

尤其是诊断结论，不能完全让 LLM 自由判断，否则不同运行之间可能产生不同结果。

---

### 4. “Subword 分词”不是当前重点

队友方案中写了：

```text
Subword 分词 → 词向量化 → 向量数据库
```

实际上 Subword 通常是嵌入模型内部完成的。开发时更重要的是：

- 怎样划分语义 Chunk；
- 每个 Chunk 带什么元数据；
- 如何与知识点 ID、题型 ID、错因 ID 对齐。

而且“整章或整单元一个 Chunk”粒度过大。

对本赛题更适合：

| 内容 | 推荐粒度 |
|---|---|
| 定理和公式 | 一个知识点一个 Chunk |
| 解题方法 | 一种方法一个 Chunk |
| 典型例题 | 一题一个 Chunk |
| 测评题 | 一题一个结构化记录 |
| 错因 | 一个具体错误一个记录 |
| 诊断规则 | 一个触发条件一个记录 |

---

### 5. 组卷材料内部存在冲突

设计文档中写的是：

- 单选 8
- 多选 4
- 填空 4
- 解答 6

合计是 **22 题**，但文字写成“19 题”。

另一份组卷 Prompt 写的是：

- 单选 8
- 多选 3
- 填空 3
- 解答 5

合计是 **19 题**。

难度比例也不一致：

- 架构文档：50% / 30% / 20%
- Prompt 手册：70% / 20% / 10%

因此当前组卷内容仍是概念稿，不能直接当成最终规则。Prompt 手册本身只是生成提示词，并不是可验证的组卷算法。`AGMATG_高中数学智能诊断Agent_设计文档.md` `高中数学智能组卷Prompt提示词手册.docx`

### 6. 平台关系需要明确

文档同时写了：

## 四、建议把四个功能重新定位

你现在设想的是：

1. 知识点诊断
2. 高考试卷组卷
3. 学情规划
4. 教案制作

为了与赛题对齐，建议改成：

### 核心能力一：解三角形知识诊断

必须完整实现。

包括：

- 学生画像采集；
- 初始题选择；
- 动态难度调整；
- 多轮错因追问；
- 知识点掌握度；
- 诊断证据。

### 核心能力二：个性化学习规划

必须完整实现。

包括：

- 当前分数和目标分；
- 可投入时间；
- 薄弱项优先级；
- 1-4 周计划；
- 每周练习和复测安排。

### 辅助能力三：个性化练习包

把“高考整卷组卷”收缩成：

> 根据学生薄弱知识点生成一份解三角形专项练习。

例如：

- 基础巩固 5 题；
- 同类变式 3 题；
- 综合提升 2 题；
- 带答案和错因提示。

这样既利用已有组卷思路，又直接服务于诊断结果。

### 辅助能力四：补弱学案 / 教师复核报告

把泛化的“教案生成”改成：

- 学生补弱学案；
- 教师端诊断复核报告；
- 对应知识点教学建议。

这比生成一份普通课堂教案更贴近评分要求。

题目解析和错题本不必单独作为大功能，可以作为诊断工作流内部节点。

## 二、需要修正的几个判断

### 1. “现在基本没人用 RAG”不准确

过时的主要是这种固定流水线：

```text
用户问题
→ 单次向量检索
→ TopK 拼接
→ LLM 回答
```

检索本身并没有消失。现在更常见的演进方向是让模型主动决定：

- 是否需要搜索；
- 用关键词还是语义搜索；
- 搜索哪一类资料；
- 是否继续追查；
- 打开完整文档还是只读取片段。

近期研究通常将其称为 Agentic Retrieval 或 Agentic RAG，其核心变化是由模型参与检索决策，而不是取消检索。([arXiv](https://arxiv.org/abs/2605.05538?utm_source=chatgpt.com))

所以更准确的意见应当是：

> 不需要把传统向量 RAG 作为系统主干。对于体量很小、结构明确的赛题数据，应以结构化题库和诊断规则为主，由 Agent 按需调用全文搜索或语义搜索工具。

本赛题只有一个章节、约 80 道题。完全可以先使用 PostgreSQL、SQLite 或 JSON 存储：

```text
题目ID
知识点ID
题型ID
错因ID
难度
答案
诊断条件
前置知识
后续推荐题
```

这些字段用普通查询比向量检索更准确、更可解释。教材和讲解资料才适合保留检索工具。

### 2. “后期必须微调甚至从头训练”也过于绝对

从头训练基础模型对这个产品几乎没有现实必要。即使进入商业化阶段，更合理的顺序通常也是：

```text
通用模型 + 结构化数据 + 工具调用
→ 积累真实交互数据
→ 建立评测集
→ Prompt和Harness优化
→ 小规模LoRA/SFT或蒸馏
→ 必要时本地部署
```

微调只能解决某些稳定行为，例如：

- 错因分类；
- 教育语言风格；
- 诊断报告格式；
- 特定数学步骤判定。

它无法替代题库、规则、学生状态管理和可解释证据。

本地开源模型的优势确实包括数据控制和可定制性，但“本地必然更经济、更安全”也不成立。本地部署还需要计算资源、运维、权限隔离、日志安全和版本管理。对于比赛 Demo，可以先用能力更稳定的 API 模型；正式产品再根据合规要求切换到私有部署。

### 3. Dify 没有过时，但不一定适合承担全部系统

Dify 当前仍然定位为 Agentic Workflow、知识管道、模型管理和工具编排平台，也支持云端、VPC 和自托管部署。([Dify](https://dify.ai/?utm_source=chatgpt.com))

它的问题不是“旧”，而是：

- 状态复杂时调试不够直观；
- 自适应循环容易形成庞大的可视化连线；
- 学生长期状态、教师管理和复杂前端仍需要外部后端；
- 版本控制和自动测试不如代码方案自然。

Pi 则是一个极简的终端编码 Agent Harness，核心面向编码工作流，可通过扩展、Skills 和 Prompt 模板定制；官方说明中甚至明确不默认提供子 Agent 和计划模式。([Pi](https://pi.dev/?utm_source=chatgpt.com))

因此，Pi 更适合：

- 帮你开发这个系统；
- 验证 Harness、Skill 和工具设计；
- 做单用户实验原型。

它不适合直接充当多用户教育产品后端。要支持登录、学生会话、教师端、历史数据和权限，你仍然要自己补齐大量基础设施。

最合理的使用方式是：

> 用 Pi/Codex 类 Harness 辅助开发；产品运行时采用一个轻量中心后端，内部实现自己的诊断 Agent。

### 核心数据层

建议分成三类数据。

第一类是确定性业务数据：

- 题库；
- 知识点树；
- 题型库；
- 错因库；
- 诊断规则；
- 题目之间的先后关系。

使用关系数据库或 JSON，不需要向量数据库。

第二类是学生记忆：

- 解题方法偏好；
- 历史测评轨迹；
- 当前学习计划完成度。

第三类是教材和解释资源：

- 课件；
- 概念讲解；
- 例题解析；
- 教学建议。

这部分可以提供关键词搜索、全文搜索或可选的语义检索，由 Agent 主动调用。

## 四、记忆系统怎么设计更可靠

你提出“先划分 ABCD 四种学生，再逐步形成专属画像”，这个思路可以使用，但不宜把人永久归为四类。

更合适的方案是：

### 初始阶段：低样本先验

用少量诊断题得到一个粗略起点，例如：

- A：概念基础薄弱；
- B：概念掌握但方法迁移弱；
- C：方法掌握但计算或表达不稳定；
- D：基础较好，需要综合提升。

这些类别只用来初始化，不作为最终标签。

### 后续阶段：连续画像

学生画像使用连续数值，例如：

```json
{
  "正弦定理识别": 0.82,
  "余弦定理应用": 0.57,
  "边角关系转换": 0.41,
  "分类讨论意识": 0.29,
  "计算稳定性": 0.73,
  "提示依赖度": 0.66
}
```

每次交互后更新，不断摆脱最初的四类先验。

你说的“正交题目”更准确的表达应当是：

> 选择区分不同能力维度、属性相关性较低、信息增益较高的诊断题组。

例如第一组题分别测：

- 概念识别；
- 公式选择；
- 运算执行；
- 分类讨论；
- 图形建模。

它们不需要在严格数学意义上正交，只需要尽可能减少重复测量。

### 不建议记录的内容

游戏偏好、日常习惯、性格等信息，除非学生主动提供并明确用于学习计划，否则容易产生无依据推断，也与赛题关系较弱。

真正有价值的教育记忆是：

- 学生习惯先画图还是先列式；
- 是否倾向套公式；
- 是否会主动检查多解；
- 遇到困难时需要何种提示；
- 是否能解释自己的步骤；
- 哪种反馈方式效果最好。

这才是能够形成个性化 Skill 的数据。

## 五、聊天式诊断怎样做得有创新

单纯做选择、判断、填空确实很难体现 Agent 价值，但只用一道综合大题也有问题：覆盖范围不足，诊断容易被偶然因素影响。

建议采用混合形式：

```text
3～4道短题完成能力定向
        ↓
选择一个最可疑的薄弱维度
        ↓
进入一道综合问题的对话式诊断
        ↓
要求学生逐步表达思路
        ↓
Agent根据步骤动态追问
```

例如：

1. 学生先判断应该使用正弦定理还是余弦定理；
2. Agent 问为什么；
3. 学生写出公式；
4. Agent 发现漏掉第二个可能解；
5. Agent 改变一个条件，追问解的个数是否变化；
6. 根据回答判断是概念问题、分类讨论问题还是计算问题。

这样既有结构化数据，也能观察思维过程。

## 六、多模态方案

拍照上传应该保留，这是实际使用中很重要的入口。

建议采用两级处理：

```text
题目印刷体
→ OCR / 公式识别
→ 文本模型处理

手写步骤、几何图形、复杂版面
→ 原生视觉语言模型
→ 必要时OCR结果作为辅助
```

你提到的模型名称可能记错了。目前 Moonshot 官方发布的是 **Kimi K3**，不是 Kimi H3；官方模型说明中包含原生视觉理解、长上下文和工具调用能力。([Kimi API Platform](https://platform.kimi.ai/docs/models?utm_source=chatgpt.com))

但比赛中没有必要绑定单一模型。应该定义统一模型接口，方便在：

- 云端多模态模型；
- PaddleOCR/PaddleOCR-VL；
- 本地视觉模型；
- 文本推理模型

之间替换和对比。

## 七、题目生成要受控

对于正式诊断，建议以官方题库和人工整理题为主，不让模型自由生成用于评分的核心题目。

模型生成适合用于：

- 同构变式题；
- 数值替换题；
- 补充练习；
- 追问题；
- 讲解示例。

生成后必须经过：

```text
模板约束
→ 符号计算或程序求解
→ 答案一致性检查
→ 难度和知识点检查
→ 才允许给学生使用
```

几何题可以专门做一个参数化生成 Skill：

- 由模板生成点、边、角参数；
- 使用 Python、TikZ 或 SVG 绘图；
- 自动计算标准答案；
- 验证三角形合法性。

这样比要求大模型直接“想一道带图题并画出来”稳定。

你的反馈可以凝练成下面这段，发给队友会更准确：

### 核心原则

**结构化数据是主干。**

知识点 ID、题型 ID、错因 ID、前置关系、难度和诊断规则均应进入关系数据库或图数据库。

**Agent 负责动态决策。**

Agent 决定：

- 当前还缺什么诊断证据；
- 下一道题测哪个能力；
- 是否需要追问；
- 应调用哪种判题工具；
- 是否需要检索教学资料；
- 怎样更新学生画像。

**检索是工具，不是系统中心。**

教材讲解、例题和长文资源仍可使用全文检索或语义检索，但不应让向量相似度承担诊断逻辑。

**模型可替换。**

商业系统需要统一模型网关，允许：

- 云端强模型用于早期验证；
- 本地开源模型用于私有化部署；
- 专用微调模型用于错因分类、步骤评分等高频任务；
- 多模态模型用于题目和手写过程理解。

# 一、近期 Harness 工程形成的共识

## 1. Harness 不等于多 Agent 框架

Anthropic对 Harness 的工程定义，本质上是将模型变成 Agent 的运行系统：处理输入、组织上下文、调用工具、管理状态并返回结果。评估 Agent 时，实际评估的是“模型和 Harness 的组合”，不能只测模型。([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents?utm_source=chatgpt.com))

一个生产级 Harness 至少包含：

```text
模型适配
+ 状态管理
+ 上下文编译
+ 工具调度
+ 执行控制
+ 记忆管理
+ 安全边界
+ 轨迹记录
+ 评测与回放
```

“几个 Agent 互相聊天”只是可选编排模式，不是 Harness 的核心。

## 2. 简单、可组合比复杂框架更可靠

Anthropic总结大量产业项目后发现，成功系统通常采用简单、可组合的模式，而不是一开始建立复杂多 Agent 框架。([Anthropic](https://www.anthropic.com/engineering/building-effective-agents?utm_source=chatgpt.com))

Google ADK 2.0 的设计方向也相同：将可预测的确定性工作流，与需要模型探索的 Agent 步骤混合，而不是把所有控制权交给 LLM。([Google 开发者博客](https://developers.googleblog.com/en/why-we-built-adk-20/))

因此，本项目不应让模型决定所有事项。

适合交给确定性代码的内容：

- 保存笔迹；
- 识别区域调度；
- 数学等价性校验；
- 题目约束检查；
- 学生状态更新；
- 权限和数据隔离；
- 诊断置信度阈值；
- 任务暂停与恢复。

适合交给模型的内容：

- 理解学生当前意图；
- 判断解题思路；
- 生成追问；
- 解释错因；
- 选择合适的反馈表达；
- 在若干合法动作之间做决策。

## 3. 状态必须独立于上下文窗口

Google近期的长周期 Agent 工程强调，应使用持久化状态模式和事件驱动恢复，而不是把大量 JSON 或完整聊天记录塞进向量数据库。([Google 开发者博客](https://developers.googleblog.com/build-long-running-ai-agents-that-pause-resume-and-never-lose-context-with-adk/?utm_source=chatgpt.com))

OpenAI和Anthropic也都将上下文压缩、持久记忆和会话状态分离视为长时间 Agent 的基本能力。([OpenAI Developers](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction?utm_source=chatgpt.com))

这意味着：

```text
学生状态 ≠ 对话历史
学生记忆 ≠ 向量库中的聊天记录
Agent会话 ≠ 模型上下文窗口
```

学生画像必须是应用数据库中的正式业务状态。

# 二、类似教育产品给出的关键经验

## 1. MATHia：必须分析步骤，不只分析答案

Carnegie Learning 的 MATHia 已运行二十多年。它的关键经验是：

- 观察学生每一步操作；
- 判断使用了哪种策略；
- 定位具体在哪一步出错；
- 只补学生尚未掌握的离散技能；
- 根据解题路径提供即时提示。

MATHia明确指出，只看最终答案无法判断学生是完全不会，还是只在四个步骤中的一个步骤出错。([卡内基学习](https://www.carnegielearning.com/blog/mathia-ai))

这直接支持你的草稿本思路：**笔迹过程本身才是产品的重要数据资产。**

## 2. ALEKS：学生画像应是知识状态，不是简单人格分类

ALEKS以 Knowledge Space Theory 为基础，通过知识之间的先后依赖，估计学生已经掌握什么、最适合接着学习什么。([aleks.com](https://www.aleks.com/about_aleks/knowledge_space_theory?utm_source=chatgpt.com))

所以你提出的 A/B/C/D 学生类型可以作为冷启动先验，但不能成为长期核心模型。

长期状态应该是：

```text
学生 × 知识点 × 题型 × 错因 × 解题策略
```

而不是永久把学生归入某个固定人格类别。

## 3. Khanmigo：结构化学习历史比原始对话更有效

Khan Academy 在 2025-2026 年间对超过 1500 万次辅导会话进行了产品实验，结果很有参考价值：

- 加入近期答题表现，下一题正确率提高 3.4%；
- 加入未掌握的前置技能信息，提高 2.7%；
- 直接加入完整会话日志，最初没有显著改善；
- 将日志提炼成更易理解、与教学相关的信息后，效果才改善；
- 额外提供更多相关题型样例和内容链接，未产生显著提升。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

这说明：

> 产品壁垒不在于把更多资料、聊天和例题全部塞给模型，而在于提炼出准确的结构化学习状态。

Khanmigo还专门使用数学验证系统检查计算，并通过预检查判断是否真的需要调用数学 Agent，从而降低延迟和成本。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

## 4. 成熟系统关注“下一题能否独立完成”

Khanmigo采用的重要指标不是“用户是否喜欢当前回答”，而是：

> 辅导结束后，学生能否在没有 AI 帮助的情况下正确完成下一道同技能题。

这比单纯测回复正确率更适合作为本系统的核心产品指标。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

# 三、最简洁的数学抽象

整个系统可以抽象成一个**事件驱动的部分可观测控制系统**。

学生真实知识状态不可直接观察：

$$
x_t=
(\text{知识掌握度},
\text{错因概率},
\text{策略偏好},
\text{提示依赖},
\text{认知负荷})
$$

系统可以观察到：

$$
o_t=
(\text{笔迹},
\text{数学表达式},
\text{步骤变化},
\text{作答时间},
\text{对话},
\text{求助行为})
$$

系统可以执行：

$$
a_t\in
\{
等待,\ 识别,\ 校验,\ 追问,\ 提示,\ 讲解,\ 换题,\ 复测
\}
$$

状态更新为：

$$
x_{t+1}=F(x_t,o_t,a_t)
$$

选题与干预目标可以概括为：

$$
a_t^*=
\arg\max_a
\left[
\mathbb E(\text{学习增益})
+\lambda I(\text{知识状态};\text{新观察})
-\alpha\text{打断成本}
-\beta\text{答案泄漏}
-\gamma\text{推理成本}
\right]
$$

这里有两个不同目标：

- **诊断阶段**更重视信息增益；
- **教学阶段**更重视学习增益。

这样就能解释为什么某些时候系统应该继续追问，有时应该提示，有时应该保持安静。

# 四、建议采用“三循环架构”

## 1. 感知循环：毫秒到秒级

负责：

- 接收笔迹；
- 分割书写区域；
- 识别文字和公式；
- 更新当前草稿状态；
- 发现新增或修改步骤。

它不负责决定教学策略。

## 2. 辅导循环：数秒到分钟级

负责：

- 校验当前步骤；
- 判断错因；
- 决定是否反馈；
- 选择追问或提示；
- 选择下一题。

这是 Tutor Agent 所在的主要循环。

## 3. 学习循环：天到周级

负责：

- 更新知识掌握状态；
- 统计错误变化；
- 调整学习计划；
- 生成教师报告；
- 安排复测；
- 分析长期迁移效果。

三个循环使用不同数据、不同延迟要求，也不应由一个大 Prompt 全部承担。

# 六、草稿本应如何实现

你的“停笔一段时间后主动识别”方向成立，但需要拆成两件事：

> 停笔触发识别，不等于停笔立即触发教学反馈。

## 1. 不要只保存截图，必须保存原始笔迹

浏览器可以保存每条 stroke：

```json
{
  "stroke_id": "s_1042",
  "points": [
    {"x": 412.4, "y": 261.8, "t": 0, "pressure": 0.42},
    {"x": 414.1, "y": 263.0, "t": 12, "pressure": 0.51}
  ],
  "tool": "pen",
  "region_id": "r_18"
}
```

原始笔迹包含：

- 书写顺序；
- 笔画轨迹；
- 停顿时间；
- 涂改关系；
- 压力和速度；
- 公式各符号之间的空间关系。

在线手写识别将书写视为一系列轨迹，而不是单张静态图片。Google 的数字墨水研究和 MathWriting 数据集都采用这种表示；MathWriting包含 23 万个人工书写公式和 40 万个合成样本。([谷歌研究](https://research.google/blog/a-return-to-hand-written-notes-by-learning-to-read-write/?utm_source=chatgpt.com))

所以：

```text
原始 stroke 是主数据
局部截图是识别辅助数据
```

## 2. 使用局部脏区域，而不是反复上传整页

每次书写后只标记发生变化的区域：

```text
笔抬起
→ 计算 dirty bounding box
→ 等待约 700～1200 ms
→ 合并相邻笔画
→ 只识别该区域
```

用户继续书写时取消本轮请求。

这能显著降低：

- 图像传输量；
- OCR重复计算；
- 多模态模型成本；
- 旧内容被反复误识别的问题。

## 3. 采用三级识别

### 一级：专用 OCR/公式模型

PaddleOCR 的 PP-FormulaNet 系列支持复杂印刷公式和手写公式，并可输出 LaTeX。PaddleOCR-VL则更适合复杂文档、表格、公式、图表和整页布局解析。([GitHub](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/index/index.en.md?utm_source=chatgpt.com))

建议分工：

```text
单个公式或一行推导
→ PP-FormulaNet

拍照上传整张试卷、复杂版面
→ PaddleOCR-VL / PP-Structure

文字、公式和图形混合且语义不确定
→ 多模态大模型
```

### 二级：数学上下文纠错

OCR可能将：

```text
sin A
```

识别成：

```text
s in A
```

此时可结合：

- 当前题目；
- 上一步公式；
- 知识点范围；
- 合法符号集合；
- 学生笔迹轨迹；

进行候选重排。

### 三级：多模态模型裁决

只有以下情况才调用较强 VLM：

- OCR置信度低；
- 含有几何图形；
- 多行推导关系复杂；
- 笔迹和公式候选冲突；
- 需要理解圈画、箭头和旁注。

不能让 VLM 成为每次停笔都必经的路径。

## 4. 建立“步骤图”，不要只生成一段 LaTeX

内部表示建议是：

```text
Stroke
  ↓
Symbol
  ↓
Expression AST
  ↓
Solution Step
  ↓
Solution Graph
```

一个步骤对象可以是：

```json
{
  "step_id": "step_4",
  "latex": "a^2=b^2+c^2-2bc\\cos A",
  "ast": {},
  "source_strokes": ["s_100", "s_101", "s_102"],
  "derived_from": ["step_2"],
  "confidence": 0.94,
  "verification": {
    "valid": true,
    "method": "cosine_law"
  }
}
```

这样系统可以：

- 在原笔迹上标出具体错误；
- 识别学生修改了哪一步；
- 回放整个解题过程；
- 判断同一道题用了哪条解法路径；
- 给教师展示“错误发生点”，而不是只显示最终答案。

这会成为比普通拍照搜题更明显的产品差异。

# 七、反馈不应由“静止时间”直接决定

推荐采用两级触发。

## 识别触发

满足任一条件即可：

- 停笔达到防抖时间；
- 新起一行；
- 写出等号或结论符号；
- 点击“检查此步”；
- 提交答案。

## 教学反馈触发

还需要经过 Tutor Policy：

```text
识别置信度足够？
数学验证结论足够确定？
学生当前是否仍在主动书写？
错误是否会导致后续全部失效？
是否已经连续出现同类错误？
此时反馈会不会泄露答案？
```

正常情况下，系统可以静默理解学生正在写什么，却不立刻打断。

比较合理的策略是：

- 明显笔误：等待学生自行修正；
- 核心概念错误：及时追问；
- 中间计算错误：允许继续一两步后再提示；
- 学生卡住较久：给低级别提示；
- 学生主动检查：立即反馈；
- 最终提交：完整诊断。

即时识别与即时干预是两种不同能力。

# 八、Harness 内部结构

## 1. 事件日志

所有行为首先写成不可变事件：

```text
StrokeAdded
StrokeDeleted
RegionRecognized
ExpressionConfirmed
StepVerified
HintRequested
TutorResponded
MasteryUpdated
TeacherCorrected
```

当前状态由事件重放得到。

优点是：

- 可以恢复中断会话；
- 可以回放学生解题；
- 可以比较不同模型版本；
- 可以重新运行诊断算法；
- 可以追溯某个结论的依据；
- 教师修改后可重新计算画像。

## 2. 状态归约器

将事件归约为当前状态：

```text
SessionState
├─ 当前题目
├─ 当前草稿
├─ 结构化步骤图
├─ 已确认错误
├─ 当前诊断假设
├─ 学生知识状态
└─ 可执行动作集合
```

## 3. Context Compiler

模型调用前，不直接提供完整历史，而是组装最小上下文：

```text
当前题目
+ 最近相关步骤
+ 已验证结论
+ 可能错因
+ 学生相关掌握状态
+ 当前允许调用的工具
```

Khanmigo的实验已经表明，结构化学习信号比直接加入完整原始日志更有效。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

## 4. Skill Registry

Skill 不应只是自然语言 Prompt，而应有明确契约：

```yaml
name: verify_math_step
input_schema:
  previous_step: Expression
  current_step: Expression
output_schema:
  valid: boolean
  error_type: string
  evidence: array
preconditions:
  - recognition_confidence >= 0.8
timeout_ms: 2000
fallback:
  - numerical_check
  - llm_review
eval_suite: verify_step_v3
```

推荐的核心 Skills：

- `recognize_ink_region`
- `parse_math_expression`
- `verify_math_step`
- `classify_misconception`
- `select_diagnostic_probe`
- `generate_scaffolded_hint`
- `retrieve_teaching_resource`
- `update_student_state`
- `generate_practice_set`
- `build_learning_plan`
- `compose_teacher_report`

## 5. Verifier Gate

模型提出动作后，必须经过门控：

```text
模型建议“指出错误”
        ↓
错误结论是否经过验证？
        ↓
提示是否泄露最终答案？
        ↓
是否符合当前提示等级？
        ↓
允许输出
```

数学系统不能仅依靠 LLM 自我反思来保证正确性。

# 九、学生记忆系统

建议划分三层。

## 第一层：不可变学习事件

保存学生实际发生过什么：

- 做了什么题；
- 写了哪些步骤；
- 请求过几次提示；
- 哪一步被修改；
- 教师是否纠正诊断。

这是证据层。

## 第二层：结构化学生状态

例如：

```json
{
  "knowledge": {
    "正弦定理适用条件": 0.82,
    "余弦定理变形": 0.64,
    "SSA多解讨论": 0.27
  },
  "misconceptions": {
    "忽略三角形多解": 0.73,
    "边角对应错误": 0.18
  },
  "strategy": {
    "先画图": 0.76,
    "偏好正弦定理": 0.61,
    "检查意识": 0.22
  },
  "interaction": {
    "hint_dependency": 0.34,
    "preferred_hint_level": 2
  }
}
```

比赛初期可使用专家先验加贝叶斯更新，数据量积累后再训练知识追踪模型。BKT以隐状态表示学生是否掌握某项技能，知识追踪本身就是长期智能辅导系统的基础任务。([ERIC](https://files.eric.ed.gov/fulltext/EJ1115329.pdf?utm_source=chatgpt.com))

## 第三层：语义记忆

只保存难以放进固定字段、但与教学有关的信息，例如：

- 学生习惯先列式后补图；
- 对反问式提示容易焦虑；
- 更容易理解几何解释而非代数推导；
- 某次错误来自题意误读而不是知识缺陷。

语义记忆不应覆盖结构化状态。

## 不建议动态生成“每个学生的可执行 Skill”

这是你之前思路中需要收紧的部分。

为每位学生自动生成并运行新的 Skill 会造成：

- 行为不可控；
- 难以评测；
- 难以版本管理；
- 安全边界模糊；
- 同一学生不同时间产生矛盾策略。

更适合的是：

```text
全局稳定 Skills
+ 每个学生的策略参数
+ 个性化上下文
```

例如不是生成一个新 Skill，而是调整：

```json
{
  "feedback_style": "socratic",
  "intervention_delay": "long",
  "preferred_representation": "geometry",
  "max_hint_level": 2
}
```

# 十、框架选型比较

| 方案 | 适合程度 | 判断 |
|---|---:|---|
| Dify | 中 | 适合早期演示和内容运营，不适合承载实时笔迹、复杂状态和核心诊断 |
| Pi | 低，作为运行后端 | 它是极简终端编码 Harness，适合开发工具和架构参考，不是多租户教育运行时 |
| OpenAI Agents SDK | 中高 | 简洁、Tracing 和工具循环成熟，但产品会更依赖特定模型生态 |
| Google ADK 2.0 | 高 | 代码优先，支持确定性工作流和 Agent 混合；当前版本变化较快 |
| Microsoft Agent Framework | 中高 | Session、Context Provider、Middleware、MCP较完整，但仍较新 |
| LangGraph | 高 | 模型中立、持久状态、流式、HITL、确定性与Agent步骤混合较成熟 |
| Temporal | 后期高 | 适合商业化后的长周期可靠执行，目前加入会增加开发成本 |

Pi官方定位就是极简终端编码 Harness，核心通过 Extensions、Skills 和 Prompt Templates 扩展，同时默认不提供子 Agent 和计划模式。它适合作为开发和实验工具，不适合直接承担学生、教师、权限、数据、实时输入和持久会话。([Pi](https://pi.dev/docs/latest?utm_source=chatgpt.com))

LangGraph提供持久执行、流式输出、人工介入和状态保存，并允许把确定性节点与模型节点放入同一个图中，比较符合当前需求。([Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview))

### 最终选择

**当前阶段：**

```text
自己的领域 Harness
        构建在
LangGraph + FastAPI + PostgreSQL
```

LangGraph只负责编排会话级、教学级动作；实时笔迹处理不经过 LangGraph，避免把高频事件塞进 Agent 图。

**商业扩展阶段：**

当出现跨天任务、批量生成、教师审批、异步报告、长周期计划时，再引入 Temporal 或等价的 Durable Execution 层。

# 一、创新不能是功能堆叠

OCR、RAG、知识图谱、多 Agent、本地模型、Dify、LangGraph、自动组卷，这些都属于技术组件，本身很难构成有说服力的创新。

真正能拿分的创新需要同时满足四个条件：

1. 解决现有产品尚未很好解决的问题；
2. 能形成清晰的技术机制；
3. 能通过实验验证；
4. 能迁移到更大产品，而非只适用于一次演示。

因此不应宣称十几个“创新点”，建议形成：

> 3 个核心创新 + 3 个支撑创新。

所有功能围绕同一条主线展开。

# 二、核心创新主线

现有多数学习产品主要观测：

```text
题目 → 最终答案 → 对错
```

本项目计划观测：

```text
题目
→ 笔迹和修改过程
→ 数学表达式
→ 解题步骤
→ 解题策略
→ 错误机制
→ 知识状态
→ 教学干预
```

项目核心创新可以概括为一句话：

> 从“基于答案的学习诊断”，升级为“基于解题过程的可验证认知诊断”。

这条主线能够自然串联草稿本、多模态、记忆、自适应出题、错因分析、学习规划和教师端。

# 三、三个核心创新

## 核心创新一：草稿本原生的过程感知交互

### 现有问题

普通 AI 辅导产品主要依赖聊天输入。数学学习中，学生实际思维通常体现在：

- 画图；
- 列式；
- 推导；
- 涂改；
- 跳步；
- 回退；
- 不同公式之间的转换。

要求学生把这些内容重新描述成文字，会丢失大量信息。

### 本项目方案

学生直接在数字草稿本中书写，系统保存的不是单张截图，而是连续笔迹事件：

```text
Stroke
→ Symbol
→ Expression
→ Solution Step
→ Solution Graph
```

也就是：

```text
笔画
→ 数学符号
→ 数学表达式
→ 解题步骤
→ 解题过程图
```

每一个识别出的步骤都能映射回原始笔画。

例如系统发现：

```latex
\frac{a}{\sin A}=\frac{b}{\sin B}
```

后续学生写出错误变形时，可以知道：

- 错误发生在哪个步骤；
- 来源于哪几笔；
- 是识别错误还是数学错误；
- 学生之后是否主动修改；
- 该错误影响了哪些后续步骤。

PaddleOCR 的公式识别流水线已经支持印刷公式、复杂公式和手写公式转 LaTeX，因此底层识别能力可以复用，创新重点应放在识别后的步骤建模上。([PaddleOCR](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/formula_recognition.html))

### 真正创新的部分

“可以手写”不算创新，以下组合才算：

> 原始笔迹事件 + 数学步骤图 + 修改关系 + 学生认知状态更新。

### 可验证假设

> 与只使用最终答案相比，加入解题过程信息能够提高错因分类准确率和教师一致性。

实验可以设置：

- 基线 A：只看最终答案；
- 基线 B：看最终答案和静态截图；
- 实验组：看完整步骤轨迹。

指标：

- 错因分类准确率；
- 与教师诊断的一致率；
- 诊断置信度；
- 无法归因比例。

近期过程型知识追踪研究也明确指出，只依赖最终正确性会忽略解题过程中包含的数学能力信息，而引入过程信号可以提高预测性能和解释能力。([arXiv](https://arxiv.org/abs/2512.00311))

## 核心创新二：静默感知、选择性干预

### 现有问题

“停笔一秒就弹出反馈”看起来智能，实际很容易：

- 打断学生思考；
- 泄露答案；
- 让学生形成提示依赖；
- 把正常试错误判成知识错误；
- 降低书写流畅性。

### 本项目方案

将“识别”和“反馈”彻底分离。

系统可以持续识别学生正在写什么，但不一定立即说话。

```text
停笔
→ 局部识别
→ 数学验证
→ 判断学生是否仍在思考
→ 评估是否需要介入
→ 等待 / 追问 / 提示 / 纠错
```

Tutor Agent 的动作集合为：

$$
a_t\in
\{
\text{等待},
\text{确认},
\text{追问},
\text{轻提示},
\text{强提示},
\text{讲解},
\text{换题}
\}
$$

决策目标可以抽象为：

$$
a_t^*=
\arg\max_a
\left[
G_{\text{learn}}
+\lambda G_{\text{info}}
-\alpha C_{\text{interrupt}}
-\beta C_{\text{leak}}
-\gamma C_{\text{error}}
\right]
$$

其中：

- $G_{\text{learn}}$：预计学习增益；
- $G_{\text{info}}$：预计诊断信息增益；
- $C_{\text{interrupt}}$：打断学生的成本；
- $C_{\text{leak}}$：泄露答案的风险；
- $C_{\text{error}}$：系统误判风险。

### 干预示例

| 学生状态 | 系统动作 |
|---|---|
| 刚写完一步，仍在继续书写 | 静默等待 |
| 出现轻微计算错误，但整体思路正确 | 暂不打断 |
| 错误导致后续推导全部失效 | 进行低级别追问 |
| 连续出现同类错误 | 提升干预级别 |
| 长时间停顿 | 提供方向提示 |
| 主动点击“检查此步” | 立即反馈 |
| OCR 置信度低 | 请求确认，不做数学诊断 |

Khanmigo 的大规模实验将“是否过早给出答案”作为防护指标，并发现只分析学生已经完成的数学过程、不继续代算剩余步骤，可以显著减少答案泄漏。其核心效果指标也是辅导后学生能否独立完成下一道同技能题。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

### 可验证假设

> 选择性干预相较于每步即时纠错，能够减少打断和答案泄漏，同时提高下一题独立正确率。

指标：

- 下一题独立正确率；
- 单题平均打断次数；
- 提示依赖度；
- 过早给出答案比例；
- 学生主动修正比例；
- 平均响应延迟。

这一点有明确的教育价值，也有明显的交互创新。

## 核心创新三：可追溯的证据链诊断

### 现有问题

大量所谓“AI 学情报告”实际上是模型根据几道题生成的一段文字：

> 你的正弦定理掌握一般，余弦定理有待提高。

这种结论难以复核，也无法解释为什么得到该判断。

### 本项目方案

每个诊断结论必须形成完整证据链：

```text
原始笔迹
→ 识别表达式
→ 数学验证结果
→ 具体错误步骤
→ 错因候选
→ 追问结果
→ 诊断规则
→ 学生状态更新
```

例如：

```text
证据1：学生正确选择正弦定理
证据2：正确写出 a/sinA=b/sinB
证据3：求出 sinB 后直接得到唯一角度
证据4：追问“sinB相同时角B是否唯一”，学生回答“唯一”
------------------------------------------------
诊断：
正弦定理公式掌握；
反三角函数基本运算掌握；
SSA条件下三角形多解意识薄弱。
置信度：0.88
```

教师可以点击诊断结果，回到对应笔迹和追问。

### 技术模型

诊断对象不只是一个标签，而是：

```json
{
  "claim": "SSA多解讨论薄弱",
  "evidence": [
    "step_4",
    "probe_answer_2",
    "rule_SSA_03"
  ],
  "alternative_causes": [
    "反三角函数知识不熟"
  ],
  "confidence": 0.88,
  "status": "待复测确认"
}
```

### 真正创新的部分

知识点标签和错因标签已有大量产品使用。更有区分度的是：

> 诊断结论能够回溯到原始解题过程，并显式保留候选原因、不确定性和复测条件。

### 可验证假设

> 证据链诊断能够提高教师对系统诊断的认可率，并降低错误诊断无法纠正的风险。

指标：

- 教师诊断一致率；
- 教师平均复核时间；
- 教师修改率；
- 诊断可解释性评分；
- 复测后的诊断确认率。

# 四、三个支撑创新

## 支撑创新一：诊断与教学双目标的自适应选题

普通自适应系统通常按“答对升难、答错降难”运行，过于粗糙。

本项目应区分两个阶段：

### 诊断模式

目标是最大化信息增益：

$$
q_t^*=
\arg\max_q
I(Z;R_q\mid H_t)
$$

其中：

- $Z$ 是学生知识状态；
- $R_q$ 是学生对题目 $q$ 的响应；
- $H_t$ 是已有历史。

系统应选择最能区分当前多个诊断假设的题。

例如当前不能确定学生属于：

- 不会正弦定理；
- 不会边角对应；
- 遗漏多解。

下一题应专门区分这三个原因，而不只是随机再出一道中等题。

### 教学模式

目标改为最大化学习增益：

$$
q_t^*=
\arg\max_q
\left[
P(\text{可完成})
\cdot G(\text{掌握提升})
\right]
$$

既不能太简单，也不能超出学生当前可学习边界。

ALEKS 的知识空间理论将学生表示为一个“知识状态”，并利用内边界和外边界分别表示已经能够完成的高阶内容，以及当前准备学习的内容。其评估题目也按最大信息量选择，而不是固定顺序出题。([aleks.com](https://www.aleks.com/about_aleks/Science_Behind_ALEKS.pdf))

### 创新表达

不能说“我们首创自适应出题”，更准确的表述是：

> 将信息增益式诊断与学习增益式教学统一到同一教学策略引擎中，并使用过程证据动态切换目标。

---

## 支撑创新二：过程感知型学生数字模型

学生模型不应只包含：

```text
正弦定理掌握度：70%
```

建议拆成五个维度：

$$
S_t=(K_t,T_t,M_t,B_t,I_t)
$$

其中：

- $K_t$：知识点掌握状态；
- $T_t$：题型和解题策略状态；
- $M_t$：错因分布；
- $B_t$：行为过程特征；
- $I_t$：交互和提示偏好。

具体包括：

```text
知识掌握度
题型熟练度
错误机制
解题路径偏好
修改行为
检查意识
提示依赖
作答时间
迁移能力
自信程度
```

记忆系统分三层：

1. 原始事件：做过什么、写过什么；
2. 结构化学生状态：当前掌握和错误概率；
3. 教学语义记忆：更适合哪种解释方式、容易在哪类表达上卡住。

不建议自动给每个学生创建可执行 Skill。更稳定的方式是：

```text
共享 Skills
+ 个体状态
+ 个性化策略参数
```

OpenAI 的长期个性化实践也推荐把固定结构化字段与非结构化记忆备注结合，而不是只保存全部历史对话。([OpenAI Developers](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization?utm_source=chatgpt.com))

Khanmigo 的实验显示，向模型提供结构化的近期表现和未掌握前置技能，分别提高了下一题正确率；直接加入完整对话日志最初没有带来可测量提升。([Khan Academy Blog](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/))

### 创新表达

> 不只追踪“会不会”，还追踪“怎么做、怎么错、如何修正、需要何种帮助”。

## 支撑创新三：可迁移的 Chapter Package

可商业化系统不能每扩展一个章节就重新开发一套工作流。

每个章节应封装为统一内容包：

```text
Chapter Package
├─ 知识点与前置关系
├─ 题型体系
├─ 错因体系
├─ 题库
├─ 参数化题目模板
├─ 合法解题路径
├─ 步骤验证器
├─ 诊断规则
├─ 教学资源
├─ 学习规划模板
└─ 评测集
```

Harness 不关心当前是“解三角形”还是“函数”，它只读取章节包的统一接口。

例如：

```text
load_chapter("triangle_solving")
load_chapter("function")
load_chapter("derivative")
```

### 商业价值

这样产品扩展的主要成本从“重新开发系统”变成：

> 教研人员生产、审核和维护新的章节包。

这也是教师端和内容运营端存在的原因。

### 创新表达

Chapter Package 本身不是全新概念，但它能形成项目的规模化机制：

> 将教研知识、认知诊断规则和 Agent 工具封装为标准化、可验证、可版本化的学科能力包。

# 五、Harness 作为技术支撑，不应当作为主宣传创新

推荐的 Tutor Harness 结构是：

```text
事件日志
→ 状态归约
→ 上下文编译
→ 工具调用
→ 数学验证
→ 教学策略决策
→ 输出门控
→ 状态更新
```

具体由两部分组成：

### 确定性部分

- 笔迹保存；
- 公式解析；
- 数学等价性校验；
- 状态更新；
- 诊断规则；
- 权限；
- 事件重放；
- 输出约束。

### Agent 部分

- 理解学生思路；
- 生成追问；
- 区分候选错因；
- 选择教学表达；
- 在合法动作集合中做策略决策。

Anthropic的工程经验建议优先采用简单、可组合的模式，避免框架抽象掩盖实际 Prompt 和执行过程。([Anthropic](https://www.anthropic.com/engineering/building-effective-agents))

Google ADK 2.0 同样将确定性执行与开放式 Agent 推理分开：能够明确写成 A→B 的业务流程应使用确定性工作流，真正模糊的步骤才交给模型。([Google 开发者博客](https://developers.googleblog.com/why-we-built-adk-20/))

因此，“用了多 Agent”不应列入创新点。更有价值的说法是：

> 构建了教学确定性规则与生成式 Agent 协同的混合 Harness。

# 七、完整项目模型

可以将整个项目抽象为五个对象：

$$
\mathcal P=(C,Q,S,E,\Pi)
$$

其中：

- $C$：Content，学科内容和知识结构；
- $Q$：Question，题目及其合法解题路径；
- $S$：Student State，学生动态认知状态；
- $E$：Evidence，笔迹、步骤、对话和验证证据；
- $\Pi$：Tutor Policy，教学决策策略。

系统运行过程为：

$$
E_t=\operatorname{Observe}(\text{ink},\text{text},\text{behavior})
$$

$$
D_t=\operatorname{Diagnose}(E_t,C,Q,S_t)
$$

$$
A_t=\Pi(D_t,S_t)
$$

$$
S_{t+1}=\operatorname{Update}(S_t,E_t,A_t)
$$

对应产品语言就是：

```text
观察学生怎么做
→ 判断学生为什么这样做
→ 决定现在应不应该介入
→ 观察介入后的变化
→ 更新对学生的理解
```

产品价值可以进一步概括为：

$$
V=
O_p\times D_r\times I_e\times C_s
$$

- $O_p$：解题过程可观测性；
- $D_r$：诊断可靠性；
- $I_e$：教学干预有效性；
- $C_s$：内容扩展能力。

任何一项接近零，系统整体价值都会明显下降。

同样不建议主打：

### “ABCD 四类学生”

适合作为冷启动先验，但分类过于粗糙，容易显得缺乏科学性。

### “为每个学生生成独属 Skill”

难以验证、难以管理，工程风险较高。个性化策略参数更可靠。

### “AI 自动生成全部题目”

生成题的正确性和难度难以保证，应作为经验证的辅助生产能力。

### “停笔后立即反馈”

容易制造打断和提示依赖，应改成静默识别和选择性干预。

## 一、正确的产品目标形态

产品主体应当是：

> **聊天原生的自适应数学诊断与学习规划 Agent。**

学生通过连续对话完成：

```text
基本情况采集
→ 少量试探性题目
→ 根据回答动态追问
→ 区分具体错因
→ 更新知识状态
→ 选择下一道最有诊断价值的问题
→ 形成诊断报告
→ 生成学习计划
→ 后续复测与持续调整
```

核心界面应当是对话，而不是草稿本：

```text
┌──────────────────────────────┐
│ Agent：你目前数学大约多少分？ │
│ 学生：90 分左右               │
│                              │
│ Agent：先看一道正弦定理问题。 │
│ [题目卡片]                    │
│ [A] [B] [C] [D]              │
│                              │
│ 学生：B                       │
│                              │
│ Agent：你选择 B 的主要依据是？│
│ ①公式记忆 ②图形关系 ③计算结果 │
└──────────────────────────────┘
```

选择题、填空题、图片、公式和草稿只是对话消息中的不同内容类型。

## 二、“聊天式”不只是 UI，而是诊断方法

如果只是把普通题库放进聊天窗口里逐题发送，仍然不算真正的聊天式诊断。

聊天的价值在于系统可以根据上一轮回答主动形成新的诊断动作。

例如学生做错一道题，系统不应立即输出标准解析，而应继续问：

```text
你认为这道题应该使用正弦定理还是余弦定理？

你能先指出已知边对应的角吗？

求出 sin B 后，角 B 是否只有一种可能？

假如 B 是钝角，题目条件是否仍然成立？
```

不同回答会产生不同结论：

```text
公式写不出
→ 定理记忆问题

公式正确但边角对应错
→ 对应关系问题

能求出 sin B 但只取一个角
→ 分类讨论问题

步骤全部正确但最后数值错误
→ 计算稳定性问题
```

因此产品的核心不是“让 AI 看懂学生写了什么”，而是：

> **让 Agent 知道下一句话应该问什么，才能以最少轮次排除错误假设。**

## 三、草稿本应该降级为辅助工具

草稿本思路仍然有价值，但不能成为产品中心。

更合理的位置是聊天中的“可展开答题工具”：

```text
Agent 发题
    ↓
学生选择输入方式
├─ 直接输入答案
├─ 输入公式
├─ 拍照上传
└─ 打开草稿板
    ↓
OCR / 多模态模型识别
    ↓
识别结果作为一条聊天消息进入诊断流程
```

例如：

```text
学生在草稿板书写
        ↓
系统识别为：
a² = b² + c² - 2bc cos A
        ↓
聊天窗口：
“我识别到你使用了余弦定理，对吗？”
        ↓
学生确认
        ↓
Agent继续追问为什么选择余弦定理
```

这样草稿板服务于聊天式诊断，不会取代题目要求。

停笔识别也可以保留，但建议只做：

- 自动转录；
- 自动形成作答消息；
- 标记可能需要追问的步骤；
- 辅助判断学生的解题过程。

不应设计成持续弹出实时教学反馈，否则产品容易变成另一个方向的“智能作业本”。

## 四、重新定义项目模型

整个项目可以抽象成一个**对话式主动诊断系统**。

### 隐状态

学生真实掌握情况不可直接观察：

$$
z_t=
(K_t,T_t,M_t,C_t)
$$

其中：

- $K_t$：知识点掌握状态；
- $T_t$：题型与方法掌握状态；
- $M_t$：错因概率；
- $C_t$：学生当前的信心、负担和配合状态。

### 可观测信息

$$
o_t=
(\text{答案},\text{解释},\text{耗时},\text{修改},\text{提示使用},\text{图片或笔迹})
$$

### Agent 可执行动作

$$
a_t\in
\{
\text{提问},
\text{出题},
\text{追问理由},
\text{降低难度},
\text{增加变式},
\text{给提示},
\text{停止诊断}
\}
$$

### 决策目标

$$
a_t^*=
\arg\max_a
\left[
I(z;o_{t+1}\mid a)
+\lambda G_{\text{learn}}
-\alpha C_{\text{time}}
-\beta C_{\text{friction}}
\right]
$$

也就是选择：

- 最能缩小诊断范围的问题；
- 同时具有一定学习价值；
- 又不会让对话过长、过重。

这比“答对升难、答错降难”更符合真正的自适应诊断。

## 五、创新点也需要重新围绕聊天设计

之前提出的“过程感知、克制干预、步骤证据链”可以保留部分思想，但主创新应调整为以下方向。

### 核心创新一：假设驱动的诊断对话

Agent 不按照固定题单提问，而是维护多个候选诊断假设。

例如学生答错后：

```text
H1：正弦定理公式不会
H2：边角对应关系错误
H3：反三角函数求解错误
H4：遗漏 SSA 多解
H5：普通计算失误
```

Agent选择最能区分这些假设的下一句追问。

这比简单的“错了再出一道类似题”更有技术含量，也更符合少题量诊断的目标。

### 核心创新二：多轮错因消歧

一次错误不能直接对应一个错因标签。

系统应通过连续对话完成：

```text
初始错误
→ 候选错因集合
→ 针对性追问
→ 排除部分原因
→ 必要时发一题微型验证题
→ 得到最终诊断
```

诊断可以保留概率：

```json
{
  "SSA多解意识薄弱": 0.82,
  "反三角函数不熟": 0.13,
  "偶然计算失误": 0.05
}
```

这会比硬规则“一错即判定”科学得多。

### 核心创新三：对话中的最小充分测评

系统目标不是问得越多越好，而是寻找能够支持诊断结论的最小对话集合。

可以定义：

$$
\min N
$$

满足：

$$
P(z\mid o_{1:N})>\tau
$$

也就是在诊断置信度达到阈值后尽早停止，避免学生重复刷题。

这直接对应题目提出的“少量题目”和“轻量测评”。

### 核心创新四：可解释对话证据链

每个诊断结果都应关联：

- 哪道题；
- 学生怎样回答；
- Agent追问了什么；
- 学生怎样解释；
- 哪条诊断规则被触发；
- 是否仍需复测确认。

例如：

```text
诊断：SSA 情形分类讨论意识薄弱

证据：
1. 正确写出正弦定理；
2. 正确求得 sin B；
3. 直接认定 B 唯一；
4. 经追问后仍认为正弦值对应唯一角；
5. 在一道微型判断题中再次遗漏补角情况。
```

这才是题目所要求的“给出判断依据”。

### 核心创新五：长期对话记忆驱动规划

聊天不只用于一次测评。

长期系统应记住：

- 哪些知识点已经稳定掌握；
- 哪些结论只有一次证据；
- 哪些错因重复出现；
- 学生对哪种提示反应更好；
- 学习计划执行情况；
- 复测是否通过。

每次新对话都从之前的状态继续，而不是重新开始。

## 一、重新定义两者的关系

可以把系统分成三个平面：

### 1. 对话控制面

负责：

- 采集学生情况；
- 提出诊断问题；
- 决定下一步问什么；
- 要求学生解释选择；
- 发起局部草稿任务；
- 确认系统识别结果；
- 给出提示和学习规划。

这是赛题要求的聊天式主体。

### 2. 草稿观察面

负责提供聊天难以获得的证据：

- 学生先画图还是先列公式；
- 选择了正弦定理还是余弦定理；
- 边角对应是否正确；
- 是否主动标注已知条件；
- 是否意识到多解和分类讨论；
- 使用了哪条解法路径；
- 哪一步出现修改、停顿和回退。

### 3. 学生状态面

融合两个通道：

$$
e_t=e_t^{\text{dialogue}}\cup e_t^{\text{ink}}
$$

然后更新学生状态：

$$
S_{t+1}=\operatorname{Update}(S_t,e_t)
$$

因此完整循环是：

```text
Agent通过聊天提出诊断任务
        ↓
学生用文字、选项或草稿作答
        ↓
系统从草稿中提取方法与步骤证据
        ↓
Agent通过聊天确认或追问
        ↓
更新学生画像
        ↓
选择下一道题或下一句问题
```

这个结构完全符合聊天式要求，而且比普通“聊天框里逐题考试”更有区分度。

## 二、关键产品形态：草稿本是一种对话消息

不要把草稿本做成与聊天并列的另一个产品。应将它嵌入每轮对话。

例如：

```text
Agent：
请尝试解决这道题。你不用写完整答案，
先在草稿区画出图形，并标出已知边角关系。

[打开草稿本]

学生完成书写

学生消息：
[草稿缩略图]
系统识别：
- 标出了边 a、b
- 将角 A 对应到边 b，疑似对应关系错误
- 当前似乎准备使用正弦定理
识别置信度：0.76

Agent：
我看到你准备使用正弦定理。不过我不太确定
你标注的角 A 对应哪条边。你认为是哪一条？
```

这样每一次草稿输入都变成一个 **Ink Turn**：

```json
{
  "type": "ink_turn",
  "image": "rendered_region.png",
  "strokes": "...",
  "recognized_math": "...",
  "method_hypotheses": [
    {"method": "sine_law", "confidence": 0.76}
  ],
  "diagnostic_evidence": [
    {"type": "side_angle_mapping", "status": "uncertain"}
  ]
}
```

聊天仍是流程骨架，草稿则为聊天增加证据。

## 三、不需要让大模型直接理解矢量参数

你的技术担忧成立一半。

通用多模态大模型通常不适合直接接收：

```text
[(x1,y1,t1), (x2,y2,t2), ...]
```

然后稳定还原复杂数学表达。但系统没有必要这样设计。

应采用“双表示”：

```text
矢量笔迹：作为原始数据保存
渲染图像：作为主要识别输入
```

### 矢量笔迹的用途

矢量轨迹主要用于：

- 重绘；
- 撤销和修改；
- 确定书写顺序；
- 找到新增区域；
- 判断停顿和回退；
- 将识别结果映射回笔画；
- 后期训练在线识别模型。

### 图像的用途

将局部笔迹实时渲染为高分辨率 PNG，再交给：

- PaddleOCR 文字识别；
- PP-FormulaNet 手写公式识别；
- 多模态模型理解图形和整体语义。

PaddleOCR 官方公式识别流水线已经明确支持手写公式，并将其转换为机器可读表达。([PaddleOCR](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/formula_recognition.html?utm_source=chatgpt.com))

所以最现实的链路是：

```text
矢量笔迹
→ 定位最近修改区域
→ 局部光栅化
→ OCR / 公式识别
→ 多模态语义判断
→ 聊天确认
```

而不是：

```text
矢量坐标
→ 直接发送给LLM
→ 期待模型完全理解
```

## 四、矢量数学识别并非不存在

在线手写识别本身已经是成熟技术方向。

Google 的在线手写系统将输入表示为带时间戳的笔画点序列；MathWriting 数据集也专门保存在线数学笔迹，并以 InkML 形式提供轨迹和标准数学标签。([谷歌研究](https://research.google/blog/rnn-based-handwriting-recognition-in-gboard/?utm_source=chatgpt.com))

商业方案 MyScript iink 可以直接接收 stroke groups，并返回 LaTeX 数学表达式；它还能够输出结构化识别树。([MyScript 开发者](https://developer.myscript.com/docs/interactive-ink/2.0/web/rest/math-example/?utm_source=chatgpt.com))

因此准确说法应是：

> 在线数学笔迹识别已有成熟商业方案和研究数据，但高质量开源、可直接部署且适合中文高中数学场景的完整方案仍有限。

比赛阶段没必要自行训练矢量识别模型。可选两条路径：

| 路径 | 优点 | 问题 |
|---|---|---|
| MyScript iink | 直接处理轨迹，数学识别成熟 | 商业授权、外部依赖 |
| 矢量渲染 + PaddleOCR/VLM | 开源、容易集成、演示可控 | 丢失部分动态轨迹语义 |

推荐比赛阶段采用第二条，同时保留原始笔迹，为后续商业版本接入 MyScript 或训练专用在线模型留下接口。

## 五、不要试图理解整张任意草稿

实现困难的根源不是草稿本本身，而是目标定义得过大：

> “实时理解学生在无限画布上写下的任何数学内容。”

这个目标短期不可控。

应该改为**对话驱动的局部草稿取证**。Agent每次只要求学生提供一个有限证据：

- 请画出题目的基本图形；
- 请标出已知边和对应角；
- 请只写出准备使用的定理；
- 请写出第一步等式；
- 请圈出你认为可能有两个解的位置；
- 请完成从这一行到下一行的变形；
- 请在图上补出需要的辅助线。

这样每轮识别对象都很小，系统还提前知道预期内容范围。

例如 Agent 已经要求“写出准备使用的定理”，候选基本只有：

```text
正弦定理
余弦定理
面积公式
其他
```

识别难度远低于开放式理解完整解答。

这也更符合聊天式诊断：草稿不是被动监控，而是 Agent 主动发起的一种诊断探针。

## 六、草稿本应该是半结构化的

完全自由画布最自然，但识别难度最高。完全结构化输入容易实现，却失去了真实草稿价值。

比较合理的是半结构化草稿本：

### 自由区域

学生可以：

- 画图；
- 写公式；
- 列计算；
- 涂改和连接。

### 轻量语义工具

提供可选工具：

- “这是辅助线”；
- “这是已知条件”；
- “这是中间结论”；
- “圈出最终答案”；
- “检查这一步”；
- 边、角、点的快速标注；
- 分类讨论分支标记。

学生不必处处使用，但这些操作能给系统提供高质量标签。

对于几何题，还可以让学生直接在题目图像上：

- 点击一个角；
- 选择一条边；
- 画辅助线；
- 拖动标签；
- 圈出使用的三角形。

这比完全依靠视觉模型猜测学生指的是哪一条边可靠得多。

---

## 七、停笔识别可以做，但不要停笔就反馈

推荐分开两个触发器。

### 识别触发器

以下情况进行后台识别：

- 停笔约 800～1500 毫秒；
- 换行；
- 画出等号；
- 完成封闭图形；
- 点击“检查”；
- 提交草稿。

只处理最近变化的局部区域。

### 对话触发器

识别完成后，不一定立即回复。只有以下情况才介入：

- 学生主动提交；
- 识别到高置信度的关键错误；
- 学生停滞较长时间；
- Agent需要确认某个诊断假设；
- 当前草稿已经提供足够证据；
- 学生请求检查。

也就是：

```text
停笔 → 自动观察
关键证据形成 → 发起对话
```

而非：

```text
停笔 → 立即纠错
```

## 八、草稿识别必须允许不确定

数学草稿识别不可能始终准确。如果系统把 OCR 错误直接当作学生错误，产品会迅速失去可信度。

因此识别结果必须分层：

```text
高置信度
→ 直接用于诊断，但保留证据

中置信度
→ 通过聊天确认

低置信度
→ 不诊断，请学生圈选、重写或口头说明
```

例如：

> 我识别到你这里可能写的是  
> $a^2=b^2+c^2-2bc\cos A$。  
> 是这样吗？

学生只需点击“是”或“不是”。

这种确认本身也是自然的聊天交互，反而进一步强化了聊天式形态。

## 九、真正值得做的创新是“对话式草稿取证”

草稿本单独看，只是输入组件；聊天单独看，只是对话界面。

二者结合后形成更强的创新：

> Agent根据当前诊断假设，主动要求学生在草稿中完成一个最小操作；系统从该操作中提取证据，再通过聊天消除歧义。

可以称为：

- 对话驱动草稿诊断；
- Ink-in-the-loop tutoring；
- 多模态主动诊断；
- 对话-笔迹双通道认知建模。

其循环为：

$$
H_t
\xrightarrow{\text{选择探针}}
Q_t
\xrightarrow{\text{对话/草稿回答}}
E_t
\xrightarrow{\text{证据验证}}
H_{t+1}
$$

其中：

- $H_t$：当前候选诊断假设；
- $Q_t$：Agent提出的问题或草稿任务；
- $E_t$：学生提供的对话和笔迹证据。

系统不是持续窥探整张草稿，而是主动选择最有信息量的观察任务。

## 十、不同解法正是草稿本最重要的价值

只看最终答案，很难区分：

- 正弦定理解法；
- 余弦定理解法；
- 面积转化；
- 向量方法；
- 建系方法；
- 几何定理方法。

草稿可以显示学生的策略选择。

但不能依赖一个模型自由判断“这个学生是什么思维风格”。更科学的做法是先定义有限的策略标签：

```text
图形表征
代数转化
定理直接应用
辅助线构造
向量表示
坐标化
分类讨论
数形结合
```

系统从草稿中输出多个候选策略及置信度，需要时再聊天确认：

> 你这里引入坐标，是准备把几何问题转成代数问题吗？

研究表明，即使模型擅长解数学题，精确找到学生解答中的首个错误仍然困难；将专门的步骤验证结果提供给辅导模型，可以让反馈更有针对性并减少幻觉。([arXiv](https://arxiv.org/abs/2407.09136?utm_source=chatgpt.com))

所以应采用：

```text
模型识别策略候选
+ 数学工具验证步骤
+ 对话确认意图
```

不能只靠多模态模型一次判断。

## 十一、草稿习惯培养可以成为独立产品价值

这个方向值得保留，但必须把“良好草稿习惯”定义成可观察指标，不能泛化成主观性格判断。

可以建立草稿规范量表：

| 维度 | 可观察行为 |
|---|---|
| 图形规范 | 点、边、角是否标注 |
| 条件映射 | 已知条件是否写到图上 |
| 布局组织 | 不同步骤是否分区 |
| 推导完整性 | 关键变形是否跳步 |
| 中间结果 | 是否保存可复用结论 |
| 分类讨论 | 是否明确书写不同情况 |
| 检查行为 | 是否回代或检查定义域 |
| 答案定位 | 最终结论是否清晰标记 |

系统可以在诊断结束后给出：

> 这次你不是不会余弦定理，主要问题是图中没有标注边角对应关系，导致后续将 $a$ 和 $b$ 写反。建议以后先完成“三点、三边、三角”的对应标记，再列公式。

但“草稿习惯是否提升考试成绩”应作为待验证假设，通过前后测、错误率和完成时间评估，不宜直接当作已经证实的结论。

## 十二、分阶段实现，避免被草稿本拖死

### 比赛版

只实现：

## 一、产品界面应这样定型

平板和电脑采用固定分栏：

```text
┌──────────────────┬─────────────────────────────────────┐
│     聊天栏        │             数学草稿纸               │
│                  │                                     │
│ Agent 发题        │  画图、标注、列式、推导、涂改         │
│ 澄清问题          │                                     │
│ 文字提示          │       一道题对应一张独立草稿          │
│ 诊断确认          │                                     │
│ 学习建议          │                                     │
└──────────────────┴─────────────────────────────────────┘
```

手机横向空间不足，改成：

- 草稿纸全屏；
- 聊天栏作为可上拉的底部面板；
- 收到新消息时显示悬浮提示；
- 点击聊天中的草稿引用，自动定位到对应区域。

聊天栏不能只是摆设。完整交互必须表现为：

```text
Agent 通过聊天提出任务
→ 学生主要通过草稿作答
→ 系统后台理解草稿
→ Agent 在聊天中确认意图或继续追问
→ 学生再修改草稿或文字回答
```

因此每次草稿变化都可以视为一种 `Ink Turn`，与文字消息共同组成对话。

系统状态可以简洁表示为：

$$
C_t=(D_t,G_t,S_t)
$$

其中：

- $D_t$：聊天对话状态；
- $G_t$：当前草稿的结构化状态；
- $S_t$：学生认知状态。

Agent 根据三者决定下一轮说什么：

$$
a_t=\pi(D_t,G_t,S_t)
$$

## 二、草稿纸本身的设计方向是对的

建议坚持以下约束：

- 一题一草稿；
- 只有一种黑色笔触；
- 不放复杂工具栏；
- 支持自然涂改、圈画、划线和箭头；
- 支持长按停顿后自动修正直线、圆、椭圆；
- Agent 永远不在学生笔迹层写字或画标记；
- 系统反馈只出现在聊天栏。

这能减少数字工具对真实解题习惯的改变。

但“无限画布”最好定义成：

> **存储空间无限、书写尺度相对固定的连续纸张。**

不要允许任意缩放到非常小或非常大，否则：

- 学生的书写尺度会失真；
- OCR输入分辨率不稳定；
- 空间布局特征难以比较；
- 与真实考试草稿习惯差异过大。

可以无限平移、向下扩展，但保持主要书写比例稳定。

还有一个关键细节：长按修正后的图形不能覆盖原始轨迹。系统应同时保存：

```text
原始笔迹
修正后几何图元
修正操作事件
```

因为修正后的标准直线是系统辅助结果，不能直接拿来评价学生画图能力。

## 三、真正的技术核心不是 OCR，而是“时序草稿场景图”

你说得对，公式不是最大难点。PaddleOCR 的公式识别链路已经能将图片中的手写公式转换成 LaTeX；真正困难的是辅助线、标签、箭头、圈画和空间关系。当前多模态模型在几何图中的精细定位和关系识别上仍有明显不足，辅助线理解也是专门研究问题。([PaddleOCR](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/formula_recognition.html?utm_source=chatgpt.com))

因此不能把整张草稿截图直接丢给一个视觉模型，期待它自动还原全部思路。更合理的中间表示是：

$$
G_t=(V_t,E_t,T_t)
$$

即一个**时序草稿场景图**。

### 节点 $V_t$

包括：

- 原始笔画组；
- 直线、线段、圆、椭圆、弧；
- 三角形等组合图形；
- 点名、边名、角名；
- 数学公式；
- 箭头；
- 圈选区域；
- 单下划线、双下划线；
- 删除线；
- 直角、等长、平行等关系标记；
- 文字旁注。

### 边 $E_t$

表达：

- 某标签位于某点附近；
- 某文字标注某条边；
- 某辅助线连接两个点；
- 某箭头指向某表达式；
- 某圆圈包围某个结果；
- 某双下划线强调某个结论；
- 两条线相交、平行或垂直；
- 某公式在某个图形之后写出；
- 某一步由前一步修改而来。

### 时间 $T_t$

记录：

- 先画了什么；
- 后补了什么；
- 在哪里停顿；
- 哪部分被划掉；
- 哪条辅助线反复修改；
- 最终保留了哪种解法。

近期在线数学笔迹研究也在强调笔画到符号、空间关系和结构的显式映射；单纯输出整段 LaTeX 会丢失笔迹与符号之间的对应，不利于交互式错误定位。([arXiv](https://arxiv.org/abs/2508.19773?utm_source=chatgpt.com))

这张图才是学生“怎么想”的机器表示。

## 四、矢量参数不是无用，恰恰适合识别非公式信息

通用大模型不能直接稳定理解一长串坐标，但不代表矢量笔迹没有价值。

对于基础图形和标记，矢量轨迹通常比截图更容易处理：

| 草稿元素 | 主要识别方式 |
|---|---|
| 直线、线段 | 直线拟合与残差判断 |
| 圆、椭圆 | 圆/椭圆拟合 |
| 折线、三角形 | 拐点检测和闭合关系 |
| 箭头 | 主线与端部短线关系 |
| 圈选 | 闭合轨迹与包围关系 |
| 单/双下划线 | 平行近邻线段检测 |
| 删除线 | 高频交叉和覆盖关系 |
| 长时间停顿 | 轨迹时间戳 |
| 修改和回退 | 笔画增删顺序 |

这些基础判断很多不需要大模型，用几何算法即可完成。

真正需要模型的是：

- 这条线是辅助线还是原图重画；
- 圈起来的内容表示重点、疑问还是最终答案；
- 箭头表示推导、对应还是引用；
- 学生画这条线的意图是什么；
- 当前草稿属于哪种解题策略。

所以推荐使用三种信息共同判断：

```text
原始矢量轨迹
+ 局部渲染图像
+ 当前题目和聊天上下文
```

已有研究已经尝试同时将数字笔迹表示为时序 stroke token 和图像，而不是只采用其中一种。([arXiv](https://arxiv.org/html/2402.15307v1?utm_source=chatgpt.com))

## 五、识别架构应分四层

### 第一层：本地几何处理

前端实时完成：

- 笔画采集；
- 轨迹简化；
- 停顿检测；
- 长按图形修正；
- 脏区域计算；
- 圆、直线、箭头等初步识别。

这一层延迟低，不调用模型。

### 第二层：局部内容识别

停笔后只处理最近改变的区域：

```text
新增笔画
→ 计算局部边界
→ 光栅化为高分辨率图片
→ 文字/公式/图形分类
```

公式交给 Paddle 公式模型，文字交给 OCR，基础图形优先采用矢量几何结果。Paddle 的现有公式链路支持手写公式，但其输出重点是 LaTeX，不负责理解整张几何草稿的语义。([PaddleOCR](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/formula_recognition.html?utm_source=chatgpt.com))

### 第三层：场景图融合

融合：

- 矢量图元；
- OCR文本；
- 数学公式；
- 空间关系；
- 书写顺序；
- 题目中的原始图形。

得到当前 `Ink Scene Graph`。

### 第四层：多模态语义判断

只在必要时调用 VLM，并给它四类输入：

1. 当前完整草稿缩略图；
2. 最近修改区域高清图；
3. 结构化场景图；
4. 当前题目和聊天目标。

模型输出的不是“完整答案”，而是有限候选：

```json
{
  "strategy_candidates": [
    {"name": "余弦定理", "confidence": 0.71},
    {"name": "作高后使用直角三角形", "confidence": 0.22}
  ],
  "new_auxiliary_line": {
    "from": "A",
    "to": "BC",
    "possible_intent": "作高"
  },
  "uncertainties": [
    "垂足标签无法确认"
  ]
}
```

低置信度时由聊天确认：

> 我看到你从 $A$ 向 $BC$ 画了一条线。你是准备作高，还是只是划分图形？

这样不需要强迫模型一次识别正确。

## 六、可以形成一套“考试自然标记语法”

你提出圈起来、双划线的思路很有价值，但不能把它做成一套只有软件里才能使用的暗号。所有标记应当在真实考试草稿纸中也自然成立。

建议先支持少量高价值标记：

| 自然标记 | 可能含义 | 系统处理 |
|---|---|---|
| 圈起来 | 重点、待求量、疑问或结果 | 结合上下文判断，必要时询问 |
| 双下划线 | 最终结论或关键中间量 | 作为高优先级候选 |
| 箭头 | 推导、对应或引用 | 建立两个区域的关系 |
| 划掉 | 放弃的步骤或计算错误 | 保留历史，不进入当前解法 |
| 在图上打相同短线 | 两边相等 | 建立等长候选 |
| 小方框 | 直角 | 建立垂直候选 |
| 两个分支排列 | 分类讨论 | 建立解法分支 |
| 在图上补字母 | 点、边、角标注 | 绑定邻近几何元素 |

这些标记不能直接当作绝对语义。例如圈起来有时代表答案，有时代表“这里有问题”。系统应学习学生个人习惯，或在第一次出现时聊天确认：

> 你通常用双下划线标记最终结果，对吗？

之后可以作为该学生的个性化交互偏好，但仍保留置信度。

这里真正的创新不是手势本身，而是：

> 将考试中自然存在的草稿标记转化为低成本的机器可读语义，同时不要求学生学习额外的数字化操作规范。

## 七、模型不在草稿上标注是一个正确约束

这样做有三个好处：

1. 学生草稿保持原始性，不被系统输出污染；
2. 可以区分学生本人写的内容和系统建议；
3. 更接近真实考试环境。

但纯文字有时难以指出具体位置。可以采用“引用而不改写”的方式：

> 你右上角圈出的第二个式子中，$\sin B$ 对应的边似乎写成了 $a$。你能重新确认一下边角对应吗？

聊天消息内部保存一个 `region_id`。学生点击消息时，画布自动平移到对应区域，并短暂显示边框或聚焦动画；这个边框属于界面覆盖层，不写入笔迹，也不改变草稿。

## 八、草稿信息可以分三级使用，降低实现风险

不必第一版就完全理解任意草稿。

### L0：行为层

不理解具体内容，也能观察：

- 是否先画图；
- 是否反复修改；
- 停顿在哪里；
- 是否进行分类讨论；
- 是否主动检查；
- 是否有明确最终答案；
- 草稿是否过度杂乱。

### L1：结构层

识别：

- 图形；
- 辅助线；
- 标签；
- 圈画；
- 箭头；
- 公式区域；
- 解题分支。

### L2：语义层

进一步判断：

- 使用了什么方法；
- 辅助线目的是什么；
- 哪一步发生数学错误；
- 当前草稿体现了哪种思维策略。

即使 L2 还不够稳定，L0 和 L1 已经能形成可展示、可量化的创新能力。当前研究也表明，多模态模型对客观计算型手写内容理解较好，但对学生自由数学图示和主观图形意图的判断明显更困难。([arXiv](https://arxiv.org/abs/2510.05538?utm_source=chatgpt.com))

## 九、这个形态的核心创新应重新表述

不是“AI 草稿纸”，也不是“实时 OCR”。

建议定义为：

### 1. 双通道聊天

> 对话不再只由文字组成，学生的每次草稿变化也是一个可解释的对话回合。

### 2. 时序草稿建模

> 不只看最终截图，保留图形构造、辅助线、标注、推导和修改的发生顺序。

### 3. 解题策略识别

> 同一答案可以识别出不同解法路径，并进一步判断学生的策略偏好和迁移能力。

### 4. 草稿习惯诊断

> 从图形标注、条件映射、分类讨论、结果定位和检查行为中评价草稿使用习惯。

### 5. 证据驱动的聊天追问

> Agent 不凭最终答案直接归因，而是根据草稿证据选择下一句最有区分力的问题。

## 十、比赛版应该把范围收得足够精确

比赛 Demo 不要承诺“完全理解任意数学草稿”。只针对解三角形实现五类关键证据：

1. 是否主动画三角形；
2. 是否正确标注边角对应；
3. 选择正弦定理、余弦定理、面积法还是作辅助线；
4. 是否出现多解或分类讨论；
5. 是否明确保留最终结论并检查条件。

重点识别以下元素：

```text
三角形
点和边角标签
直线/高线/中线/角平分线
圆和外接圆
箭头
圈选
双下划线
删除线
正弦/余弦/面积公式
```

## 一、PaddleOCR-VL 能否直接按提示词输出“圈起来的内容”

结论是：

> **原版 PaddleOCR-VL 不适合被当作通用视觉问答模型，通过任意自然语言提示稳定提取“被圈画的内容”。**

PaddleOCR-VL 当前的定位是文档解析。它的 `prompt_label` 更接近“指定识别任务类型”，例如 OCR、公式、表格、图表等，并且只有关闭版面分析、直接调用 VLM 时才生效；官方接口没有把它定义成任意自然语言指令接口。([PaddleOCR](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PaddleOCR-VL.html))

因此下面这种调用不能视为官方保证能力：

```text
请找出学生圈起来的内容，并说明它是什么意思
```

模型有可能偶然完成，但稳定性、定位精度和结构化输出都难以保证。

PaddleOCR-VL-1.5/1.6 对下划线、强调符号、异形区域定位和 text spotting 有所增强，但这仍然主要服务于文档元素识别，不等于理解“学生为什么把这里圈起来”。([arXiv](https://arxiv.org/html/2601.21957))

### 更可靠的做法

把任务拆成两步：

```text
先找到圈画区域
→ 再识别圈内内容
```

#### 数字草稿模式

因为有原始矢量轨迹，圈选区域比较容易判断：

1. 找到闭合或近似闭合轨迹；
2. 判断其包围区域；
3. 获取圈内相交或包含的笔画；
4. 将该区域渲染成局部图像；
5. 交给 OCR、公式识别或多模态模型。

这一步甚至不需要训练模型，几何算法就能完成初版。

#### 纸面拍照模式

只有静态照片时，可以：

1. 图像矫正；
2. 检测闭合圈线；
3. 建立圈线内部掩膜；
4. 裁剪圈内图像；
5. 再调用 PaddleOCR-VL 或通用 VLM。

规则算法难以处理涂改、重叠和不规则圈线时，再增加一个轻量实例分割模型，专门识别：

- 圈选；
- 下划线；
- 双下划线；
- 删除线；
- 箭头；
- 重点框。

最终交给模型的输入应是：

```text
完整页面缩略图
+ 圈画区域高清裁剪图
+ 圈画区域坐标
+ 当前题目
+ 当前聊天上下文
```

而不是让一个 OCR 模型从整张草稿中自行猜测。

## 二、你记得的 Paddle 架构是对的

完整的 PaddleOCR-VL 并不是一个 VLM 直接吃整页。

当前完整流程是：

```text
整页图像
→ PP-DocLayoutV3 版面分析
→ 检测元素并确定阅读顺序
→ 裁剪元素级子图
→ PaddleOCR-VL-1.6-0.9B 分别识别
→ 合并为 Markdown / JSON
```

官方文档明确强调，完整 PaddleOCR-VL 是“版面分析 + VLM 识别”的两阶段系统，仅运行 0.9B VLM 组件不等同于完整流水线。([GitHub](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PaddleOCR-VL.en.md))

PaddleOCR-VL-1.5 开始使用 PP-DocLayoutV3。该模型可以同时输出分类、边界框或多边形、分割结果以及阅读顺序；然后 VLM 负责识别文字、表格、公式、图表和印章等元素。([arXiv](https://arxiv.org/html/2601.21957))

所以你的思路是合理的：

> 先通过视觉模型分区，再把各区域交给识别模型和主推理模型。

但现成 PP-DocLayoutV3 的类别与我们需要的类别并不完全一致。

### 官方版面模型擅长区分

- 文本；
- 标题；
- 图片；
- 表格；
- 公式；
- 图表；
- 页眉页脚；
- 印章等。

官方版面检测模型主要在试卷、论文、书籍、报告和合同等文档上训练。([PaddleOCR](https://www.paddleocr.ai/main/en/version3.x/module_usage/layout_detection.html))

### 它不会天然稳定区分

- 原题图形；
- 学生补画的辅助线；
- 边角标签；
- 被圈出的中间结果；
- 草稿计算区；
- 放弃的推导；
- 最终答案区；
- 分类讨论分支；
- 箭头的意图；
- 学生重新描画的图形。

所以不能直接把 PP-DocLayoutV3 当作“草稿语义分割器”。

- 最近变化区域高清图；
- 特定时间段的新增笔迹图；
- 原题与学生笔迹的叠加图；
- 只显示学生新增笔迹的透明图层。

多模态模型主要看这些图像，而不是直接读数万条矢量坐标。

当学生停笔一段时间或主动提交时，自动提供：

1. 当前题目；

4. 整体草稿缩略图；
5. 前一时刻与当前时刻的差异图；
6. 当前学生画像的少量相关字段。

- 学生正在画图还是列式；
- 是否新添辅助线；

- OCR；

```text
→ 需要精确内容时调用OCR/公式工具
```

主模型首先收到：

- 校正后的整页图；
- 当前题目；

1. 文档扫描和图像校正；

## 六、多次拍照也能形成离散过程

普通纸面虽然没有实时轨迹，但可以把每次拍照视为一个观察时刻：

$$
I_0,I_1,\ldots,I_n
$$

通过文档配准得到：

$$
\Delta I_t=I_t-I_{t-1}
$$

主模型可同时查看：

- 上一张完整草稿；
- 当前完整草稿；
- 两者的新增内容；
- 学生本轮问题。

于是仍然可以识别：

```text
第一次照片：画出三角形并标条件
第二次照片：新增一条高线和面积公式
第三次照片：划掉面积法，改用余弦定理
```

实时数字草稿获得的是连续过程，纸面拍照获得的是离散过程，两者只是观测密度不同，可以共享同一个 Tutor Agent。

## 七、推荐的感知 Harness

整体可抽象为：

$$
O_t=\operatorname{Observe}(R_t,Q_t,H_t)
$$

其中：

- $R_t$：系统自动提供的近期视觉证据；
- $Q_t$：Agent 主动发起的工具查询；
- $H_t$：题目、聊天和历史状态。

主模型维护当前假设：

$$
\mathcal H_t=
\{
\text{学生可能使用的方法},
\text{当前困难位置},
\text{可能错因},
\text{需要补充的证据}
\}
$$

然后决定：

$$
a_t\in
\{
等待,
继续观察,
查看局部,
查看历史,
调用识别工具,
询问学生,
给出提示
\}
$$

这形成一个完整的主动视觉循环：

```text
自动获得近期变化
→ 建立初步假设
→ 判断证据是否足够
→ 主动调用观察工具
→ 必要时通过聊天询问
→ 更新诊断假设
→ 决定是否干预
```

## 八、系统不需要追求“完整解析草稿”

产品目标可以进一步收紧为：

> 主 Agent 能够在需要时取得足够证据，以做出下一步教学决策。

它不必每一刻都生成完整、严格的草稿场景图。

比如当前只需要判断学生是否意识到作高，主模型只需看到最近新增的一条顶点到对边的线，再询问：

> 你刚才补的这条线，是准备作 $BC$ 边上的高吗？

确认后即可继续诊断。没有必要先完成点线关系识别、垂直检测、标签绑定和形式化几何建模。

这是 Agent 方法相对传统解析流水线的优势：允许不完整理解，并通过工具与对话主动补足。

## 九、仍需保留的确定性基础设施

Agentic 不等于把所有任务都扔给大模型。以下内容仍应由系统保证：

- 笔迹和照片可靠存储；
- 时间、空间索引；
- 图层和版本管理；
- 区域裁剪；
- 图像配准；
- 多尺度渲染；
- 差异计算；
- 工具权限与调用预算；
- 每个诊断结论引用了哪些图像或轨迹；
- 整个会话可重放。

主模型负责决定“看什么、如何理解、如何追问”，基础设施负责保证“它随时能准确拿到想看的证据”。
