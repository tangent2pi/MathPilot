# 03. 选题、切题与对话式学习流

## 1. 设计目标

学生体验是一段普通对话：可以做题、追问、要求讲解、突然换方向，也可以说“下一题简单点，但别再考刚才那种计算”。系统内部不要求学生选择复杂模式，却仍要保证：

- 一道题的回答、提示、诊断和科学证据不会混到下一题；
- 切题前该结算的事实已经结算，后台总结失败不会卡住学生；
- 自由训练和阶段训练复用同一流程；
- 模型能理解复杂自然语言选题要求；
- 用户改变要求时，旧选题结果不能抢先提交；
- 同一次切题不会因重试开出两道题。

## 2. 身份分离

### 2.1 ConversationThread

学生看到的对话。规范消息存储由 MathPilot 应用持有，而不是以 Pi Session 文件作为唯一事实源。

一个 Thread 可以包含：

- 多个 QuestionSession；
- 多个前台 Pi 上下文 epoch；
- 自由选择和程序选择的交替；
- 普通文本、题卡、草稿引用和系统状态消息。

assistant-ui 使用 External Store Runtime 渲染当前 Thread 的应用消息。Thread 列表、路由和持久化由 MathPilot 应用壳直接持有，不依赖已标记 deprecated 的 `ExternalStoreThreadListAdapter`。UI 不需要知道 Pi 是否轮换过上下文，也不承担题目领域事务。

题卡、回答收据、判定、关闭摘要和个人记录的具体读模型与组件契约见 [07-前端设施后端读模型与统一交互语言.md](./07-前端设施后端读模型与统一交互语言.md)。其中正式题卡由 `QuestionOpened` 投影，不是模型展示工具。

### 2.2 ForegroundAgentEpoch

前台 Teaching Agent 的一段 Pi 模型上下文：

- 可以因上下文长度、模型更换、故障恢复而轮换；
- 通过 Thread 消息摘要、当前题和只读工作区恢复连续性；
- 不作为公开 URL、QuestionSession 或学习证据的 ID；
- 后台 AgentAttempt 不能写入或切换它。

### 2.3 QuestionSession

一题一个领域边界：

```text
question_session_id
conversation_thread_id
learning_activity_id?
selection_intent_revision
question_revision_id / external_question_ref
frozen_measurement_contract
source                     catalog | student_external | generated_provisional
lifecycle                  active | finalizing | closed | abandoned
opened_at / closed_at
close_reason
version
```

QuestionSession 冻结题目 revision、rubric、measurement targets、诊断规则 revision 和证据政策。题库后来发布新版本，不改变已经发生的测量。

### 2.4 LearningActivity

可选的目标/策略容器，不是另一种 UI 模式：

```text
learning_activity_id
goal
source                     student | program | teacher
policy                     coverage, budget, stopping, evidence requirements
status
created_at / closed_at
```

用途：阶段测评的覆盖预算、学习计划条目、教师布置任务。自由聊天可以完全没有 LearningActivity。一个 Thread 可以跨越多个 Activity，也可以在 Activity 中穿插自由题。

### 2.5 RuntimeWorkflow / AgentAttempt

评分、诊断、选题、Light、REM、Deep 的后台运行身份。它们只产生结构化结果和领域事实，不成为可见会话，不共享前台 Pi Session。

## 3. 普通对话与后台状态并不冲突

“普通对话”指：

- 学生不需要进入一个独立的“测评页面”或选择一套状态机；
- 发题、回答、提示、总结和换题都可以表现为普通消息；
- 题卡只是消息的一种渲染，而不是不可退出的表单流程；
- 学生随时可以自由输入、跳过、改需求。

后台仍保留少量明确状态，因为并发、证据和幂等不能靠自然语言推测。状态属于领域服务，不要求在 UI 暴露为步骤条。

## 4. 自由训练与阶段训练统一

两者唯一根本差异是“当前 SelectionIntent 从哪里来”：

| 场景 | 意图来源 | 可选硬策略 |
|---|---|---|
| 自由训练 | 学生自然语言 | 权限、题目有效性、输入能力等平台约束 |
| 阶段训练 | 程序基于 Activity 目标生成 | 覆盖、预算、正式证据等 Activity policy |
| 教师指定 | 教师要求 | 班级/题目范围和教师策略 |

进入下一步后都走：

```text
SelectionIntent → 模型选题 → QuestionSession → 对话教学/诊断
→ 切题事务 → M/R/C_e → 下一次 SelectionIntent
```

科学事实不因来源不同而改变资格。计划履约是独立投影：默认只有由相应 Activity 委派且满足 policy 的题才计入“计划已完成”，但自由题产生的有效 Observation 仍会更新真实科学状态。

## 5. SelectionIntent：保留自然语言，不发明万能 DSL

```text
selection_intent_id
conversation_thread_id
student_id
revision
source                     student | program | teacher
natural_language_request
activity_constraints?       宿主提供的少量硬约束
context_snapshot_ref
supersedes_intent_id?
created_at
```

`natural_language_request` 是规范输入。例如：

> 想做一道面积题，但别再纯代公式；最好需要自己发现辅助线，计算别太长。如果刚才那个补角问题还没确定，可以顺便确认，但不要再追问口头题。

不把这段话提前压成一个试图覆盖所有未来需求的 `DemandClause[]`。宿主只分离真正的硬约束，例如租户可见性、Activity 规定的范围、题目必须有正式 rubric；偏好和折中由模型理解。

任何新的学生需求都创建更高 `revision`。旧 Intent 不原地修改，便于解释“为什么当时选了这题”。

## 6. 模型主导选题

### 6.1 分工

模型负责：

- 理解自然语言需求和隐含折中；
- 结合 M/R/C_e、历史题目和 Activity goal；
- 迭代搜索候选；
- 比较候选并最终选择；
- 说明满足了什么、哪些偏好无法同时满足。

程序负责：

- 注入已授权的状态快照；
- 过滤未发布、不可见、版本失效或输入形式不兼容的题；
- 对正式测量要求 rubric/measurement target；
- 防近期重复和并发占用；
- 在提交时重验最新 Intent revision；
- 原子创建 QuestionSession。

程序不再维护一个固定六目标权重评分器来假装理解复杂需求。

### 6.2 单一选题工具

Selector Agent 除结构化 `respond` 外只得到一个业务工具：

```text
question_catalog({
  query: string,
  cursor?: string,
  limit?: number
}) -> {
  candidates: [{
    question_revision_id,
    stem,
    dimensions,
    difficulty,
    representation,
    estimated_burden,
    error_roles,
    measurement_eligibility,
    provenance
  }],
  next_cursor?
}
```

硬权限和 Activity 限制由宿主从任务上下文注入，不允许模型传 tenant、student、SQL 或任意 scope。搜索结果以小批量返回完整题干和选题所需元数据，因此不再暴露相似的 `search` + `get` 两个工具。模型可以多次调用同一工具，逐步修改自然语言 query。

工具不返回标准答案、完整解析和会泄漏给前台的隐藏内容。真正教学所需内容在选定并提交后，由 QuestionSession 的授权投影提供。

### 6.3 选择输出

```text
SelectionDecision
  intent_id / intent_revision
  chosen_question_revision_id
  satisfied_requirements[]
  unsatisfied_preferences[]
  scientific_purpose          measure | discriminate | remediate | verify | practice
  target_dimensions[]
  target_error_causes[]
  evidence_refs[]             状态和候选引用
  model/prompt/skill version
```

模型输出 Decision 后还没有生效。`commitSelection` 在数据库事务中：

1. 锁定 Thread/学生当前选题槽；
2. 校验 `intent_revision` 仍为最新；
3. 重验 question revision 的可见性和资格；
4. 确认当前没有 active QuestionSession，也没有另一道新题已经提交；
5. 冻结 measurement contract；
6. 创建一个 active QuestionSession；
7. 追加 `QuestionOpened` 和可见题目消息。

任一校验失败返回 `stale_intent | candidate_invalid | already_committed`，Selector Workflow 决定重搜或正常结束，不覆盖新状态。

## 7. 需求多变时如何工作

### 7.1 选题前改变需求

学生发出新要求：

1. 新建 SelectionIntent revision；
2. Signal 当前 SelectQuestionWorkflow；
3. 正在运行的 AgentAttempt可以取消；即使取消不及时，旧 Decision 也无法通过 revision 校验；
4. 用最新 Intent 重新选择。

正确性依赖最终提交校验，而不是依赖“取消一定及时”。

### 7.2 做题中改变需求

- “这题太难，换简单点”：产生 CutRequest，当前题以 `student_switch` 关闭，现有证据按真实状态结算；新 Intent 保存“更简单”。
- “先给个提示”：不切题，写 InterventionEvent，之后的成功不再算独立。
- “不要追问，直接下一题”：Claim 以 skipped/inconclusive 关闭，切题继续。
- “还是回刚才那题”：不复活已经关闭的 QuestionSession；可创建同题 revision 的新 Session，并明确是 revisit，防止证据混写。

### 7.3 切题后马上又改需求

QuestionSession 已关闭不回滚。尚未提交下一题时更新 Intent；若下一题已原子提交，则它是新的 active Session，学生再次切题即可。这样历史始终线性可解释。

## 8. 切题事务

### 8.1 CutRequest

```text
cut_request_id           幂等键
conversation_thread_id
question_session_id
expected_session_version
reason                   completed | student_switch | skipped | teacher_switch |
                         system_policy | abandoned
next_intent_ref?
requested_at
```

同一个 `cut_request_id` 重试必须返回同一结果。

### 8.2 硬路径

```text
1. Freeze
   - current QuestionSession: active -> finalizing
   - 拒绝新的当前题 Attempt；之后的用户消息排入下一意图/普通消息

2. Final judgment
   - 使用已完成 Judgment
   - 或在有未判 Attempt 时执行有界评分
   - 服务耗尽重试后显式写 unresolved，不永久阻塞

3. Diagnostic close
   - concluded / inconclusive / skipped / unclassified
   - 将已发生关系写成 ErrorEvidence

4. Scientific commit（同一领域事务）
   - 编译并追加 Observation / DelayedReviewEvent / ErrorEvidence
   - 重放或增量校验 M/R/C_e projection
   - 写 QuestionClosed、close reason、version

5. Next selection
   - 读取最新 SelectionIntent
   - 启动/唤醒 SelectQuestionWorkflow
```

第 4 步未提交成功前不能展示下一道题。它是防止证据跨题和双开的硬屏障。

### 8.3 软路径

QuestionSession 关闭后异步执行：

- Light evidence atom；
- 教学会话摘要；
- Thread/AgentEpoch 连续性摘要；
- REM/Deep 触发检查；
- 分析、报表和非关键通知。

这些失败会记录、重试或进入人工检查，但绝不让学生停留在“正在总结”而无法下一题。现有 `closeChain` 在模型 TSS 失败时不关闭 Session 的设计应被替代。

### 8.4 为什么不能舍弃切题

若只在消息流中插入下一张题卡而没有 Cut：

- 迟到的判题可能写到错误的当前题；
- 同一回答可能被两个选择器读取；
- Dream 不知道 Light 应以哪一题为边界；
- 教师纠正无法准确重放；
- 重试可能重复开题；
- 自由/阶段的计划履约无可靠关联。

所以切题流程不是特殊交互补丁，而是自然对话背后的最小一致性事务。

## 9. QuestionSession 生命周期

只保留四个顶层状态，具体评分/诊断进度由自己的事实对象表达：

| 状态 | 可接收本题 Attempt | 可切题 | 说明 |
|---|---:|---:|---|
| `active` | 是 | 是 | 正常对话学习 |
| `finalizing` | 否 | 幂等返回已有 Cut | 正在完成硬结算 |
| `closed` | 否 | 幂等返回关闭结果 | 事实已提交 |
| `abandoned` | 否 | 否 | 管理性终止；也必须明确是否产生科学事实 |

不把 `GRADE/DIAGNOSE/PROBE_AWAIT/TSS/QUEUE_DREAM` 全塞进同一状态枚举。它们分别属于 Judgment、Claim 和 Workflow，减少交叉状态爆炸。

## 10. 无当前题的普通对话

Thread 可以没有 active QuestionSession。学生可能：

- 问概念；
- 讨论历史题；
- 修改训练需求；
- 等待选题；
- 查看报告。

只有与一题明确绑定的 Attempt 才进入科学证据。普通解释消息可以进入会话历史和语义摘要，但不能偷偷制造 Observation。

## 11. 外部题与模型生成题

### 11.1 学生提供外部题

创建 `source=student_external` 的 QuestionSession，题干快照冻结。若没有验证后的 rubric/measurement contract：

- Teaching Agent 可以正常帮助；
- Judgment 可以给教学反馈；
- 科学内核只接收 provisional 事实；
- 后续内容审核通过后不能追溯性篡改原证据资格，除非创建带明确审核事件的新 Observation 并可审计。

### 11.2 模型临时生成题

默认只能 `teaching_only`。若要用于正式测量，必须先通过独立校验：答案、rubric、测量目标、难度与重复性。不要在 Selector Agent 内同时“生成题、审题、选题、提交”，这会消除独立门禁。

## 12. 失败、并发和恢复

| 场景 | 处理 |
|---|---|
| 学生连点两次下一题 | CutRequest 幂等；只有一个 closing commit |
| 两个浏览器标签同时切题 | session version + 当前选题槽锁；一个成功，另一个读取结果 |
| 评分模型超时 | Workflow 重试；耗尽后写 unresolved 并继续结算 |
| 数据库在科学提交前失败 | Workflow 重试 Activity；下一题不可见 |
| 数据库提交成功但 Workflow 未收到响应 | 幂等键重读已提交结果，不能重复写事实 |
| Selector 模型失败 | 维持无 active 题，重试或在对话中说明未选出；不回滚已关闭题 |
| 选题时用户改需求 | 旧 revision 提交失败，新 Workflow 接管 |
| 题目在选出后被撤回 | commit 重验失败并重搜 |
| 前台 Pi Epoch 崩溃 | 新 Epoch 从应用消息、当前 Session 和工作区恢复 |
| 后台 AgentAttempt 崩溃 | Temporal 重试新的 Attempt；旧 Attempt 只留审计，不暴露给学生 |
| Light/Dream 失败 | 软异步重试，不影响下一题 |

## 13. 一段完整使用场景

```text
学生：我想练面积，但计算别太长。
→ SelectionIntent r1(source=student)
→ Selector 用 question_catalog 搜索并提交 Q1
→ 创建 QuestionSession S1，普通消息显示题卡

学生作答错误。
→ Judgment 指向两个候选错因
→ 一个短探针把候选分开，保存正反 ErrorEvidence
→ Teaching Agent 给针对性提示；提示后改对只记教学事实

学生：下一题想换成需要自己补线的，顺便确认刚才的问题。
→ CutRequest(S1)，硬结算 Observation/C_e，S1 closed
→ SelectionIntent r2
→ Selector 选择 role=verifies_near 且需要补线的 Q2
→ 原子创建 QuestionSession S2
→ S1 的 Light 在后台运行，不阻塞 Q2

学生在 Q2 独立答对。
→ S2 关闭时 M 更新；C_e 得到近迁移反证，可能进入 improving
→ Dream 以后可附注“标准图与隐式补线情境差异”，但不改 M/C_e 状态
```

## 14. 验收标准

1. 同一可见 Thread 可连续完成至少十个 QuestionSession，证据引用无串台；
2. 前台 Pi Epoch 轮换后消息和当前题连续，Thread ID 不变；
3. 自由/阶段/教师三种 Intent 经过同一 Selector 和 Cut 流；
4. 复杂自然语言偏好可通过同一 catalog 工具多轮搜索，不需新增工具或 DSL 字段；
5. 用户在选题中更新需求，旧 Decision 100% 无法提交；
6. 并发 Cut、重试和服务重启都只产生一个 closed event 和最多一个下一题；
7. TSS、Light、REM、Deep 任一失败不阻塞下一题；
8. 未验证外部题不会更新正式 M/R/C_e；
9. 关闭后的同题重访创建新 Session，不篡改旧会话；
10. 任意 QuestionSession 都能追溯其冻结题目、规则、Intent 和科学提交。
